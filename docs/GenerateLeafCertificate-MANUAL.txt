====================================================================================================
 1  WHAT THE SCRIPT DOES
====================================================================================================
 A "leaf" is a certificate at the end of the chain. A server, a person or a program uses it.
 pki_setup.ps1 builds the CAs. This script uses an intermediate CA to sign leaves.

 One command makes SEVEN certificates, each in all file formats:

     .\GenerateLeafCertificate.ps1 -DnsName www.example.com

 For every certificate the script:
   1. makes a new private key,
   2. signs the certificate with the intermediate CA you chose,
   3. checks the certificate against the root CAs,
   4. writes the files and the hash files.

 The script never changes the CAs. It never writes into the pki folder.
 It never overwrites a folder. A second run makes a new folder with the date and time.

====================================================================================================
 2  THE WORDS YOU NEED
====================================================================================================
 Leaf           A certificate that is not a CA. The last one in the chain.
 Purpose        What the certificate may be used for. Example: a web server, or code signing.
 EKU            "Extended Key Usage". The list of purposes inside the certificate.
 SAN            "Subject Alternative Name". The server names the certificate is valid for.
 CN             "Common Name". The main name in the subject.
 DV, OV, EV     Validation levels. DV = domain only. OV = organization. EV = extended.
 Quadrant       One of four CA groups: Classic or Quantum, with or without FIPS (section 9).
 PFX            One file that holds the key and the certificate. It has a password.
 Chain          The leaf, the intermediate CA and the root CAs, in order.
 Full list      GLOSSARY.txt and GLOSSARY-ENGLISH.txt.

====================================================================================================
 3  BEFORE YOU START
====================================================================================================
 Check these four things. The script stops with a clear message if one is missing.

   1. The PKI exists. You ran pki_setup.ps1 and the folder .\pki is there.
      If not: pki_setup-MANUAL.txt, section 4.
   2. PowerShell 7 or newer.            Check:  pwsh -v
   3. OpenSSL 4.x with the FIPS module. Check:  .\GenerateLeafCertificate.ps1 -Check
      The check prints four lines. All four must say [PASS]:
          [PASS] OpenSSL 4.x            [PASS] ML-DSA (default provider)
          [PASS] FIPS provider          [PASS] ML-DSA (FIPS provider)
      A line that fails stops the script only if THIS run needs it. Fix: run
      .\Install-DevEnvironment.ps1 -Only OpenSSL,7Zip as administrator, then open a NEW window.
      OpenSSL 3.x is refused.
   4. The files are not blocked. If you downloaded the zip, run once:
          Get-ChildItem -Path . -Recurse -File | Unblock-File
      Later the script unblocks and unlocks its own folders at every start. To do only that:
          .\GenerateLeafCertificate.ps1 -Unblock

 The script runs on Windows 11 24H2 or newer, Windows Server 2025 and 2022, and on Linux with
 pwsh. Windows Server 2022 makes Classic certificates only. Windows 10 and macOS are refused
 (exit code 5).

====================================================================================================
 4  FIRST RUN, STEP BY STEP
====================================================================================================
 Step 1   Open PowerShell 7 in the project folder.
 Step 2   Check OpenSSL:
              .\GenerateLeafCertificate.ps1 -Check
 Step 3   Make the set. Use a name that your server really has:
              .\GenerateLeafCertificate.ps1 -DnsName www.example.com
 Step 4   Read the table at the end:

              PURPOSE          KEY          DAYS   EXPIRES     SUBJECT CN / FOLDER
              ServerAuth       RSA-2048     397    2027-11-18  www.example.com
              ClientAuth       RSA-2048     397    2027-11-18  www.example.com
              ServerAuth+ClientAuth  ...
              CodeSigning      RSA-4096     397    ...
              EmailProtection+ClientAuth ...
              TimeStamping     RSA-2048     397    ...
              OcspSigning      RSA-2048     365    ...

 Step 5   Open the folder .\leafcerts\www.example.com. There is one folder for each purpose.
 Step 6   List what you made:
              .\GenerateLeafCertificate.ps1 -List
 Step 7   Put the files on your server (section 8) or use Create-WebServerConfig.ps1 for nginx
          or Apache.

 The defaults when you give nothing else: EV level, Classic track, no FIPS, RSA 2048 (code
 signing RSA 4096), 397 days.

====================================================================================================
 5  THE SEVEN CERTIFICATES (PURPOSES)
====================================================================================================
 A normal run makes one certificate for each purpose. Do not mix purposes in one certificate.

 Purpose              Folder                 For                                 Names it carries
 -------------------  ---------------------  ----------------------------------  ------------------
 ServerAuth           serverauth             A TLS server (web site, API)        Your DNS / IP
 ClientAuth           clientauth             A TLS client (mutual TLS, VPN)      Your DNS / IP
 ServerClientAuth     serverauth-clientauth  A service that is server AND client Your DNS / IP
 CodeSigning          codesigning            Sign programs and scripts           None
 EmailProtection      emailprotection        S/MIME e-mail, also client login    E-mail address
 TimeStamping         timestamping           RFC 3161 time stamp server          None
 OcspSigning          ocspsigning            OCSP responder                      None

 Notes:
   * The three TLS certificates are three separate certificates with three separate keys.
   * EmailProtection also has the client-authentication purpose, so one certificate does both.
   * TimeStamping must stand alone. It is marked "critical".
   * OcspSigning has a shorter life (365 days, option -OcspDays). Time stamping lives 1825 days
     (option -TimestampDays).
   * Code signing has its own short subject (section 10).

 CHOOSE WHICH PURPOSES
 --------------------------------------------------------------------------------------------
 Leave some out of the set:
     -ExcludePurpose TimeStamping,OcspSigning
 Make ONE certificate with exactly the purposes you list:
     -Purpose ServerAuth,EmailProtection
 -Purpose is not a set. It cannot be used together with -ExcludePurpose or -AllPurposes.
 Special case: -Purpose ServerAuth,ClientAuth (nothing else) makes the three TLS certificates.

 EXTRA PURPOSES (not in the set; ask with -Purpose)
     DocumentSigning        Word, Excel, PowerPoint, Microsoft 365 documents
     DocumentSigningAdobe   Adobe Acrobat and Reader PDF
     1.3.6.1.4.1.99999.1.2  Your own purpose as a dotted number (a "custom EKU")
 A custom purpose is trusted by nothing until the program that uses it is told so.

====================================================================================================
 6  THE FILES YOU GET (FORMATS)
====================================================================================================
 -Format defaults to ALL. Every file is read back by OpenSSL after it is written.

 File                  What it is                                      Used by
 --------------------  ----------------------------------------------  ---------------------------
 <name>.crt            The certificate, PEM text                       nginx, Apache, most tools
 <name>.key            The PRIVATE key (PKCS#8 PEM)                    Servers. Keep it secret.
 <name>.pub            The public key (PEM)                            Developers
 <name>.pub.der        The public key (DER)                            Developers
 <name>-fullchain.crt  Leaf + intermediate + roots                     nginx ssl_certificate
 <name>-chain.crt      The chain without the leaf                      Apache, mutual TLS
 <name>.pem            The certificate, PEM text                       Linux tools, OpenSSL
 <name>.der            The certificate, binary                         Java, appliances
 <name>.cer            The certificate, binary                         Double-click in Windows
 <name>.cert           The certificate, PEM text                       Node.js, Go
 <name>.p7b            Leaf + chain, no key                            Windows and Java import
 <name>.rfc7468.pem    Strict PEM (64-character lines)                 Strict parsers
 <name>.pfx            Key + leaf + chain, with a password             IIS, Kestrel, Windows
 <name>-fips.pfx       The same, FIPS style (FIPS leaves only)         FIPS software
 <name>.cnf            The OpenSSL settings that made it               Audit
 convert-formats.ps1   Commands that convert THIS certificate         You
 tls-guidance.txt      TLS settings (ServerAuth, ClientAuth only)      Server admins
 leaf-info.json        What was issued                                 Audit

 Choose some formats only:   -Format PEM,DER      Make only a PFX:   -Format PFX
 PFX password: default Abc12345! (the lab password). Change it with -Password.
 Very old software: -LegacyPfx makes a 3DES / SHA-1 PFX.
 The PFX shows a friendly name in Windows, for example:
     Server Authentication for nextmantra.com Sign by : Agantra EV RSA-4096 G1 CA

====================================================================================================
 7  HASH FILES
====================================================================================================
 A hash is a short fingerprint of a file. If one byte changes, the hash changes. You use it to
 prove that a file was not damaged or changed on its way to the server.

 For every certificate the script writes two hash files next to it:

     <name>.sha256
     <name>.sha512

 Each line is "<hash>  <file>". It covers every certificate file of that name:
 .crt .pem .cert .cer .der .p7b .rfc7468.pem .pfx. The private key is not hashed.

 Check the files:
     Linux and macOS:   sha256sum -c <name>.sha256
     Windows:           Get-FileHash <file> -Algorithm SHA256

 Choose the algorithms:   -HashFile sha256,sha384
 Allowed: sha256 sha384 sha512 sha3-256 sha3-384 sha3-512. Turn it off:   -HashFile None

====================================================================================================
 8  WHERE THE FILES GO
====================================================================================================
 .\                                the project folder
   pki\                            the PKI. This script does NOT write here.
   leafcerts\                      all leaf certificates of this script
     leaf-index.json               everything made so far (-List shows it)
     www.example.com\              the set. Name = the first DNS name.
       leaf-set.json
       serverauth\                 certificate files of that purpose
       clientauth\
       serverauth-clientauth\
       codesigning\
       emailprotection\
       timestamping\
       ocspsigning\
     www.example.com_20261017-130512\    the same command again: a NEW folder, date and time

 * A single certificate (-Purpose) goes to leafcerts\<name>\ with no purpose folders.
 * Nothing is overwritten. A set is all or nothing: if one certificate fails, the new folder is
   removed.
 * -OutputRoot <path> changes leafcerts. A short name is relative to the project folder.
 * pki_setup.ps1 never deletes leafcerts. Old leaves of a replaced PKI stay until you delete
   them. They do not verify against the new CAs.
 * Windows only: -InstallPfx also imports the leaf PFX files into LocalMachine\My (needs an
   administrator window).

 FILE NAMES come from [ leaf_names ] in agantra_pki.cnf. Example of a real name:
     leafcerts\www.example.com\serverauth\www.example.com-server-ev-q1-rsa2048.crt
 The name has: the host, the purpose, the level (ev), the quadrant (q1) and the key (rsa2048).

====================================================================================================
 9  LEVEL AND QUADRANT
====================================================================================================
 LEVEL (which intermediate CA signs):
     -DV   Domain validated. The subject has the CN only.
     -OV   Organization validated. Adds company and address.
     -EV   Extended validation. Adds business fields. This is the default.
 EV leaves live 397 days at most. OV 3 years. DV 5 years. Change it with -Days.

 QUADRANT (which family of CAs signs):

     Switch                 Number   Key       Use
     ---------------------  -------  --------  -----------------------------------------
     (default) -Classic     1        RSA       Browsers, Windows servers, almost everything
     -Classic -FIPS         2        ECDSA     Systems that must follow FIPS
     -Quantum               3        ML-DSA    OpenSSL 3.5+ services, mutual TLS
     -Quantum -FIPS         4        ML-DSA    The same, with FIPS

 In file names a Quantum FIPS leaf shows q2 (Q1 = no FIPS, Q2 = FIPS in both tracks).
 If the PKI has no such quadrant (built with -ClassicPKI or -Quadrant) the script stops and
 tells you how to build it.
 Choose Classic for browsers, Windows Schannel, IIS, Kestrel and Java. Quantum is for services
 that you control on both sides.

 WHICH PKI: -Pki <name> uses <name>_pki.cnf. -Release <n> uses release n (default: the latest).
 -NoCaRevocationInfo uses the NoCR family (CAs without CRL / OCSP URLs).

====================================================================================================
 10  SUBJECT AND NAMES
====================================================================================================
 NAMES (what the certificate is valid for):
     -DnsName a.example.com,b.example.com    -IpAddress 10.0.0.5    -EmailAddress me@example.com
 The first DNS name is the CN and the name of the folder. Wildcards (*.example.com) work in this
 private PKI. With no names, the list [ leaf_san ] in agantra_pki.cnf is used.
 -CommonName <text> replaces the CN of the TLS certificates.
 ServerAuth and ClientAuth need at least one DNS name or IP address.
 EmailProtection needs an e-mail address (default: the contact e-mail of the config).

 SUBJECT FIELDS by level:
     DV   CN only.
     OV   CN, O, OU, L, ST, C, street, postal code and contact fields.
     EV   OV plus serialNumber, businessCategory and jurisdiction fields.
 Options: -Organization -OrganizationalUnit -Country -State -Locality -Street -PostalCode
          -Serial -BusinessCategory -JurisdictionCountry -JurisdictionState
          -JurisdictionLocality -Duns -ContactName -ContactEmail -ContactPhone
 Defaults come from [ subject_ov ] and [ subject_ev ] in agantra_pki.cnf.

 CODE SIGNING SUBJECT. Always short, at every level:
     C = EE   ST = Tallinn   L = Tallinn   O = <company>   CN = <company>
 Set the company with -CodeSigningCompany "Example Ltd". Empty = your organization.
 The company name may be 64 characters at most.

 TIME STAMPING AND OCSP. No SAN. The CN is "<company> Time Stamping" or "<company> OCSP Responder".
 The time stamping leaf is the time stamp server certificate. Options: -TimestampQuadrant 1|2|3|4,
 -TimestampPolicyOid, -TimestampDays, -OcspDays.

====================================================================================================
 11  KEYS, HASHES AND VALIDITY
====================================================================================================
 The script REFUSES weak values. It does not silently fix them.

 Option        Allowed                         Default
 ------------  ------------------------------  ---------------------------------------------
 -KeyType      RSA, ECDSA, MLDSA               Q1 RSA, Q2 ECDSA, Q3 and Q4 MLDSA
 -KeyBits      2048, 3072, 4096, 8192          2048
 -Curve        P-256, P-384, P-521             P-256
 -PqcAlgorithm mldsa44, mldsa65, mldsa87       mldsa65
 -Hash         sha256, sha384, sha512          the issuer's hash
 -Days         any number, up to the issuer    EV 397, OV 3 years, DV 5 years

 Rejected: RSA below 2048, curves below P-256, SHA-1, SHA-224, MD5.
 Code signing is raised on its own: RSA 4096, ECDSA P-384, ML-DSA 65, SHA-256 or stronger.

 POLICIES. Every leaf carries the level policy (DV 2.23.140.1.2.1, OV 2.23.140.1.2.2, EV
 2.23.140.1.1) and the company policies. Every OV leaf also carries the High Assurance policy.
 Add more with -Policy "OID" or -Policy "OID|https://cps.example.com". The CPS pointer is set
 with -CpsUrl (DV, OV) and -CpsUrlEv (EV).

====================================================================================================
 12  REVOCATION SWITCHES (NO CRL, NO OCSP)
====================================================================================================
 Normal leaves point to the CRL and the OCSP server. Offline or development systems may say
 "cannot connect to the revocation server". Then switch the pointers off:

     -NoCrl              no CRL distribution point
     -NoOcsp             no OCSP URL
     -NoRevocationInfo   both

 The "CA issuer" URL stays. Such a certificate cannot be checked or revoked by CRL or OCSP.
 leaf-info.json records what was left out. With these switches the NoCR PKI signs the leaf. If you
 have no NoCR PKI the script stops. Build one with:
     .\pki_setup.ps1 -NoCaRevocationInfo -InstallTrust

====================================================================================================
 13  DEVELOPMENT SAN
====================================================================================================
 -AddDevelopmentSAN adds a long list of development names to the SAN. FOR DEVELOPMENT ONLY.

 Your names stay first. The list is added after them. Duplicates are removed.
     DNS     21 names: nextmantra.com, *.nextmantra.com, localhost, local.dev,
             *.nextmantra.internal, *.agantra.api, and so on
     IP      603 addresses: 127.0.0.1, ::1, 10.10.2.2 and the four private ranges
     E-MAIL  four addresses of the company
 Where it goes: ServerAuth, ClientAuth and ServerClientAuth get everything. EmailProtection gets
 the e-mail addresses only. Code signing, time stamping and OCSP get nothing.

 With -EV the SAN rules of EV (no wildcard, no IP, no internal name) are NOT applied. Use this to
 test EV-looking certificates. A public CA would never issue them. A warning is printed and
 leaf-info.json says developmentSan = true.
 The e-mail certificate then uses ECDSA P-384 / SHA-512 by default.
 Change the list in [ development_san ] of agantra_pki.cnf. A range may have 1024 addresses at
 most. The big SAN makes each TLS certificate about 6 KB larger.

====================================================================================================
 14  RECIPES, COPY AND PASTE
====================================================================================================
 The whole set for a public web site
     .\GenerateLeafCertificate.ps1 -EV -DnsName www.example.com,example.com

 Internal service, DV, FIPS, ECDSA P-384, only the TLS certificates
     .\GenerateLeafCertificate.ps1 -DV -Classic -FIPS -KeyType ECDSA -Curve P-384 `
         -DnsName api.int.example `
         -ExcludePurpose CodeSigning,EmailProtection,TimeStamping,OcspSigning

 Mutual TLS between OpenSSL services (ML-DSA)
     .\GenerateLeafCertificate.ps1 -OV -Quantum -DnsName svc.int.example `
         -ExcludePurpose EmailProtection

 One certificate that is both server and client, only a PFX
     .\GenerateLeafCertificate.ps1 -OV -DnsName shop.example.com `
         -Purpose ServerClientAuth -Format PFX

 A code signing certificate only
     .\GenerateLeafCertificate.ps1 -OV -Purpose CodeSigning -CodeSigningCompany "Example Ltd"

 An e-mail certificate for a person
     .\GenerateLeafCertificate.ps1 -DV -Purpose EmailProtection -EmailAddress user@example.com

 Office or PDF document signing
     .\GenerateLeafCertificate.ps1 -OV -Purpose DocumentSigning,DocumentSigningAdobe -Format PFX

 A time stamping and an OCSP certificate
     .\GenerateLeafCertificate.ps1 -OV `
         -ExcludePurpose ServerAuth,ClientAuth,ServerClientAuth,CodeSigning,EmailProtection

 Short life, 90 days
     .\GenerateLeafCertificate.ps1 -OV -DnsName shop.example.com -Days 90

 Development with all development names
     .\GenerateLeafCertificate.ps1 -EV -DnsName api.nextmantra.com -AddDevelopmentSAN

 Offline test system without CRL and OCSP
     .\GenerateLeafCertificate.ps1 -OV -DnsName lab.example.com -NoRevocationInfo

 Only SHA-256 hash files
     .\GenerateLeafCertificate.ps1 -OV -DnsName shop.example.com -HashFile sha256

 Show what was made / show the names in the SAN
     .\GenerateLeafCertificate.ps1 -List
     openssl x509 -in <name>.crt -noout -ext subjectAltName

====================================================================================================
 15  PROBLEMS AND ANSWERS
====================================================================================================
 Message                                         Cause and fix
 ----------------------------------------------  ----------------------------------------------
 "OpenSSL 4.0 or newer ... not found"            You have 3.x. Run Install-DevEnvironment.ps1.
 "This leaf certificate needs FIPS / ML-DSA"     OpenSSL has no FIPS module or ML-DSA. Same fix.
 "This PKI has no Quadrant N"                    The PKI was built without it. Use another one.
 "RSA key size ... is rejected"                  Below the floor (section 11). Use a larger key.
 "Hash ... is rejected"                          Use sha256, sha384 or sha512.
 "-Purpose makes ONE certificate ..."            Do not combine -Purpose with -ExcludePurpose.
 "TimeStamping must be the ONLY purpose"         Time stamping and OCSP stand alone.
 "-ExcludePurpose removed every purpose"         Leave at least one purpose.
 "ServerAuth needs at least one DNS name or IP"  Add -DnsName or -IpAddress.
 "EmailProtection needs ... e-mail address"      Add -EmailAddress.
 "Invalid leaf naming"                           A template in [ leaf_names ] is wrong.
 The folder already exists                       Not an error. A NEW folder with the time was made.
 Old leaf does not verify                        pki_setup -Clean made new CA keys. Make a new leaf.
 Files are read-only, blocked or busy            .\GenerateLeafCertificate.ps1 -Unblock
 Leaves are in pki\leafcerts                     Version 4.6 wrote there. Copy them to leafcerts.
 "Invalid IP range" / "more than 1024"           A range in [ development_san ] is first-last,
                                                 IPv4, 1024 addresses at most.
 "Invalid DNS name in the development SAN"       A DNS.n entry is not a host name.
 NoCR PKI not found                              Build it: pki_setup.ps1 -NoCaRevocationInfo
 Browser says the site is not trusted            The root is not installed on that device.
                                                 See pki_setup-MANUAL.txt, section 7.

====================================================================================================
 16  LIMITS YOU MUST KNOW
====================================================================================================
 * ML-DSA certificates (-Quantum) are not accepted today by Windows Schannel (IIS, Kestrel on
   Windows), Java 25 and the browsers for HTTPS. Use Classic leaves there.
 * This is a private PKI. A public CA refuses wildcard and internal names. EV leaves here follow
   the policy and the subject fields. They do not show a browser EV badge.
 * -Duns writes organizationIdentifier = DUNS+<number>. That is a private convention.
 * Mixing purposes in one certificate is allowed (except time stamping and OCSP). A warning
   advises separate certificates when code signing is combined with TLS or S/MIME.
 * The OCSP certificate is for YOUR OCSP responder software. This PKI does not run one.
 * A leaf made from a DevKit copy is not in the CRL / OCSP database of the master PKI.
 * The private key and the PFX password are in plain files. Protect the folder. Never e-mail
   a .key file.
 * Wildcards match one level: *.example.com matches app.example.com, not a.b.example.com and not
   example.com itself.
 * Files are UTF-8 without BOM with LF endings, except convert-formats.ps1 (BOM, CRLF).

   * Classic, FIPS and Quantum leaves; DV, OV, EV; -Purpose and -ExcludePurpose; the checks that
