====================================================================================================
 1  WHAT THE DEVKIT IS
====================================================================================================
 Your developers need two things on their computer:
   1. Trust in your private PKI, so that a test site shows no warning.
   2. A way to make their own test certificates.

 The DevKit gives both in ONE zip file:

     PkiTransport.ps1 -DevKit        (you, on the computer that holds the pki folder)
            |
            v
     agantra-pki-devkit-<date>.zip   (you send it; you send the password by another way)
            |
            +--  Windows:  .\Install-PkiTrust.ps1      then   .\GenerateLeafCertificate.ps1 ...
            `--  Linux:    ./Install-PkiTrust.sh       then   ./GenerateLeafCertificate.sh ...

 Every PowerShell script has a bash twin, so the same kit works on Windows, Linux, WSL and in
 containers.

====================================================================================================
 2  THE WORDS YOU NEED
====================================================================================================
 Kit            The folder or zip that you built. Its name is agantra-pki-devkit-<date>.
 .certpacked    The encrypted file inside the kit. It holds the PKI. It has a password.
 Trust          Put the root CA into the computer, so programs accept your certificates.
 Issuing CA     An intermediate CA that signs the certificates of the developers.
 Leaf           A certificate for a server, a person or a program.
 CSR            A request for a certificate. A colleague makes it and you sign it.
 Serial number  The number of a certificate. Two certificates of one CA must never share it.
 Full list      GLOSSARY.txt and GLOSSARY-ENGLISH.txt.

 3  BEFORE YOU START
====================================================================================================
 OWNER
   1. The PKI exists (pki_setup.ps1 was run, folder .\pki).
   2. PowerShell 7 and OpenSSL 4 on your computer.
   3. A way to send a file, and a second way to send a password.

 DEVELOPER
   1. The zip and the password. The password comes from the owner by another way.
   2. Windows 11 24H2 or newer, Windows Server 2025 or 2022: PowerShell 7 and administrator
      rights (the roots go into the machine store).
      Linux: Ubuntu 24+, CentOS Stream 10+, RHEL 10+, Rocky 10+, Oracle Linux 10+, SUSE 15+,
      openSUSE. bash, openssl 3.0+ and python3. sudo is used only for the system store.
   3. Windows 10 and macOS are refused (exit code 5).

====================================================================================================
 4  OWNER: MAKE THE KIT
====================================================================================================
 Run on the computer that holds the pki folder:

     .\PkiTransport.ps1 -DevKit -GeneratePassword

 The script writes .\transport\agantra-pki-devkit-<yyyyMMdd-HHmmss>.zip and shows the password
 ONCE. Write it down.

 Other ways:
     .\PkiTransport.ps1 -DevKit -Out D:\share\devkit.zip -PackagePassword 'a strong password 12+'
     .\PkiTransport.ps1 -DevKit -KitArchiveFormat 7z -ArchiveFormat 7z -Out D:\share\devkit.7z
     .\PkiTransport.ps1 -DevKit -DevKitNoKeys        CA certificates only. Developers can trust
                                                     the PKI but cannot issue.

 ONE kit holds ONE PKI: the latest release. Choose another with -Release N, -NoCaRevocationInfo or
 -PkiRoot. Make one kit for each release.
 The kit is built from the CURRENT configuration (agantra_pki.cnf and the pki folder): policies,
 CPS addresses, company numbers, CRL and OCSP addresses, subject defaults and the development SAN
 go into devkit.env. Build the kit again when any of them changes.
 The password can also come from the variable PKI_TRANSPORT_PASSWORD.

====================================================================================================
 6  WHAT IS NOT INSIDE, AND THE KEYS
====================================================================================================
 The .certpacked holds the private keys of the ISSUING (intermediate) CAs ONLY: the six DV, OV and
 EV CAs of quadrants 1 and 2. They sign the leaf certificates.

 NEVER inside:
   * The keys of the Enterprise Root, the Track Roots and the Quadrant Roots.
     A stolen root key lets a thief build a new hierarchy under your trust.
   * The keys of the OCSP responder and the time stamp server, old leaf keys, any .pfx or .p12.

 certpack.json says so:  "scope": { "caPrivateKeys": true, "issuingKeysOnly": true }
 -DevKitNoKeys leaves out every key.

 WHAT THIS MEANS. A developer with the kit can make certificates that your clients trust, until you
 revoke the intermediate CA. So:
   * Send the kit to named people only.
   * Use a long password. Send it by another way.
   * Delete kits you do not need.
   * Keep a list of who got which kit (the file name has the date).
   * If a kit is lost: revoke the intermediate (PkiRevocation.ps1) and build a new kit.
 The alternative is a signing service on the PKI server that takes requests. Then no key leaves the
 server. See PKI-Server-Design.txt.

====================================================================================================
 7  SEND THE KIT
====================================================================================================
 1. Send the zip (mail, share, Teams). The zip is not encrypted. The .certpacked inside is.
 2. Send the password by ANOTHER way: phone, password manager, another chat.
 3. Send the SHA-256 of the zip (shown at the end of the build). The developer compares it:
        Windows:   Get-FileHash .\file.zip
        Linux:     sha256sum file.zip
 4. Write down who received it.

 8  DEVELOPER: WINDOWS, STEP BY STEP
====================================================================================================
 Step 1   Unzip (right-click, Extract All) to a short path, for example C:\pki-devkit.
          Do not unzip into OneDrive or Downloads.
 Step 2   If Windows blocks the scripts:   Unblock-File .\*.ps1
 Step 3   No OpenSSL 4 yet? Once, as administrator:
              .\Install-DevEnvironment.ps1 -Only OpenSSL,7Zip
          Then open a NEW PowerShell.
 Step 4   Start PowerShell 7 AS ADMINISTRATOR:
              cd C:\pki-devkit
              .\Install-PkiTrust.ps1
          It asks for the password and then:
            * checks the computer (Windows 11 24H2+ or Server, OpenSSL 4.0.1+),
            * checks the SHA-256 of every file and unpacks to this folder,
            * puts the roots in Local Machine > Trusted Root Certification Authorities,
            * puts the intermediates in Local Machine > Intermediate Certification Authorities,
            * proves the chains with OpenSSL,
            * gives every issuing CA a NEW RANDOM serial counter (section 13).
          -InstallMissing installs OpenSSL and 7-Zip for you.
 Step 5   From now on a normal PowerShell is enough:
              .\GenerateLeafCertificate.ps1 -OV -DnsName www.example.com
 Step 6   Read section 10 for people, Office and the other scripts.

 Install-PkiTrust.ps1 again later? It installs the trust again and leaves pki\ and leafcerts\
 alone. -Reset unpacks pki\ anew (new serials; leafcerts is kept).
 Remove the trust:   .\PkiTransport.ps1 -RemoveTrust -Package .\<name>.certpacked

====================================================================================================
 9  DEVELOPER: LINUX, STEP BY STEP
====================================================================================================
 Step 1   Unpack:
              unzip agantra-pki-devkit-*.zip && cd agantra-pki-devkit-*
 Step 2   Make the scripts executable (once):
              bash make-executable.sh
          A zip made on Windows loses the executable bit and may carry Windows line endings. This
          puts them right. You can also start any script with  bash ./name.sh  without the bit.
 Step 3   Install the PKI:
              ./Install-PkiTrust.sh
          It asks for the password. It uses sudo only for the system store and for missing
          packages. --yes answers yes. --password-file FILE reads the password from a file.
 Step 4   Make certificates:
              ./GenerateLeafCertificate.sh --ov --dns www.example.com
 Step 5   Read section 10 for people, Office and the other scripts.

 You need bash, openssl 3.0+ (4.0.1+ is better), python3 (for the JSON files and the request
 check) and sudo (for the store).
 Need OpenSSL 4?  ./Install-DevEnvironment.sh --yes --only openssl     (section 12)
 Remove the trust: remove the agantra-pki-* files in /usr/local/share/ca-certificates and run
 update-ca-certificates --fresh.

====================================================================================================
 11  SIGN THE REQUEST (CSR) OF A COLLEAGUE
====================================================================================================
 A colleague or another department makes THEIR OWN key and a request (.csr). They send you only
 the request. You sign it with the kit and send back the folder. They keep their key.

     Windows:  .\SignCsr.ps1 -Csr .\web01.csr                  Linux:  ./SignCsr.sh --csr web01.csr
               .\SignCsr.ps1 -Csr .\web01.csr -OV -Purpose ServerClientAuth
               .\SignCsr.ps1 -Csr .\web01.csr -EV -FIPS -Check         (report only)

 * The request is checked against the rules of the PKI first. Red ERROR = nothing is signed (exit
   code 2). Yellow WARN = signed; read it. Each line says the field, the reason and the fix.
 * Level: -DV, -OV, -EV. Without one, the level follows the request. Track: Classic (default) or
   -Quantum. -FIPS selects the FIPS quadrant.
 * The kit signs with its intermediate keys only. It can NEVER sign a root or a CA certificate. A
   request for a CA goes to the owner of the original PKI (SignExternalCa.ps1).
 * The result is in csr-signed\<name>_<date-time>\ : the certificate (.crt .cer), -fullchain.crt,
   -chain.crt, .p7b, root.crt, our-ca-bundle.crt and README.txt for your colleague. Never a key.
 * The rules and codes are in SignCsr-MANUAL.txt. SignCsr.sh also needs python3.

====================================================================================================
 12  INSTALL OPENSSL 4 ON THE MACHINE
====================================================================================================
 Install-DevEnvironment.ps1 and .sh need nothing else from the kit. They install OpenSSL 4.0.3 or
 newer (4.0.1 is the minimum) with the FIPS module and ML-DSA, check it, and put it on the PATH.

     Windows (PowerShell 7, administrator):  .\Install-DevEnvironment.ps1 -Only OpenSSL,7Zip
         Installs FireDaemon.OpenSSL with winget, writes fipsmodule.cnf, sets OPENSSL_MODULES and
         OPENSSL_CONF, and adds the bin folder to the machine PATH. Open a NEW PowerShell.

     Linux:    ./Install-DevEnvironment.sh --yes --only openssl
         By default it uses the OpenSSL of the system (enough for the .sh scripts). Nothing is
           built.
         --openssl-source ppa     OpenSSL 4 from the PPA of the owner
         --openssl-source build   a full build of OpenSSL 4 from the official release (the hash is
                                  checked; it takes a long time)
         --check                  only check (exit 0 = ready, 4 = not ready)
         --dry-run                show what would change
         --no-path                leave the PATH alone
         Open a NEW terminal after the install.

 More: Install-DevEnvironment-MANUAL.txt. Install-PkiTrust -InstallMissing (Windows) and
 Install-PkiTrust.sh --install-openssl use the same code.

====================================================================================================
 13  SERIAL NUMBERS, REVOCATION, COPIES
====================================================================================================
 SERIAL NUMBERS. Two copies of one PKI that count from the same number would issue the SAME serial
 numbers. Two different certificates with one serial under one CA break CRL and OCSP. So:
   * Install-PkiTrust writes a new random 128-bit value into the 'serial' file of every issuing CA
     of THIS copy. pki\.devkit-instance.json records the copy.
   * The shell scripts use a random serial for every certificate.
   * The master PKI keeps its own counter. A clash of two random 128-bit numbers will not happen.

 REVOCATION. A certificate made from a kit copy is NOT in the index.txt of the master PKI. So the
 master CRL does not list it, and the master OCSP answers "unknown". Nobody can revoke it centrally.
 These are DEVELOPMENT certificates. Do not use them in production.
 The log of what a developer made: leafcerts\leaf-index.json (PowerShell) and
 leafcerts/issued-by-devkit.tsv (shell). To bring them under the master, give the folder to the
 owner, who can merge the entries with PkiRevocation.ps1. This is not automatic.

 PATHS. The CA configuration files hold absolute paths. Install-PkiTrust rewrites them to the kit
 folder. So the kit works anywhere and never touches the database of the computer that built it. Do
 not move the folder after the install. If you must, run Install-PkiTrust again with -Reset
   (--reset)
 in the new place.

 ONE KIT = ONE MOMENT. After the owner rebuilds the PKI (pki_setup -Clean) every older kit is
 obsolete.

====================================================================================================
 14  SHELL SCRIPTS AND POWERSHELL SCRIPTS
====================================================================================================
 The .sh generators make the same certificates as the PowerShell generators. The extensions were
 compared one by one with openssl x509 -text: subject by level, SAN, key usage and purposes,
 policies (level, company, High Assurance for OV), CPS pointers, CRL addresses, OCSP and CA issuer
 addresses, the digest of the issuer, ECDSA P-384 + SHA-512 for e-mail certificates with the
 development SAN, RSA 4096 for Office and code signing, EV at 397 days at most.

 What the .sh generators do NOT have:
   * The Quantum quadrants 3 and 4 (ML-DSA). Use the PowerShell generator. SignCsr.sh does sign
     Quantum requests, because the key belongs to the department.
   * The formats .cer .der .p7b .rfc7468.pem and convert-formats.ps1. They write .crt .key .pub .pfx
     -chain.crt -fullchain.crt leaf-info.json and the hash files. Convert with openssl.
   * -Format, -Policy and a password for each call. Only --pfx-password.
   * tls-guidance.txt, and leaf-index.json (they append to leafcerts/issued-by-devkit.tsv).
 The default level of the .sh generators is OV. The PowerShell generators default to EV.

====================================================================================================
 16  LIMITS YOU MUST KNOW
====================================================================================================
 * The zip is not encrypted as a whole. Only the .certpacked is. Do not put secrets next to it.
 * A zip made on Windows has no Unix permissions. That is why make-executable exists. A zip made on
   Linux keeps the executable bit.
 * One kit = one PKI at one moment (section 13).
 * A kit with keys makes every holder an operator of the issuing CAs (section 6).
 * Certificates from a kit are development certificates (section 13).
 * The kit holds the version of the scripts it was built with. Build a new kit to update.

 18  WHAT WAS TESTED, WHAT WAS NOT
====================================================================================================
 Tested (Linux, OpenSSL 4.0.3, PowerShell 7, a fresh PKI):
   * Build a kit, unzip it, bash make-executable.sh, ./Install-PkiTrust.sh --yes: the roots are in
     the system store and every chain verifies; six issuing CAs got new serial counters.
   * ./GenerateLeafCertificate.sh from the unpacked kit: seven certificates, hash files check OK.
   * The help of every script runs; the manual and the helps fit 100 columns.
 NOT tested:
   * Install-PkiTrust.ps1 and the Windows certificate stores, Make-ShExecutable.ps1 through WSL.
   * Windows PowerShell scripts of the kit on Windows (they parse, they were not run there).
   * RHEL, Rocky, SUSE and macOS.
   * -KitArchiveFormat 7z and the PPA and build sources of Install-DevEnvironment.sh.
   * Firefox and other browsers with the installed roots.
