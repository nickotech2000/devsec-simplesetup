====================================================================================================
 1  GOALS AND TARGETS
====================================================================================================
 * One private PKI with two tracks, CLASSIC and QUANTUM, and four quadrants:
        quadrant   1 Classic non-FIPS | 2 Classic FIPS | 3 Quantum non-FIPS | 4 Quantum FIPS       (internal numbers)
        NAMED      Classic Q1         | Classic Q2     | Quantum Q1         | Quantum Q2           (Q1 = non-FIPS, Q2 = FIPS, both tracks)
   Each quadrant has three policy-isolated intermediates: DV, OV, EV.
 * CLASSIC  quadrants use RSA (Q1) and ECDSA (Q2).
   QUANTUM  quadrants use the post-quantum signature ML-DSA at EVERY level: Track Root, Quantum Q1 / Q2 roots,
   intermediates and leaves, FIPS and non-FIPS. Only the Enterprise Root, which anchors both tracks,
   is RSA. Servers that support it also negotiate the hybrid key exchange X25519MLKEM768 (ML-KEM).
 * Generation: PowerShell 7+ and OpenSSL 4.x. Older OpenSSL stops the script. ENGINE API gone;
   native providers only:  non-FIPS = -provider default   FIPS = -provider fips -provider base.
   ML-DSA is native in OpenSSL 3.5 / 4.x (genpkey -algorithm mldsa87).
 * Windows: Windows 11 Home / Pro (24H2 or newer, updated) and Windows Server 2025 store and
   validate ML-DSA certificates. Windows 10 and Server 2022 cannot: the Quantum quadrants are
   skipped there.
 * Other targets: Ubuntu 26, CentOS Stream 10, Rocky 10, RHEL 9, Oracle Linux 10, SUSE 16, FreeBSD
   (VM), macOS on Mac mini M2 and M4. Browsers: Chrome, Edge, Brave, Firefox, UC Browser, QQ
   Browser. Runtimes: Kestrel on .NET 10 LTS / 11, nginx, Apache httpd, Node.js 26, Python 3.14, Go,
   PHP 8, Java 25, Rust, IIS (legacy).
 * Reference machines (your screenshots, section 7.3): an Ubuntu 26.04.1 LTS development server and
   a Windows 11 26H2 Pro development VM with Visual Studio 2026 and Visual Studio Code.
 * Private PKI: every client installs the Enterprise Root. No browser shows the EV company line.
 * Variants of the PKI: the full PKI (four quadrants), -ClassicPKI (Enterprise Root, Classic Track
   Root, Q1 Root, DV / OV / EV intermediates only), and an Enterprise Root signed by a public CA
   (DigiCert, GlobalSign, Sectigo) instead of self-signed (section 6, diagram 5;
   PUBLIC-CA-ENTERPRISE-ROOT.txt).
 * Names of all roots and intermediates are configurable (section 4).
 * IMPORTANT: ML-DSA certificates are not accepted for HTTPS by Windows Schannel (Kestrel / IIS on
   Windows), Java 25 or the browsers today (section 7). Quantum leaves are for OpenSSL-based
   services and mutual TLS; browser-facing sites use the Classic leaves.

 3  RULES BY LEVEL
====================================================================================================

 3.1  ROOT KEY POLICY  (enforced in code, not configurable)
      Every root-level CA (Enterprise Root, both Track Roots, all four Quadrant Roots) is RSA 8192
      with SHA-512. Where the algorithm is not RSA, the strongest key and the largest digest it
      offers are used:

        Algorithm   Root key                  Digest    Used for
        ----------  ------------------------  --------  ------------------------------------------
        RSA         8192 bit                  SHA-512   Enterprise Root, Classic Track Root
        RSA         4096 bit (4.9.4)          SHA-384   Q1 root (Classic non-FIPS; -QuadrantRsaBits
                                                        4096|8192)
        ECDSA       P-384 (4.9.4)             SHA-384   Q2 root (Classic FIPS; -QuadrantCurve
                                                        P-384|P-521)
        ECDSA       P-521 (secp521r1)         SHA-512   Enterprise/Track roots when not RSA (none
                                                        today)
        ML-DSA      ML-DSA-87 (NIST level 5)  none      Quantum Track Root, Quantum Q1 root, Quantum
                                                        Q2 root

      * Why 8192: it is also the largest RSA size Chrome (BoringSSL) accepts. 16384 would fail.
      * Why P-521: largest NIST curve; roots only sign CA certificates and never take part in a TLS
        handshake, so TLS limits of some stacks on P-521 do not apply (L12).
      * ML-DSA is a pure signature scheme: it hashes internally (SHAKE256) and takes no SHA-512, so
        the digest column reads "none". ML-DSA-87 is the highest parameter set. "ML-DSA-874" in the
        first draft does not exist; ML-DSA has the sets 44, 65 and 87.
      * The validator rejects a root-level CA that breaks this table, and checks that every
        certificate below an ML-DSA CA is ML-DSA signed (and no classical CA signs one by mistake).
      * Not used: Ed448 (poor Windows chain support), RSA above 8192 (Chrome rejects it), SLH-DSA
        (30 KB signatures, little client support).

 3.2  BELOW THE ROOTS  (configurable)
        Level                  Key                        Digest       Parameter
        ---------------------  -------------------------  -----------  ---------------------------
        Q1 intermediates       RSA 4096 (or 8192)         SHA-256      -IntermediateRsaBits
        Q2 intermediates       ECDSA P-384 (or P-256/521) SHA-384      -IntermediateCurve
        Quantum intermediates  ML-DSA-87 (or 65 / 44)     none         -PqcAlgorithm
        Leaf Q1                RSA 2048                   SHA-256      -LeafSizes
        Leaf Q2                ECDSA P-256                SHA-384      -
        Leaf Quantum           ML-DSA-65 (or 44 / 87)     none         -PqcLeafAlgorithm
      Leaf floors (Phase B): RSA below 2048, ECC below P-256 and hash below SHA-256 rejected.
      Code signing: key 4096 or larger and SHA-256 or larger, enforced even if the parameters say
                    less.
      No silent downgrade: if OpenSSL cannot create an ML-DSA key the script STOPS. Only
      -PqcFallback (RSA, size -FallbackRsaBits, default 8192, via genrsa) lets a build continue;
      each such key is warned about, marked * in the summary and listed in pki-manifest.json. Not
      quantum-safe.

 3.3  VALIDITY  (from the moment of generation; each level shorter than the one above)
        Enterprise Root     1000 years     -RootYears        (expires 3026)
        Track Root           500 years     -TrackYears
        Quadrant Root        400 years     -QuadrantYears
        Intermediates        250 years     -IntYears
        Leaf EV              397 days      -LeafDays         (EV maximum 397: every EV certificate,
                                                             10.74)
        Leaf OV                3 years     -OvLeafYears      (default when not given)
        Leaf DV                5 years     -DvLeafYears      (default when not given)
      pki_setup.ps1 issues EV leaves (397 days). The OV and DV defaults are stored in
      agantra_pki.cnf and used by the leaf generator (Phase B). The run prints every CA with its
      validity and expiry date.

 3.4  DIGEST BY ISSUER
        Enterprise Root and Classic Track Root sign with SHA-512.
        Quadrant Roots sign intermediates with SHA-256 (RSA), SHA-384 (ECDSA) or no digest (ML-DSA).
        Intermediates sign leaves the same way.   The Enterprise Root signs the Quantum Track Root
        with SHA-512 (it is an RSA key); everything below the Quantum Track Root is signed by
        ML-DSA.

 3.5  LENGTH-EXTENSION SHIELD AND OTHER PROTECTION
      A length-extension attack targets H(secret || message) constructions (MACs). An X.509
      signature covers the whole DER TBSCertificate, so the attack does not apply. What the script
      enforces instead:
        * digest allow-list: SHA-1 and MD5 rejected; SHA-512 required for classical root-level CAs
        * critical basicConstraints with a fixed pathlen at every level (3, 2, 1, 0)
        * keyCertSign + cRLSign only on CAs
        * 128-bit random positive serial numbers; separate serial database per CA
        * private key files restricted to the owner, SYSTEM and Administrators (icacls)
        * optional -RsaPss (RSASSA-PSS, randomized padding, MGF1 over the same digest) for RSA CAs.
          Off by default because some older chain engines reject PSS.
        * post-generation validation of every CA and leaf (keys, digests, pathlen, policies, chains)

 4  NAMES  (configurable)
====================================================================================================
 Defaults:
 Enterprise Root     Agantra Root CA G1
 Track Root          Agantra Classic Root CA G1
                     Agantra PQC Root CA G2
 Quadrant Root       Agantra Classic Q1 Root CA G1          (Q2 likewise)
                     Agantra PQC Q1 Root CA G2  (Q2 likewise)
                     Q1 = non-FIPS, Q2 = FIPS, in BOTH tracks. The track word and the generation (G1
                     Classic, G2 Quantum) keep every name and file stem unique: agantra-q1-root-g1
                     (Classic) / agantra-q1-root-g2 (Quantum). The internal quadrant numbers 1..4
                     (-Quadrant, ids q1-ev .. q4-ev, folders) are NOT renamed. Leaf file names use
                     the same Q1 / Q2: www.example.com-ev-q2-mldsa65.crt is a Quantum FIPS leaf.
 Intermediate        Agantra <EV|OV|DV> <algorithm> <G1|G2> CA
                       Agantra EV RSA-4096 G1 CA
                       Agantra OV ECDSA-P384 FIPS G1 CA
                       Agantra DV ML-DSA-87 G2 CA
                       Agantra EV ML-DSA-87 FIPS G2 CA
 G1 = Classic track, G2 = everything in the Quantum track. The algorithm in an intermediate name is
 the key that really exists (after a -PqcFallback it reads RSA-8192, never ML-DSA). No year range.
 "PQC" is literally true for the Quantum track (ML-DSA).

 WHERE THE NAMES ARE DECIDED  (one module: scripts\01b_CaNaming.ps1)
   Defaults   scripts\01b_CaNaming.ps1            ($script:PkiNamingDefaults, documented in the file)
   Overrides  agantra_pki.cnf  [ ca_names ]        (Prefix, QuantumLabel, SlugPrefix, GenEnterprise, GenClassic,
                                                    GenQuantum and one template per kind of CA)
   Templates  EnterpriseRoot  ClassicTrackRoot  QuantumTrackRoot  ClassicQuadrantRoot  QuantumQuadrantRoot
              Intermediate        tokens: {Prefix} {QuantumLabel} {Gen} {N} {Level} {Algorithm}
                                  {Track} {Id}
   Rules      at most 64 characters (X.520), every CA a different name, only the tokens above,
              file-name stem only a-z 0-9 '-'. The script stops with the reason; -ShowNames previews
              everything.
   File stem  agantra-q1-ev-g1 style, used in the CRL / CA-issuer URLs ({ca}) and in pki\publish.
 Every CA subject also carries jurisdictionC, serialNumber, C, L, O, OU, name, emailAddress,
 telephoneNumber. O is written without the umlaut: Agantra Inovatif OU. OU per layer: OU_Root,
 OU_Track, OU_Quadrant, OU_Intermediate in [ pki_settings ].

 Policy OIDs                  EV 2.23.140.1.1     OV 2.23.140.1.2.2     DV 2.23.140.1.2.1  (CA/B Forum defaults)

                                     DV, no PEN, no custom policy. No extended key usage (Windows:
                                     all application policies).
   Quadrant Roots                    EV, OV and DV (+ the PEN policies and [ custom_policies ]).
   Intermediates                     only their own level (policy isolation) + the PEN policies of
                                     that level + custom policies.
   Leaves                            their level + the PEN policies of that level + custom policies
                                     + -Policy.
   The EV leaf carries EV.
 IANA Private Enterprise Number (PEN)   67096 (Agantra Inovatif OU): PEN in agantra_pki.cnf [
                                        iana_pen ]
   or -IanaPen <number>. When set, these OIDs are added (PenPolicyArc defaults to 1):
        1.3.6.1.4.1.<PEN>.1      company policy        Quadrant Roots, intermediates, leaves
        1.3.6.1.4.1.<PEN>.1.1    company EV level      Quadrant Roots, EV intermediates, EV leaves
        1.3.6.1.4.1.<PEN>.1.2    company OV level      Quadrant Roots, OV intermediates, OV leaves
        1.3.6.1.4.1.<PEN>.1.3    company DV level      Quadrant Roots, DV intermediates, DV leaves

   Your applications can therefore recognise a company EV certificate by its own OID.
 Extra policies   agantra_pki.cnf [ custom_policies ]:   label = OID | CPS-URL
   Written into every Quadrant Root, intermediate and leaf (NOT the Enterprise Root and Track
   Roots). Phase B adds a leaf parameter for more. A policy missing from the CA certificates is not
   asserted by the CA chain.
 CA extensions   basicConstraints critical CA:true pathlen:N | keyUsage critical keyCertSign,cRLSign
   subjectKeyIdentifier | authorityKeyIdentifier keyid:always | certificatePolicies |

 DIAGRAM 3 - TLS 1.3 HANDSHAKES  (classic and quantum quadrants)
 ---------------------------------------------------------------------------------------------------

  A. CLASSIC leaf (Q1 / Q2): works with every client
        CLIENT (browser, Windows 11, Go, Node, curl ...)               SERVER (any)
          |  ClientHello: groups = X25519MLKEM768, X25519 ...            |
          |------------------------------------------------------------->|
          |  server picks X25519MLKEM768 if it can, else X25519          |
          |<-------------------------------------------------------------|
          |  Certificate: RSA / ECDSA chain from this PKI                |
          key exchange: hybrid (quantum-safe)   authentication: RSA / ECDSA (classical)

  B. QUANTUM leaf (quadrants 3 / 4): both ends must support ML-DSA certificates
        CLIENT with OpenSSL 3.5+ (curl, Python, Node, nginx proxy ...)  SERVER with OpenSSL 3.5+
          |  ClientHello: groups = X25519MLKEM768 ... ; signature_algorithms include mldsa44/65/87
          |------------------------------------------------------------->|
          |  Certificate: ML-DSA leaf + ML-DSA chain from this PKI       |
          |<-------------------------------------------------------------|
          key exchange: hybrid ML-KEM  authentication: ML-DSA  =  fully post-quantum handshake

  C. Where B is not possible: Windows Schannel servers, Java 25, browsers and Windows 10 clients do
     not offer or accept ML-DSA certificates: the handshake fails. For such clients the site needs a
     Classic leaf (A). An OpenSSL server can hold both an RSA and an ML-DSA certificate and present
     the one the client supports (dual-certificate setup; possible with OpenSSL-based servers, test
     it first).

 9  LIMITATIONS
====================================================================================================
 L1   ML-DSA certificates are not usable for HTTPS on Windows Schannel (Kestrel / IIS on Windows),
      Java 25 or any listed browser (7.1). A Quantum leaf cannot be shown in Edge / Chrome / Brave /
      Firefox / UC / QQ. Browser-facing sites use Classic leaves; the Quantum quadrants serve
      OpenSSL-based services and mutual TLS between your own systems.
 L2   Mixed deployments need two certificates for one site (Classic + Quantum) or two sites. Phase B
      will not change that: it is how the client ecosystem works today.
 L3   ML-DSA signatures are big: about 3.3 KB (ML-DSA-65) and 4.6 KB (ML-DSA-87) each. A Quantum
      chain of leaf + intermediate + quadrant root + track root carries four of them: tens of KB.
      Servers, proxies and load balancers with small header or handshake limits can fail.
 L4   The Quantum FIPS quadrant (number 4, named Quantum Q2) needs a FIPS provider that contains
      ML-DSA (OpenSSL 3.5+ / 4). The FIPS provider is not by itself a compliance claim (L13).
 L5   Private PKI. Every client installs the Enterprise Root. Firefox, Chrome on Linux, Java, Node,
      Python, PHP and Android apps have their own stores or settings (manual, section 7).
 L6   UC Browser and QQ Browser are not verified and may ignore user-installed roots. Test first.
 L7   Validity beyond the year 2038 can fail on 32-bit time stacks (old 32-bit Android, embedded).
 L8   OpenSSL. This script needs 4.x, which no listed OS packages, and 4.0 is a short-support
      release (about May 2027; OpenSSL 3.5 LTS runs to April 2030). Servers can use 3.5. macOS
      /usr/bin/openssl is LibreSSL: use a Homebrew OpenSSL 4 with -OpenSslPath.
 L9   PowerShell 7 is required. FreeBSD is not an officially supported PowerShell platform: build
      the PKI elsewhere and install root.crt by hand. Certificate-store functions are Windows only;
      other systems use the commands in the manual. macOS and Linux have no ML-DSA-aware system
      store or browser; use the root in OpenSSL-based tools.
 L10  Windows 10, Windows 11 before 24H2 and Server 2022 cannot hold ML-DSA certificates. On them the
      Quantum quadrants are skipped by default and -InstallTrust fails for them if forced.
 L11  ML-DSA private keys in a PFX: Windows 11 24H2+ / Server 2025 should import them (CNG ML-DSA), but
      this is not documented well and untested by me. If Import-PfxCertificate and certutil both
      fail, the PFX stays on disk and a warning is printed.
 L12  P-521 is used for the Q2 CA signature. Windows, macOS, NSS and BoringSSL verify it, but some TLS
      stacks restrict P-521 in handshakes. Leaves are P-256 for that reason.
 L13  FIPS. The quadrants use the OpenSSL FIPS provider for key generation and signing. That is not a
      compliance statement: it holds only for a FIPS-validated module of the exact version and only
      for algorithms the module covers. The module must match the OpenSSL version.
 L14  Keys are plain PKCS#8 PEM files protected by file permissions. For production keep the roots
      offline or in an HSM. The PFX password defaults to Abc12345!: change it with -Password.
 L15  Revocation. CRL / OCSP / CA Issuers URLs help only after you publish pki\publish at those hosts.
      No OCSP responder is provided. An ML-DSA CRL can only be checked by a client that supports
      ML-DSA.
 L16  Leaf lifetime. EV 397 days (the maximum for every EV certificate since 4.9.5, 10.74), OV 3 years, DV 5 years by default. Chrome and Apple apply the 398-day
      limit to publicly trusted roots only (private roots are exempt), Windows and Firefox do not
      enforce it, but your own security policy or a customer's scanner may. Phase A issues EV
      leaves.
 L17  Phase A has only the default EV leaves. DV / OV leaves, formats (DER, P7B, ...), custom leaf
      policies, TLS / cipher guidance output, the transport zip and a new pki_reuse.ps1 are Phases
      B, C. pki_reuse.ps1 and GenerateLeafCertificate.ps1 still expect the old single-root layout.
 L18  Testing. Tested on Linux with PowerShell 7.4 and a real OpenSSL 4.0.3 (built from source with the FIPS
      provider): the full four-quadrant PKI with real ML-DSA, default and FIPS providers; -Check,
      -Verify, tamper detection, strict failure and -PqcFallback; a live TLS 1.3 handshake with the
      ML-DSA leaf (Peer signature type mldsa65, group X25519MLKEM768, Verification OK); -ClassicPKI;
      naming overrides and refusals; the public-CA flows (subordinate and cross-sign) against a
      stand-in CA; the three module sets. NOT tested by me: the Windows
      certificate store functions, any Windows machine, any browser, UC / QQ, macOS, FreeBSD, nginx
      / Apache / Kestrel / Node / Python as servers. Section 14 closes that gap on your machines.
 L18a PFX and FIPS. The FIPS provider has no PKCS#12 KDF, so the normal .pfx of a FIPS quadrant is
      packaged with the default provider (the key stays FIPS-generated); a FIPS-conformant -fips.pfx
      (PBMAC1) is written next to it for the FIPS leaves. Windows import of the -fips.pfx is
      untested.
 L19  Information in section 7 reflects public documentation of mid-2026 and your screenshots.
      Versions change: check nginx -V, process.versions.openssl, ssl.OPENSSL_VERSION, your Windows
                       build.
 L20  PHP 8.4.13 and Python builds on Windows may bundle an OpenSSL older than 3.5: no ML-DSA and no
      hybrid key exchange there. Java 25 never offers the hybrid group.
 L21  The IANA PEN (67096) is set; company OIDs appear in certificates made AFTER it was set. Existing CAs do not have them (rebuild), and a leaf then warns that its issuer lacks the policy.
 L22  Policy OIDs alone do not make a browser show an EV badge: that needs a public root in the browser's
      EV list. They let YOUR applications recognise the certificate type.

 L23  Public CA (PUBLIC-CA-ENTERPRISE-ROOT.txt). Tested with a stand-in CA, NOT with DigiCert, GlobalSign or
      Sectigo: I did not verify their products, prices or rules. A public CA may refuse RSA 8192 /
               P-521,
      allow pathlen below 3 only (then level 0 cannot be signed), require an HSM, impose name
      constraints and cap validity. Signing is manual (files); no portal / ACME / REST.
 L24  Under a public root, public TLS rules apply to every leaf (398 days, no private names the CA does not
      allow); the 1000 / 500 / 400 / 250 year CAs are shortened to the public certificate's end
      date; the ML-DSA quadrants are useless for browsers. Use -ClassicPKI with it.
 L25  Renewal of a public-CA-signed Enterprise Root is manual: everything below ends with it, so plan the
      re-signing of the same key and the re-issue of the CAs below early.
 L26  Only level 0 (Enterprise Root) is signed by the public CA. Signing a lower level (Q1 Root or an
      intermediate) is possible in principle but not automated (document, section 5).
 L27  CA names are fixed when a CA is issued: changing a template later needs -Clean (a new PKI).
 L28  Track and Quadrant Roots in the Trusted Root store are trust anchors although they are not self-signed
      (owner decision, 10.17). Consequences: trust in a Quadrant Root does not depend on the
      Enterprise Root staying installed; removing the Enterprise Root alone does not remove trust in
      the branches (use -RemoveTrust / -RemoveAllTrust); a branch can be trusted on its own. Whether
      Windows accepts the chains is shown by -Verify ("Windows chain"); that result on your machine
      is the proof.
 L29  Machine-wide OPENSSL_CONF. Install-DevEnvironment.ps1 writes a master OpenSSL configuration (default,
      fips AND the third-party oqsprovider) and sets OPENSSL_CONF for the machine. pki_setup.ps1
      ignores it: every OpenSSL command gets its own configuration. Plain "openssl" commands in your
      shell still use the master file; an oqsprovider built for OpenSSL 3 may print errors under
      4.x, which does not affect the PKI. Two ML-DSA implementations (native and oqsprovider) in one
      shell can confuse other tools.
 L30  Install-DevEnvironment.ps1 installs FireDaemon.OpenSSL (latest). It is not guaranteed to be 4.x; the
      scripts check and say so (section 2.3 of the manual).
 L31  Phase B was tested here on Linux with OpenSSL 4.0.3 and the real FIPS provider: all levels, all four quadrants,
      every format, the floors, the naming, live TLS 1.3 handshakes. NOT tested: -InstallPfx and
      everything that touches the Windows stores, Windows PowerShell behaviour of
      convert-formats.ps1 (UTF-8 with BOM), and the server snippets of tls-guidance.txt in your
      nginx / Apache / Kestrel versions.
 L32  ML-DSA leaves: Windows Schannel (Kestrel / IIS on Windows), Java 25 and browsers do not accept them for HTTPS
      (L1). Issue Classic leaves for those; the Quantum leaves are for OpenSSL services and mutual
      TLS (10.11).
 L33  -Duns writes organizationIdentifier = DUNS+<number>. The CA/Browser Forum has no D-U-N-S scheme there; this is a
      private convention. EV here means the EV policy OID and subject fields, not a browser EV badge
      (L22).
 L34  .cer is written as DER (the Windows default export); .cert as PEM; .p7b as PEM-armored PKCS#7 with leaf and
      chain. The conversion script shows how to get the other encodings.
 L35  tls-guidance.txt lists cipher suites and group names that are right for OpenSSL 3.5+ / 4.x servers. FIPS group
      names (SecP256r1MLKEM768 ...) and ChaCha20 / X25519 exclusion follow common FIPS practice;
      confirm against the validated module you deploy. Windows Schannel has its own cipher policy
      (registry / group policy).
 L36  Unlock = the Read-only attribute is removed from EVERY file and folder of the script folder at every start. A
      key file you marked read-only on purpose is writable again: protect keys with access rights
      (ACLs) instead.
 L37  The Windows Internet mark is removed with Unblock-File: tested only for its Read-only part on Linux.
 L38  leafcerts\ is never deleted by pki_setup.ps1; leaves of a replaced PKI do not chain to the new one (warning).
      Leaves of version 4.6 (pki\leafcerts) are not moved.
 L39  An OCSP signing certificate is for YOUR OCSP responder; this PKI does not run one. A time stamping certificate
      needs a time stamping authority service to be useful.
 L40  Phase C was tested on Linux (OpenSSL 4.0.3, real 7-Zip, Ubuntu 24.04 real system store). NOT tested: -Install / -RemoveTrust on
      Windows, macOS, and the other Linux families except by simulation (--dry-run with a fake
      os-release). The package names of 7-Zip on the RHEL family (EPEL) and SUSE are best effort.
 L41  7-Zip takes the password as an argument (visible in a process list while it runs). The built-in zip engine has no such process.
 L42  ZipCrypto is cryptographically weak; it exists for destinations without 7-Zip and for packages without secrets.
 L43  A package with leafcerts or CA keys is as sensitive as those keys; -IncludeCaKeys lets the destination issue certificates your
      clients trust. Nothing here protects the package after it is unpacked: protect and delete the
      extracted keys.
 L44  macOS may refuse ML-DSA certificates (post-quantum support of the keychain); classic CAs install. The shell script reports which.
 L45  An Enterprise Root signed by a public CA is not installed as a trust anchor on Linux / macOS (the public root already is).
 L46  The OpenSSL source build was NOT completed here: a 1-core VM compiled for over 30 minutes without finishing. Tested: the download, the checksum, the
      Configure with the full flags, and the five readiness checks against a real OpenSSL 4.0.3.
      Build time: 5 minutes on 8 cores, over an hour on one.
 L47  Install-DevEnvironment.ps1 was not run on Windows 11 (WinGet, the FireDaemon upgrade, Windows PowerShell 5.1); it parses and its help, unblock and readiness
      code ran on PowerShell 7 / Linux. The package names of 7-Zip (EPEL on the RHEL family, SUSE)
      and of dotnet / node / go / php are best effort.
 L48  The bootstrap scripts need the Internet and root (or administrator). Distribution packages may be older than "latest". Nothing is removed or downgraded.
 L49  A source build trusts the SHA-256 of the same release page (not a signature). The pwsh download is checked against hashes.sha256 of its release.
 L50  A -AddDevelopmentSAN certificate has 428 SAN entries (about 6 KB more) and is NOT EV-conformant in its SAN: a public CA, a CT-logging validator or a browser
      EV policy would reject it. Some clients ignore IP-address SANs or limit the SAN size.
      leaf-index.json lists every SAN entry of every certificate.
 L51  A wildcard covers one label only (*.nextmantra.com does not match a.b.nextmantra.com or nextmantra.com): the development list therefore names the apex
      domains separately and has no deeper wildcards.
 L52  The development SAN is added to certificates made by GenerateLeafCertificate.ps1 only, not to the default EV leaves of pki_setup.ps1.
 L53  Certificates cannot be renamed: a PKI built before 4.9.x keeps its old names, subjects and policies (a Quantum quadrant root called "... Q3 Root CA G2", roots with OV / DV
      policies, no PEN). Rebuild with pki_setup.ps1 -Clean to get the current ones; the leaves of
      the old PKI then no longer chain to the new CAs. Leaf files made earlier keep their q3 / q4
      names.
 L54  The short code signing subject is not an "EV code signing" subject in the CA/B Forum sense (no serialNumber, jurisdiction, businessCategory): it is for your own lab.

              is extracted.

 17.3 Security model
   Protected   confidentiality and integrity of the package in transit and at rest: AES-256 + HMAC
               per entry (zip) or AES-256 (7z); SHA-256 of every file in the manifest; extraction
               refuses names that leave the destination; a wrong password writes nothing.
   Not protected  the machine that unpacks; the extracted private keys; the password channel; a weak password (policy: 12+ ASCII, 3 classes);
               ZipCrypto (weak by design; refused with private keys); 7-Zip receives the password as
               an argument.
   Scope as risk  CA certificates only = public data. leafcerts = leaf private keys. -IncludeCaKeys = the ability to issue trusted certificates.

 17.4 Destination rules
   Windows    install only on Windows 11 client build >= 26200 (25H2); older Windows, Server, other
              OS refused (exit 2). Roots -> Trusted Root, intermediates -> Intermediate
              (Install-PkiTrust, with read-back); PFX: leaf only. OpenSSL >= 4.0.1 required (exit
              4).
   Linux      family from /etc/os-release: debian / rhel / suse; anchors dir + update command per
              family; ca-certificates installed when the store tooling is missing; 7-Zip installed
              when needed; OpenSSL 4.0.3 built from the official release (checksum verified) on
              consent.
   macOS      security add-trusted-cert (roots) / add-certificates (intermediates, all-ca) in the
              System keychain.
   Roots      every root is an anchor on Linux / macOS by default (one kind of anchor); --trust
              changes it.

 17.5 Reuse
   Module set Transport = 00_Common, 02_OpenSSL (OpenSSL discovery and versions, the bootstrap
   advice), 07_TrustStore (Install-PkiTrust, read-back, removal), 09_Administrator, 16_CertPack,
   17_Transport. Packing loads the Library set (config, catalog, Import-PkiExisting). -Kit copies
   the destination files, so a destination does not need the project.

 20  CSR SIGNING DESIGN  (SignCsr.ps1 / SignCsr.sh, SignExternalCa.ps1, scripts\22_CsrSigning.ps1, scripts\19_ExternalCaSigning.ps1, devkit\lib\pki-csr.py, 4.9.5)
====================================================================================================

 20.1 Two jobs, two scripts
   LEAF request (server, person, code signer ...)  -> SignCsr       -> intermediate q<N>-dv|ov|ev     original PKI and DevKit
   CA request of a department                      -> SignExternalCa -> Classic Quadrant Root q1|q2-root   original PKI only
   Enterprise / Track Roots sign nothing here. The DevKit can not sign a CA: no root key, and
   SignExternalCa.ps1 is not in the kit.

 20.2 Flow of SignCsr
   Read-PkiCsr (openssl req -text / -subject -nameopt multiline,sname / -verify)  ->  Test-PkiCsrSpec (Key, Subject, Names, Extensions, Validity -> findings)
   ->  Write-PkiCsrFindings (colour)  ->  ERROR? exit 2 | -Check? stop  ->  extensions written by THIS PKI (EKU / KU from the purpose and the key type, policies, CRL / AIA, SAN from the
   validated names)  ->  openssl ca -preserveDN (DV: -subj /CN=)  ->  chain files, .cer, .p7b, verify (-x509_strict), sign-info.json, README.txt, signed-csr.tsv.
   SignCsr.sh: pki-csr.py prints the same report and writes csr.env (names, key, counts); bash
   builds the extension file with the functions of lib\pki-lib.sh and calls openssl ca with a
   temporary copy of the CA configuration (default provider only: signing does not need the FIPS
   module, and the .include of fipsmodule.cnf of another machine is not a problem).

 20.3 The specification (single definition; the finding codes are the same in PowerShell and Python)
   Signature      valid, SHA-256+ (MD5 / SHA-1 / SHA-224 rejected; ML-DSA without digest)
   Key            Classic RSA 2048 / 3072 / 4096 / 8192, ECDSA P-256 / P-384 / P-521 | Quantum
                  ML-DSA-44 / 65 / 87 | code signing RSA 4096+, P-384+, ML-DSA-65+ | CA key RSA
                  4096+, P-384+
   Subject        DV CN | OV C O CN (+OU) | EV OV + ST L serialNumber businessCategory jurisdictionC
                  | code signing C O CN | CA OV: C O OU CN ; CA EV: + the EV fields
   Names          TLS DNS / IP (EV: no wildcard, IP, internal, e-mail) | S/MIME e-mail | code
                  signing, TSA, OCSP none
   Validity       DV 5 y | OV 3 y | EV 397 d max | TSA 5 y (EV 397 d) | OCSP 1 y | never beyond the
                  issuer
   Ignored        keyUsage, EKU, policies, CRL / OCSP of the request.  Refused: CA:TRUE (leaf), the
                  CN of one of our CAs (CA request).

 20.4 Decisions inside
   * One checker for leaf and CA requests (profile Leaf | Ca), so that the rules of both scripts can
     not drift apart.
   * Everything the request may influence is validated first and written by us; nothing is copied
     from the request but subject (OV / EV), SAN and the key.
   * A SAN-less TLS request is not refused when the CN is a host name: the CN becomes the DNS name,
     with a WARN (many tools make such requests).
   * Findings are collected, not thrown at the first one: the department fixes everything in one
     round.
   * Exit codes: 0 ok, 1 tool error, 2 the request does not follow the spec (scripts can tell them
     apart).

 21  RELEASES, THE NoCR VARIANT AND REMOVAL  (4.9.5; scripts\01c_Releases.ps1, 01b_CaNaming.ps1, 08_Cleanup.ps1, 07_TrustStore.ps1, pki_remove.ps1)
====================================================================================================

 21.1 Why
   * NoCR: a program that builds the chain online (Word / Office XAdES signatures: "Recoverable
     Signature - the signer's certificate can't be verified") fails or waits when the CRL / OCSP /
     caIssuers URL of a CA certificate is not reachable. A PKI whose CA certificates carry no such
     URL can not fail that way. NOT CONFIRMED FOR WORD 365: a test on 2026-10-11 (leaf signed by
     'Agantra EV RSA-4096 G1 CA (NoCR)', XAdES-EPES) still showed 'Recoverable Signature'. A chain
     with NO revocation information at all is probably reported by Word as 'status unknown' = the
     same message. Diagnose on the Windows machine:
     certutil -verify -urlfetch <leaf>.cer   (the line that fails is the cause). CONFIRMED by
                                             certutil (see 10.86). The remedy is the opposite: make
                                             the CRL URLs REACHABLE (Start-PkiCrlServer.ps1)
     (pki-server.sh, or a hosts entry + a web server on the CRL host) and use the normal PKI.
   * Releases: a new Enterprise Root (and Track, Quadrant, intermediates) can be introduced without
     breaking the old one; each release is removed on its own.

 21.2 Layout, names, slugs
   Every PKI lives inside the folder pki\ next to the scripts, one subfolder each:

    pki\R1         release 1, CA certificates WITH CRL / OCSP / CA Issuers information   (normal family)
    pki\R2         release 2 (a new Enterprise Root and everything below it)
    pki\NoCR-R1    release 1 of the NoCR family: CA certificates WITHOUT that information
    pki\NoCR-R2    release 2 of the NoCR family

  A PKI made by an older version sits directly in pki\ (pki\root, pki\classical ...). It counts as
  R1 and keeps working.

  NAMES.  Release 1 has no suffix. From release 2 every CA common name ends in " R2", " R3" ... The NoCR family adds " (NoCR)":
      Agantra Root CA G1               R1, with revocation information
      Agantra Root CA G1 R2            release 2
      Agantra Root CA G1 (NoCR)        NoCR, release 1
      Agantra Root CA G1 (NoCR) R2     NoCR, release 2
  The Track Roots, Quadrant Roots and intermediates follow the same rule, the file names and URL
  slugs get -nocr / -r2 (agantra-q1-ov-g1-nocr-r2). Leaf certificates are not renamed. A common name
  is limited to 64 characters: when one would be longer (a Quantum Q-root with "(NoCR) R2"), the
  word PQC becomes PQC in ALL names of that PKI (agantra_pki.cnf [ ca_names ] QuantumLabelShort).
  The words are configurable: NoCrLabel, ReleaseLabel. Preview: .\pki_setup.ps1 -ShowNames
  -NoCaRevocationInfo -NewRelease.

  WHAT -NoCaRevocationInfo DOES.  The Enterprise Root, Track Roots, Quadrant Roots and intermediates are made WITHOUT crlDistributionPoints,
  authorityInfoAccess OCSP and caIssuers. Programs that check the CA certificates online (Word /
  Office signatures, some code-signing tools) then never wait for an unreachable CA URL. Leaf
  certificates keep their own revocation settings: add -NoRevocationInfo to the leaf generators when
  the leaf must not carry them either. The NoCR family is a SEPARATE set of roots (different keys):
  leaves of the normal family do not chain to it. To switch: remove the trust of the normal PKI,
  build / install the NoCR one, issue the leaves again.

  BUILD
    .\pki_setup.ps1 -InstallTrust                            R1
    .\pki_setup.ps1 -NewRelease -InstallTrust                R2 (latest + 1), the old releases stay
                                                             and keep working
    .\pki_setup.ps1 -Release 3                               exactly R3 (an existing R3 is an error
                                                             unless -Clean)
    .\pki_setup.ps1 -NoCaRevocationInfo -InstallTrust        NoCR-R1;  with -NewRelease: NoCR-R2 ...

  WHICH RELEASE DO THE OTHER SCRIPTS USE?
    GenerateLeafCertificate / GeneratePersonLeafCertificate / GenerateOffice365LeafCertificate /
    SignCsr / SignExternalCa / PkiRevocation / PkiTransport / New-PkiServerPackage and the shell
    twins (--release N, --no-ca-revocation-info):
      (nothing)             the LATEST release of the normal family (when only a NoCR family exists,
                            that one)
      -Release N            release N; when N does not exist (deleted) the LATEST release is used
                            and a warning says so. Never an error.
      -NoCaRevocationInfo   the NoCR family
      -PkiRoot <folder>     exactly that folder, nothing else
    Administration (-Verify, -ReinstallTrust, -RemoveTrust) takes the release exactly; with several
    releases installed -RemoveTrust needs -Release N, so nothing is removed by accident.

  REMOVE
    .\pki_remove.ps1 -List                      what is installed (release, variant, folder, CAs,
                                                expiry, trusted in Windows?)
    .\pki_remove.ps1 -Release 2                 trust of R2 out of Windows (Root, Intermediate,
                                                Personal), files stay
    .\pki_remove.ps1 -Release 2 -DeleteFiles    and delete pki\R2
    .\pki_remove.ps1 -Release 1 -NoCaRevocationInfo -DeleteFiles      the NoCR release
    .\pki_remove.ps1 -All                       EVERY release and BOTH families: trust out of
                                                Windows and the whole pki\ folder deleted
    .\pki_setup.ps1 -RemoveTrust -Release 2     same trust removal as pki_remove (by thumbprint and
                                                by CA name)
    .\pki_setup.ps1 -RemoveAllTrust             same as pki_remove -All
  The removal asks for a yes (-Yes skips it). Windows needs an Administrator PowerShell for the
  stores; on Linux only the files are removed.

  LIMITS.  A DevKit and a server package hold ONE PKI (the latest release unless -Release / -NoCaRevocationInfo says otherwise): the
  names and slugs of the kit come from it. The server can hold the CRL and CA files of several
  releases side by side (they have different file names); OCSP and the time stamp service serve the
  release that was installed LAST. Leaf certificates of an older release stay valid until their CA
  is removed or revoked: new leaves use the latest release.

 22  CRL / OCSP SERVER FROM THE PKI  (4.9.5; scripts\18_Revocation.ps1 Write-PkiServerInfo, linux\pki-server\pki-server.sh, PkiTransport.ps1 -Server, linux\Install-DevEnvironment.sh)
====================================================================================================
 22.1 Flow
   pki_setup.ps1 / PkiRevocation.ps1  ->  pki\R<n>\publish (CRL, CA files, slug names) + pki\R<n>\server (what the server must satisfy)
   PkiTransport.ps1 -Server           ->  agantra-pki-server-<date>.zip (no private key)  ->
                                      Ubuntu: pki-server.sh install --source ./pki  ->  nginx (PPA)
                                      + OCSP + TSA
 22.2 What the server reads from the PKI
   THE PKI TELLS THE SERVER  (4.9.5; pki\R<n>\server\ , written by pki_setup.ps1 and refreshed by every PkiRevocation.ps1 action)
   The server does not guess and does not depend on a file you keep in step: the PKI writes what it
   really contains.
       server-info.json     release, variant (normal | NoCR), name suffix, CRL days, the hosts, the
                            URL templates, and for every CA: id, common name, parent, level, track,
                            fips, slug, crl / crt file names, CRL number and next update,
                            "ocspResponder" yes / no
       ca-list.tsv          the same list for shell (tab separated: id kind slug level track fips
                            parent ocsp crl-file crt-file common-name crl-next-update)
       server.env           PKI_SRV_RELEASE, PKI_SRV_VARIANT, PKI_SRV_NAME_SUFFIX, PKI_SRV_HOSTS_CRL
                            (CRL + CA-issuer hosts), PKI_SRV_HOSTS_OCSP, PKI_SRV_CRL_DAYS
       expected-urls.tsv    EVERY CRL / CA-issuer / OCSP URL that the certificates of this PKI
                            contain: type, host, url
       DNS-RECORDS.txt      the host names to put in DNS (or the hosts file), with their role
   pki-server.sh install / update copies these files to
   /etc/agantra-pki-server/pki-info/<R1|R2|NoCR-R1>/, builds the nginx server_name lists from them,
   serves the CRL and CA files under the SAME file names (the slug of the URL: agantra-root-g1.crl,
   agantra-q1-ov-g1-r2.crl ...), creates the OCSP responders from the CA list, names the OCSP / time
   stamp requests the same way as the PKI does ("Agantra EV RSA-4096 G1 CA (NoCR) R2 OCSP
   Responder", "Agantra Time Stamping Authority (NoCR) R2"), and  pki-server.sh test  asks every URL
   of expected-urls.tsv (right host name, right path, the file parses as a CRL / certificate). The
   test therefore proves that the server satisfies the certificates that exist, not a fixed list.
   Several releases / families: install the package of each one; the files of all of them stay
   (their names differ), the host lists are added together, OCSP and the time stamp service serve
   the release installed LAST. A PKI made by an older version has no server\ folder: the hosts then
   come from agantra_pki.cnf, and  .\PkiRevocation.ps1 -Action Info  creates the folder. A NoCR PKI
   has no URL in its CA certificates; the server is still needed for the leaf certificates (they
   keep their CRL / OCSP URLs). NAMES of the CRL and CA-issuer files (the {ca} of the URLs) follow
   the CA names: Root CA -> agantra-root-g1, Classic Root -> agantra-classic-root-g1, PQC Root ->
   agantra-pqc-root-g2, Q1 / Q2 roots -> agantra-q1-root-g1 / -g2, intermediates -> agantra-q1-ov-g1
