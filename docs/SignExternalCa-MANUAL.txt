 READ THIS FIRST
----------------------------------------------------------------------------------------------------
 What it is   : Signs the CA request of another department, so they can run their own intermediate
                CA.
 Who reads it : The owner of the PKI.
 You need     : The CA .csr file and your PKI.
 Start with   : Read the first section, then run the example.
 Words        : GLOSSARY.txt (technical terms), GLOSSARY-ENGLISH.txt (everyday English words)
----------------------------------------------------------------------------------------------------
 Manual : docs\SignExternalCa-MANUAL.txt  Design : docs\PKI-Design-with-FIPS-and-PQC.txt (10.58,
          10.73)
 Needs  : PowerShell 7+, OpenSSL 4.x, the ORIGINAL PKI made by pki_setup.ps1 (a DevKit has no
          Quadrant Root key and can not do this).
 A leaf (server, person ...) request is a different job: SignCsr.ps1.

WHAT IT DOES
  A department has made its own CA key and a CSR and sends you only the CSR. This script
    1. CHECKS the request against the specification of this PKI (colour report: red ERROR, yellow
       WARN, green OK, cyan INFO; every finding says why and how to fix it); an ERROR means nothing
       is signed (exit code 2),
    2. signs it with our Classic QUADRANT ROOT, so that everything his CA issues chains to OUR
       Enterprise Root,
    3. writes a NEW folder (never overwritten):
          external-ca\<name>_<yyyyMMdd-HHmmss>\
              <name>.csr            his request, unchanged (LF)
              <name>.crt            HIS CA CERTIFICATE, signed by us
              <name>-fullchain.crt  his certificate + our chain (up to, not including, the Enterprise Root): the chain for HIS certificates
              <name>-chain.crt      our chain only          root.crt   our Enterprise Root (the trust anchor)   our-ca-bundle.crt   chain + root
              ca-info.json  README.txt   the facts: signer, subject, key, dates, serial,
                                         fingerprint, constraints, verification result
  The certificate is recorded in the index.txt of the signing root: revoke it with PkiRevocation.ps1
  -Action Revoke and it is in the CRL. Nothing but the CSR comes in; no private key of ours goes
  out.

WHO SIGNS - ONLY A CLASSIC QUADRANT ROOT
  (default)  q1-root   Classic, non-FIPS (Quadrant 1)
  -Fips      q2-root   Classic, FIPS (Quadrant 2).     -Quadrant 1|2 does the same by number.
  Never an intermediate, never a Quantum Quadrant Root, never the Track or Enterprise Root: they
  sign our own CAs only. The DevKit holds issuing keys only: a request for a CA certificate can ONLY
  be signed here, on the original PKI. (pathLenConstraint: a Quadrant Root has 1, so his CA is a
  sibling of our intermediates and may issue end-entity certificates only - pathLen 0 - unless you
  raise -PathLen.)

THE LEVEL OF HIS CA (-Level, default OV) AND WHAT HIS REQUEST MUST CONTAIN
  OV (default)  subject C (2 letters), O, OU and CN are REQUIRED, otherwise the request is rejected. ST and L are recommended.
                Allowed: street, postalCode, name, emailAddress, telephoneNumber.   Policies: OV + High Assurance + PEN.
  EV            everything of OV, plus ST, L, serialNumber, businessCategory (Private Organization |
                Government Entity | Business Entity | Non-Commercial Entity) and jurisdictionC.
                Recommended: jurisdictionST, postalCode. Validity 397 days at most.
  DV            CN required; any other field is dropped from the certificate (WARN).
  Key           RSA 4096 or 8192, or ECDSA P-384 / P-521 (equal strength; P-256, RSA 2048/3072,
                Ed25519, ML-DSA are rejected - this is a Classic CA). The signature of the request
                must be valid and SHA-256 or stronger. A request that uses the CN of one of OUR CAs
                is refused.

OPTIONS
  -CsrType Auto|Leaf|IntermediateCA   the kind of request (5.2.6, default Auto). Auto recognises it:
                                      CA:TRUE = a CA request. This script signs CA requests; a LEAF
                                      request (names, no CA:TRUE)
                         is refused with the command to use (SignCsr.ps1). A hand-made CA request
                         without CA:TRUE is accepted as a CA request. -Level: default OV, EV when
                         the request carries the complete EV information. New-PkiCsr.ps1
                         -CertificateType IntermediateCA makes a matching request.
  -Csr <file>            His PKCS#10 request (PEM).
  -Level DV|OV|EV        Level written into his certificate (default OV).          -Fips   sign with q2-root (Classic FIPS).
  -Name <text>           Name of the output folder and files (default: his CN).
  -Days <n>              Validity (default 1825 = 5 years; EV 397, EV may not be longer), cut to
                         what the signer still has.
  -PathLen 0..3          pathLenConstraint of HIS certificate (default 0). Limited to the signer's
                         pathLen - 1.
  -PermitDns <a,b>       Name constraint (critical): he may issue only for these DNS names and their
                         sub-domains (example.internal).
  -PermitEmail <a,b>     Name constraint: only these e-mail addresses / domains (@example.internal).
  -OutFolder <path>      Where the per-request folders go (default: .\external-ca next to the pki
                         folder).
  -Check                 Check the request and print the report; sign nothing.         -Strict   warnings count as errors.
  -NoColor               Plain text (also when the environment variable NO_COLOR is set).
  -Force                 Issue even when the signer has pathLenConstraint 0 (lab only).
  -List                  List the earlier requests (folders, signer, serial, dates) and stop.
  -Unblock               UNBLOCK and UNLOCK the script folder and the pki folder, then stop.
  -ConfigFile <path> -PkiRoot <path> -OpenSslPath <path> -FipsModuleConfig <path> -Verbose   as in pki_setup.ps1.   -Help   this text.
  -Release <n>         Release of the PKI to use (R1, R2 ...). Default: the LATEST release in
                       .\pki\. A release that no longer exists (deleted) is not an error: the latest
                       release is used and a warning says so.
  -NoCaRevocationInfo  Use the NoCR family (pki\pki-<name>-nocr-<NN>, CA certificates without CRL / OCSP). Default: the normal family (the NoCR one
                       when it is the only one).   -PkiRoot <folder> names one PKI folder and
                                                   overrides both.

THE OTHER SIDE (he makes the key and the CSR himself, for example)
  openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:4096 -out dept-ca.key
  openssl req -new -key dept-ca.key -sha384 -subj "/C=EE/ST=Harju/L=Tallinn/O=Dept Ltd/OU=IT Department/CN=Dept Issuing CA G1" -out dept-ca.csr
  (EV adds  /serialNumber=12345678/businessCategory=Private Organization/jurisdictionC=EE )
  He keeps dept-ca.key. He sends only dept-ca.csr and gets back the folder content.

EXAMPLES
  .\SignExternalCa.ps1 -Csr .\dept-ca.csr                         OV, signed by q1-root (Classic, non-FIPS)
  .\SignExternalCa.ps1 -Csr .\dept-ca.csr -Fips -PermitDns dept.internal -Days 3650
  .\SignExternalCa.ps1 -Csr .\dept-ca.csr -Level EV -Check        would an EV CA be accepted? report
                                                                  only
  .\SignExternalCa.ps1 -List
EXIT CODES   0 ok (signed, or -Check passed)   1 error (the message says why)   2 the request does not follow the spec (the report says where)
