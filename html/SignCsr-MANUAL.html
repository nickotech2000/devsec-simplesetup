READ THIS FIRST#

 What it is   : A script that checks the certificate request (CSR) of a colleague and, if it is
                good, signs it with the right intermediate CA of your PKI.
 Who reads it : The person who SIGNS requests: the owner of the PKI, or a developer who has a
                DevKit. No PKI knowledge is needed. Every new word is explained in GLOSSARY.txt
                and GLOSSARY-ENGLISH.txt.
 Time needed  : 10 minutes to read sections 1 to 5. A signing takes a few seconds.
 You need     : A PKI from pki_setup.ps1 (or a DevKit) and the CSR file of your colleague.
 Start with   : Section 4 (Quick start).
 Related manuals:
   NewPkiCsr-MANUAL.txt        how your colleague makes the key and the CSR (step by step)
   DevKit-MANUAL.txt           the zip that lets developers sign (sections 11 and 17)
   SignExternalCa-MANUAL.txt   sign a CSR for a CA certificate (SignCsr refuses these)
   PkiRevocation-MANUAL.txt    revoke a certificate you signed
   PKI-Design-with-FIPS-and-PQC.txt   why it is built this way (senior staff, 10.72 and section 20)
 Help in the terminal:   .\SignCsr.ps1 -Help     ./SignCsr.sh --help      (one page at a time)

1 WHAT SIGNCSR DOES#

Your colleague needs a certificate for a server, a person or a program. He makes his OWN private key and a request file (CSR) on his own computer. He sends you ONLY the CSR. SignCsr then does three things:

     COLLEAGUE                                   YOU (SignCsr)
     private key (stays with him)
     web01.csr   --------------------------->   1. checks the CSR against the rules
                                                2. signs it (only if there is no error)
     web01 folder  <---------------------------  3. writes a folder with the certificate

You never see his private key. He never sees yours. Only the CSR goes one way and only the certificate goes back.

SignCsr signs LEAF certificates (servers, people, code signing, e-mail). It does NOT sign the certificate of a new CA. That is another script (section 6).

2 THE WORDS YOU NEED#

 CSR            Certificate Signing Request. A file with his public key and his name. No secret.
 Leaf           A certificate for a server, a person or a program. It cannot sign other
                certificates.
 Intermediate   A CA below the root. It signs leaf certificates. Its name is q<N>-dv, q<N>-ov or
                q<N>-ev.
 Level          DV, OV or EV. How much the name inside the certificate was checked:
                DV = domain name only, OV = company too, EV = company, registration, country.
 Quadrant       One of four PKI families. Q1 = Classic, not FIPS. Q2 = Classic, FIPS.
                Q3 = Quantum, not FIPS. Q4 = Quantum, FIPS.
 SAN            Subject Alternative Name. The host names, IP addresses or e-mail addresses that
                the certificate is valid for.
 CN             Common Name. The main name in the subject, for example web01.dept.example.
 Chain          His certificate, then the CA that signed it, then the root.
 Revoke         Declare a certificate bad before it ends.

3 BEFORE YOU START#

  • A PKI made by pki_setup.ps1 in this project, or a DevKit that was installed with Install-PkiTrust (section 11).
  • PowerShell 7 and OpenSSL 4 for SignCsr.ps1. bash, OpenSSL 3 or newer and python3 for SignCsr.sh.
  • The CSR file. Ask your colleague to use New-PkiCsr.ps1 or new-pki-csr.sh (NewPkiCsr-MANUAL.txt). Then the level and the names are right at the first try.
  • A computer that is allowed: Windows 11 24H2 or newer, Windows Server 2025 (everything), Windows Server 2022 (Classic only, no Quantum). Linux: Ubuntu 24+, CentOS Stream / RHEL / Rocky / Oracle 10+, SLES / openSUSE 15+. Others: error, exit 5, nothing is done.

4 QUICK START#

Put web01.csr in the project folder, then:

     .\SignCsr.ps1 -Csr .\web01.csr -Check     (Linux: ./SignCsr.sh --csr web01.csr --check)
     (read the report, fix every red ERROR with your colleague)
     .\SignCsr.ps1 -Csr .\web01.csr            (Linux: ./SignCsr.sh --csr web01.csr)

The new folder is csr-signed\web01_<date>-<time>\. Send it to your colleague. The file for his web server is web01-fullchain.crt.

5 THE FOUR STEPS IN DETAIL#

 Step 1  Check only. -Check prints the report and signs nothing. Do it every time.
 Step 2  Read the report (section 8). Red ERROR = he must make a new CSR. Yellow WARN = read it;
         the CSR is allowed but something was changed or dropped.
 Step 3  Sign. Run the same command without -Check. Add -DV, -OV or -EV only when you want to force
         the level. Add -Purpose when the certificate is not for a TLS server (section 16).
 Step 4  Send the folder. README.txt inside tells him what to do with each file. The folder has no
         private key. If the channel is not trusted, compare the SHA-256 in sign-info.json with him.

Every run makes a NEW folder. Nothing is overwritten. The line in csr-signed\signed-csr.tsv shows all earlier runs: .\SignCsr.ps1 -List.

6 WHICH CA SIGNS#

 Request of                     Script                      Signs with                 Runs on
 -----------------------------  --------------------------  -------------------------  ------------
 server, person, code signer    SignCsr.ps1 / SignCsr.sh    an INTERMEDIATE CA         PKI machine
                                                                                       and DevKit
 a CA of a department           SignExternalCa.ps1          a Classic QUADRANT ROOT    PKI machine
                                                                                       only
 anything with a root           -                           -                          only you
 The intermediate is named q<N>-<level>:  q1-dv  q1-ov  q1-ev  (and q2, q3, q4).
 - Level: -DV, -OV or -EV. Without one, the CSR decides:
     complete EV data (businessCategory + serialNumber + jurisdictionC)  ->  EV
     company name and country (O and C)                                    ->  OV
     common name only                                                      ->  DV
 - Track: Classic is the default. -Quantum uses Q3 (Q4 with -FIPS). An ML-DSA CSR needs -Quantum.
 - FIPS: -FIPS uses Q2 (Classic) or Q4 (Quantum). Without it: Q1 or Q3.
 - A CSR with CA:TRUE is refused. The message names the script to use: SignExternalCa.ps1.
   Intermediates sign leaf certificates only (pathLenConstraint 0). A root never signs here.

7 THE RULES A CSR MUST FOLLOW#

 Signature   Valid (it proves he owns the key). SHA-256 or stronger. ML-DSA needs no digest.
 Key         Classic: RSA 2048, 3072, 4096, 8192, or ECDSA P-256, P-384, P-521.
             Quantum: ML-DSA-44, ML-DSA-65, ML-DSA-87.
             Code signing: RSA 4096 or more, ECDSA P-384 or more, ML-DSA-65 or more.
             Never: RSA below 2048, other curves, Ed25519, DSA.
             A Classic CSR cannot get a Quantum issuer. A Quantum CSR cannot get a Classic issuer.
 Subject     DV: CN only. Other fields are dropped (WARN).
             OV: C (2 letters), O and CN are required. ST and L are recommended. Allowed: OU,
                 street, postalCode, name, emailAddress, telephoneNumber, serialNumber.
             EV: OV plus ST, L, serialNumber, businessCategory and jurisdictionC. businessCategory
                 is one of: Private Organization, Government Entity, Business Entity,
                 Non-Commercial Entity. Recommended: jurisdictionST, postalCode.
             Code signing: C, O, CN (CN = the company name = O).
             Anything else in the subject is an ERROR for that level.
 Names       TLS (ServerAuth, ClientAuth, ServerClientAuth): DNS names and IP addresses.
             No SAN: the CN becomes the DNS name (WARN).
             EV: no wildcard, no IP address, no internal name (.internal .local .lan ...), no
             e-mail address.
             E-mail certificate: e-mail addresses only.
             Code signing, time stamping, OCSP: no names. They are dropped (WARN).
 Validity    DV 5 years. OV 3 years. EV 397 days at most (a longer -Days is an ERROR).
             Time stamping 5 years. OCSP signing 1 year. Never longer than the CA that signs.
 Ignored     keyUsage, extendedKeyUsage, CRL and OCSP addresses in the CSR. Your PKI sets them
             from -Purpose and the level. A policy OID in the CSR is kept ONLY inside the company
             arc 1.3.6.1.4.1.<PEN> (the IANA number of your company).

8 READ THE REPORT#

 Colour    Meaning
 --------  ----------------------------------------------------------------------------------
 ERROR     red. The CSR breaks a rule. Nothing is signed. Exit code 2.
 WARN      yellow. Allowed, but something is changed or dropped. Read it. -Strict makes it ERROR.
 OK        green. The check passed.
 INFO      cyan. A fact.

Every ERROR and WARN names the field, says what is wrong and gives the fix on the next line, with a code in [ ] (section 12). Plain text: -NoColor, --no-color or NO_COLOR=1.

Example of a bad CSR:

   .\SignCsr.ps1 -Csr .\shop.csr -EV
     [ERROR] serialNumber    The subject has no serialNumber, required for EV.
                             [SUBJ-REQ-serialNumber] fix: add /serialNumber=17344131 to the
                             subject (the value is yours).
     [ERROR] businessCategory  'Bank' is not one of: Private Organization, Government Entity,
                             Business Entity, Non-Commercial Entity.
     [ERROR] DNS             '*.shop.example': an EV certificate may not contain a wildcard name.
                             [SAN-EV-WILDCARD]
     [WARN]  postalCode      The subject has no postalCode (recommended for EV).
     Result: 3 error(s), 1 warning(s). Nothing was signed.  (exit code 2)

9 WHAT YOU GET#

 A new folder:  csr-signed\<name>_<yyyyMMdd-HHmmss>\   (Linux: <yyyymmdd-HHMMSS>)
 File                  What it is
 --------------------  --------------------------------------------------------------------
 <name>.crt  .cer      His certificate (PEM and DER).
 <name>-fullchain.crt  His certificate + the CA chain. This is the file for his web server.
 <name>-chain.crt      The CA chain only.
 <name>.p7b            Certificate + chain for Windows.
 root.crt              Your Enterprise Root. His clients must trust it.
 our-ca-bundle.crt     Chain + root.
 <name>.csr            His request, kept for the record.
 sign-info.json        What was signed, the SHA-256, the CA, the dates.
 README.txt            What HE must do with the files.
 Plus one line in csr-signed\signed-csr.tsv. The certificate is recorded in the index.txt of the
 issuing CA, so it can be revoked (PkiRevocation.ps1 -Action Revoke, PkiRevocation-MANUAL.txt).
 After you sign, he installs it:
   Windows  certreq -accept web01.cer
   nginx    ssl_certificate web01-fullchain.crt;  ssl_certificate_key web01.key;

10 WHAT THE CERTIFICATE CONTAINS#

Decided by YOU (the PKI), not by the request: CA:FALSE (critical), keyUsage and extendedKeyUsage.

 -Purpose                   keyUsage                                        extendedKeyUsage
 -------------------------  ----------------------------------------------  -------------------
 ServerAuth                 digitalSignature (+ keyEncipherment for RSA)    serverAuth
 ServerClientAuth           the same                                        serverAuth, clientAuth
 ClientAuth                 digitalSignature                                clientAuth
 EmailProtection            digitalSignature, nonRepudiation (+ key...)     emailProtection,
                                                                            clientAuth
 CodeSigning                digitalSignature                                codeSigning
 TimeStamping               digitalSignature                                timeStamping (critical,
                                                                            alone) + policy OID
 OcspSigning                digitalSignature                                OCSPSigning + nocheck

Also inside: the policies (level policy, your PEN policies, High Assurance for OV, the EV CPS), the CRL address and the OCSP / caIssuers addresses of the issuing CA (not with -NoCrl / -NoOcsp), the key identifiers, and the validated names. Subject: DV = the CN. OV and EV = the subject of the request. Serial: the next one of the issuing CA (DevKit: random, see section 11). Signature digest: SHA-256 (RSA CA), SHA-384 (ECDSA CA), none (ML-DSA).

11 THE DEVKIT: DEVELOPERS SIGN TOO#

The DevKit (PkiTransport.ps1 -DevKit, DevKit-MANUAL.txt) holds SignCsr.ps1 and SignCsr.sh. They work on their own: no original PKI computer is needed.

  • The kit signs with ALL its intermediates (DV, OV, EV; Classic non-FIPS and FIPS; Quantum when the PKI has those quadrants).
  • The kit can NEVER sign a root. SignExternalCa.ps1 is not in the kit and the kit has no root key. A CSR for a CA certificate goes to you.
  • The certificate goes into the index.txt of the KIT, not into the master CRL or OCSP. You cannot revoke it one by one. If a kit leaks, revoke the intermediate.
  • The serial numbers of a kit are random per copy (set at install). Two kits never make the same serial.
  • Linux with the original PKI: run .\SignCsr.ps1 -WriteShellEnv. It writes devkit.env. Then bash devkit/SignCsr.sh --csr web01.csr --ov signs on the original PKI folder.

12 REPORT CODES (THE TABLE)#

 Key and signature
   KEY-SIGNATURE        The signature of the CSR does not verify (file changed, or not signed with
                        the key inside).
   KEY-ALG              Key type not accepted (Ed25519, Ed448, DSA, RSA-PSS).
   KEY-RSA-SMALL        RSA below 2048.         KEY-RSA-ODD   RSA size is not 2048/3072/4096/8192.
   KEY-CURVE            ECDSA curve is not P-256, P-384 or P-521.
   KEY-CS-RSA, KEY-CS-CURVE, KEY-CS-MLDSA   Code signing needs RSA 4096+, ECDSA P-384+, ML-DSA-65+.
   KEY-CA-RSA, KEY-CA-CURVE                 The same for the key of a CA.
   KEY-QUANTUM-REQUIRED   Quadrant 3 or 4 (-Quantum) takes ML-DSA keys only.
   KEY-CLASSIC-REQUIRED   A Classic request with an ML-DSA key.
   KEY-DIGEST           The CSR is signed with MD5, SHA-1 or SHA-224. SHA-256 or stronger needed.
 Subject
   SUBJ-REQ-<attr>      A required attribute is missing.
   SUBJ-REC-<attr>      A recommended attribute is missing (WARN).
   SUBJ-ATTR-<attr>     The attribute is not allowed at this level.
   SUBJ-DV-DROP         DV: other attributes are dropped (WARN).
   SUBJ-FMT-C, SUBJ-FMT-jurisdictionC   Not 2 capital letters.
   SUBJ-FMT-businessCategory   Not one of the four allowed values.
   SUBJ-LEN-<attr>      Too long (CN, O, OU: 64. ST, L: 128).
   SUBJ-DUP-<attr>      The attribute is there twice.
   SUBJ-CN-CHAR         A '/' or '\' in the CN.            SUBJ-EMPTY   No subject.
   SUBJ-CS-CN           Code signing: CN should equal O (WARN).
   SUBJ-CN-NOT-SAN      DV: the CN is not one of the names.
 Names
   SAN-NONE             No usable name. The CN is used when it is a host name or an e-mail address
                        (SAN-DERIVED, WARN).
   SAN-DNS-INVALID, SAN-IP-INVALID, SAN-EMAIL-INVALID   Syntax error.
   SAN-WILDCARD         Wildcard name (WARN; allowed outside EV).
   SAN-DROPPED, SAN-OTHER   Names that this purpose does not carry.
   SAN-EV-WILDCARD, SAN-EV-IP, SAN-EV-INTERNAL, SAN-EV-EMAIL   EV rules. Internal means .internal
                        .local .localhost .lan .corp .home .intranet .private .test .invalid
                        .developer .api .ldap, or no dot.
 Other
   EXT-CA               The CSR asks for CA:TRUE.
   EXT-IGNORED          INFO. Key usage, EKU, policies of the CSR are not used.
   VAL-EV               -Days above 397 for EV.
   SUBJ-OUR-CA          (SignExternalCa) the CN is the name of one of our CAs.

13 RECIPES, COPY AND PASTE#

 Web server, level from the CSR:       .\SignCsr.ps1 -Csr .\web01.csr
 Check only:                           .\SignCsr.ps1 -Csr .\web01.csr -Check
 Server and client login, OV:          .\SignCsr.ps1 -Csr .\web01.csr -OV -Purpose ServerClientAuth
 Would the FIPS EV CA sign it?         .\SignCsr.ps1 -Csr .\web01.csr -EV -FIPS -Check
 Code signing, no CRL/OCSP address:    .\SignCsr.ps1 -Csr .\sign.csr -OV -Purpose CodeSigning `
                                           -NoRevocationInfo
 Quantum (ML-DSA) CSR:                 .\SignCsr.ps1 -Csr .\pq.csr -Quantum -OV
 Add the development names:            .\SignCsr.ps1 -Csr .\web01.csr -AddDevelopmentSAN
 Earlier requests:                     .\SignCsr.ps1 -List
 Linux:                                ./SignCsr.sh --csr web01.csr --ov --purpose ServerClientAuth
 How HE makes the CSR by hand (New-PkiCsr.ps1 is easier):
     openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out web01.key
     openssl req -new -key web01.key -sha256 -out web01.csr \
        -subj "/C=EE/ST=Harju/L=Tallinn/O=Dept Ltd/OU=IT/CN=web01.dept.example" \
        -addext "subjectAltName=DNS:web01.dept.example,DNS:www.dept.example"
     ECDSA:   openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-384 \
                 -pkeyopt ec_param_enc:named_curve -out web01.key
     ML-DSA:  openssl genpkey -algorithm ML-DSA-65 -out web01.key       (OpenSSL 3.5+ or 4.x)
     EV adds: /serialNumber=12345678/businessCategory=Private Organization/jurisdictionC=EE
 Windows without OpenSSL: save this as request.inf, then   certreq -new request.inf web01.csr
     [NewRequest]
     Subject = "CN=web01.dept.example, O=Dept Ltd, C=EE"
     KeyLength = 2048
     KeySpec = 1
     Exportable = FALSE
     MachineKeySet = TRUE
     HashAlgorithm = SHA256
     RequestType = PKCS10
     [Extensions]
     2.5.29.17 = "{text}"
     _continue_ = "DNS=web01.dept.example&"

14 PROBLEMS AND ANSWERS#

 Exit code 2, "does not follow the spec"
     Read the report. Fix the CSR (he makes a new one) or choose another level, purpose or
     quadrant. Nothing was signed.
 "This PKI has no Quadrant 3"
     The PKI was built without the Quantum quadrants. Build with pki_setup.ps1 -Quadrant 1,2,3,4.
 "The private key of ... is not here"
     A DevKit made with -DevKitNoKeys, or the key lives on the PKI server.
 "verification FAILED" in README.txt
     The chain does not reach the root file next to it. Was the PKI rebuilt after the CA was
     loaded? Run pki_setup.ps1 -Verify.
 SignCsr.sh: "python3 is needed"
     sudo apt install python3. The checker is a small script. It only reads the CSR.
 "A CA request is refused"
     The CSR has CA:TRUE. Use SignExternalCa.ps1 (SignExternalCa-MANUAL.txt).
 "NoCR PKI missing"
     -NoCrl, -NoOcsp or -NoRevocationInfo needs the NoCR family. Run
     pki_setup.ps1 -NoCaRevocationInfo -InstallTrust first.
 Exit code 5
     This computer is refused (section 3). Nothing was done.

15 LIMITS YOU MUST KNOW#

  • SignCsr signs only leaf certificates. A CA certificate goes to SignExternalCa.ps1.
  • It cannot make a certificate stronger than the CA that signs it. The validity is cut to what the CA still has.
  • It trusts the CSR only for the key, the subject and the names. It does NOT check that the company in an OV or EV subject really exists. That check is your job, before you sign.
  • A certificate signed in a DevKit is not in the master CRL. See section 11.
  • Windows Server 2022: Classic only. -Quantum is an error.

VERSION REPORT (new in 6.4.13). Every script answers -Version (PowerShell) or --version (bash). It prints the script version, author, company, e-mail, the operating system with its version and patch level (or kernel), and the newest .NET, Node.js, Python 3, Java, shell, Schannel and OpenSSL found, with the vendor of each OpenSSL. It changes nothing. Details: VERSION-INFO.txt.

17 WHAT WAS TESTED, WHAT WAS NOT#

Tested on Ubuntu 24.04 with OpenSSL 4.0.3 and PowerShell 7: -Check, signing, a refused CA request, the folder contents, and SignCsr.sh in a DevKit. NOT tested: a real Windows (the platform gate was simulated), Windows PowerShell is not used by this script, real RHEL / SUSE machines, certreq with a real Windows key store. Run the acceptance steps in PKI-Acceptance-Checklists.txt (E44).
