READ THIS FIRST#

 What it is   : A script. It builds your own private PKI: the root CAs, the intermediate CAs and
                one test certificate for each quadrant.
 Who reads it : The person who owns the PKI. IT, infrastructure or developer. No PKI knowledge
                is needed. Every new word is explained in GLOSSARY.txt.
 Time needed  : 30 minutes to read sections 1 to 4. The first run takes a few minutes.
 You need     : A Windows 11 or Windows Server computer, PowerShell 7 and OpenSSL 4.
 Start with   : Section 3 (Before you start), then section 4 (First run, step by step).
 Words        : GLOSSARY.txt (technical words), GLOSSARY-ENGLISH.txt (everyday English words)
 Related manuals:
   GenerateLeafCertificate-MANUAL.txt   make more certificates after the PKI exists
   Create-WebServerConfig-MANUAL.txt    use a certificate in nginx or Apache
   PkiTrustKit-MANUAL.txt               let other computers trust the PKI
   DevKit-MANUAL.txt                    give developers a zip to make their own certificates
   PkiRevocation-MANUAL.txt             revoke a certificate, CRL, OCSP, time stamping
   PUBLIC-CA-ENTERPRISE-ROOT.txt        let DigiCert, GlobalSign or Sectigo sign your root
   PKI-Design-with-FIPS-and-PQC.txt     why it is built this way (for senior staff)

1 WHAT THE SCRIPT DOES#

 pki_setup.ps1 builds a private PKI in the folder .\pki. "Private" means: only computers that you
 set up will trust it. A normal browser does not trust it until you install the root.

The script makes these things, from the top to the bottom:

     Enterprise Root CA
       |-- Classic Track Root CA       (RSA and ECDSA, works everywhere)
       |     |-- Quadrant 1 Root CA  --> DV, OV and EV intermediate CAs --> one test certificate
       |     `-- Quadrant 2 Root CA  --> DV, OV and EV intermediate CAs --> one test certificate
       `-- Quantum Track Root CA       (ML-DSA, safe against quantum computers)
             |-- Quadrant 3 Root CA  --> DV, OV and EV intermediate CAs --> one test certificate
             `-- Quadrant 4 Root CA  --> DV, OV and EV intermediate CAs --> one test certificate

It also writes the CRL files and the CA files that a web server must publish (folder publish), a manifest (what was made), and it can install the CA certificates into Windows.

 What the script does NOT do:
   * It does not make the many certificates that your servers and people need.
     Use GenerateLeafCertificate.ps1 for that (GenerateLeafCertificate-MANUAL.txt).
   * It does not publish the CRL files. You copy them to a web server (section 12).
   * It does not change your computer, except when you use -InstallTrust or the remove options.

Rules of thumb: * Run .\pki_setup.ps1 -Check first. It changes nothing. * Read the last page of the output. It lists every CA with key, validity and expiry date. * Never copy the .key files of the root CAs to other computers.

2 THE WORDS YOU NEED#

Only the words used in this manual. More words: GLOSSARY.txt.

   CA            Certificate Authority. A program or a person that signs certificates.
   Root CA       The top CA. It signs the CAs below it. Every computer must trust it.
   Intermediate  A CA below the root. It signs the certificates that servers and people use.
   Leaf          The last certificate in the chain: the one a server or a person uses.
   Chain         Leaf, then intermediate, then root. A client checks the whole chain.
   Track         A group of CAs with the same kind of key. This PKI has two tracks:
                 Classic (RSA and ECDSA) and Quantum (ML-DSA).
   Quadrant      One of four CA families. Number 1 to 4. See section 5.
   FIPS          A US standard for approved cryptography. A FIPS quadrant uses the OpenSSL FIPS
                 module. A non-FIPS quadrant does not.
   ML-DSA        A signature type that quantum computers cannot break. Also called "quantum safe".
   DV, OV, EV    Three levels of certificate. DV = domain checked. OV = organization checked.
                 EV = extended checks. Here the level only decides the policy and the validity.
   CRL           A list of certificates that are no longer good.
   PFX           One file with a certificate and its private key, protected by a password.
   Trust         "My computer believes certificates signed by this root."

3 BEFORE YOU START#

 3.1  Your computer
        Works: Windows 11 24H2 or newer (Home, Pro, Pro for Workstations, Education,
               Enterprise).
               Windows Server 2025.
               Linux with PowerShell: Ubuntu 24+, CentOS Stream 10+, RHEL 10+, Rocky 10+,
               Oracle Linux 10+, SLES 15+, openSUSE.
        Classic only: Windows Server 2022. Quadrants 3 and 4 are refused there.
        Refused (error, exit code 5): Windows 10, older Windows, macOS, and the China,
               Government, IoT and Embedded editions.
        On Linux you cannot use -InstallTrust. Section 7 shows how to trust the root by hand.
 3.2  PowerShell 7 or newer
        Not Windows PowerShell 5.1. The program name is "pwsh".
        Windows :   winget install --id Microsoft.PowerShell
        Linux   :   use the package instructions of Microsoft for your distribution.
        Check   :   pwsh -v
 3.3  OpenSSL 4
        Only OpenSSL 4.x works. OpenSSL 3.x is refused.
        Windows :   run this in an ELEVATED PowerShell (right click, Run as administrator):
                        .\Install-DevEnvironment.ps1 -Only OpenSSL,7Zip
                    Then open a NEW PowerShell window. The PATH is read when a window starts.
        Check   :   openssl version        It must print  OpenSSL 4.x.x
        If you have several OpenSSL programs, the script takes the newest 4.x by itself.
        To choose one:   .\pki_setup.ps1 -OpenSslPath "C:\path\to\openssl.exe"
        Before it makes any key, the script tests that OpenSSL can make ML-DSA keys and can load
        the FIPS module. If not, it stops at once and says why.
 3.4  The FIPS module (only for quadrants 2 and 4)
        Install-DevEnvironment.ps1 makes the file fipsmodule.cnf for you.
        Without it, build only the non-FIPS quadrants:   .\pki_setup.ps1 -Quadrant 1,3
        With another file:   .\pki_setup.ps1 -FipsModuleConfig C:\openssl\ssl\fipsmodule.cnf
 3.5  Administrator rights
        Needed only for  -InstallTrust  -ReinstallTrust  -RemoveTrust  -RemoveAllTrust  -Clean.
        The other commands run as a normal user.
 3.6  The files
        Keep these together in one project folder:
            pki_setup.ps1    agantra_pki.cnf    the folder scripts\
        agantra_pki.cnf holds your company data, URLs and policy names. Read section 4, step 4.

4 FIRST RUN, STEP BY STEP#

 Step 1. Unblock the files. Do this once, only if the project came from a zip or a download.
             Get-ChildItem -Path . -Recurse -File | Unblock-File
         If Windows says "running scripts is disabled":
             Set-ExecutionPolicy RemoteSigned -Scope CurrentUser

Step 2. Open PowerShell 7 as Administrator in the project folder.

 Step 3. Check the computer. This changes nothing.
             .\pki_setup.ps1 -Check
         Expected: every line says PASS or INFO. The last line says READY.
         If the last line says NOT READY: read the FAIL line. It names the step and the reason.
         Section 14 lists the common reasons.
 Step 4. Edit agantra_pki.cnf if you need to. You can skip this for a test.
         The important lines:
             company name, country, city          (who you are)
             [ crl_urls ] and [ ca_issuer_urls ]  (where clients will find the CRL and CA files)
             IanaPen                              (your IANA number; it may stay empty)
         For another company, do not edit this file. Make a new profile (section 9).
 Step 5. Build the PKI and install the trust in Windows.
             .\pki_setup.ps1 -InstallTrust
         This takes a few minutes. RSA 8192 keys are slow. The script prints one line per CA.
         Result: 4 quadrants on Windows 11, 2 quadrants (1 and 2) on Windows Server 2022.
 Step 6. Read the table at the end of the output. For each CA it shows the validity, the key,
         the digest, the expiry date and the common name. Save it if you must report it.
 Step 7. Check what was written. This changes nothing.
             .\pki_setup.ps1 -Verify
         Expected:  PKI is valid
         Several PKIs (companies, releases)?  .\pki_setup.ps1 -VerifyAll  checks every one, shows
         each output and ends with a PASSED / FAILED list. Exit code 0 = all passed.
         On Windows it also tells you whether each CA is in the certificate store.
 Step 8. Test it. Open Edge, Chrome or Brave. They use the Windows store.
         Use one of the test certificates on a test server (section 8).
         Firefox has its own store. Install the root there too (section 7).
 You are done. Next:   GenerateLeafCertificate-MANUAL.txt   to make real certificates.

5 WHICH QUADRANT DO I USE?#

   No.  Track    FIPS      Root key (digest)         Intermediate key         Test certificate
   ---  -------  --------  ------------------------  -----------------------  ----------------
    1   Classic  no        RSA 4096 (SHA-384)        RSA 4096 (SHA-256)       RSA 2048
    2   Classic  yes       ECDSA P-384 (SHA-384)     ECDSA P-384 (SHA-384)    ECDSA P-256
    3   Quantum  no        ML-DSA-87                 ML-DSA-87                ML-DSA-65
    4   Quantum  yes       ML-DSA-87                 ML-DSA-87                ML-DSA-65

The text in brackets is the digest that this CA uses when it signs. The Enterprise Root and the two Track Roots are RSA 8192 and sign with SHA-512.

 Which one for which job:
   Web sites that browsers open, IIS, Kestrel on Windows, Java 25
        --> quadrant 1 (RSA) or quadrant 2 (FIPS, ECDSA).
   Services on OpenSSL 3.5 or newer (nginx, Apache, Node.js, Python, curl, Kestrel on Linux),
   mutual TLS between your own systems, post-quantum tests
        --> quadrant 3 (no FIPS) or quadrant 4 (FIPS).

Why: Windows Schannel, Java 25 and all browsers do not accept ML-DSA certificates for HTTPS today. Windows 11 24H2 and Windows Server 2025 can hold them in the certificate store. The hybrid key exchange (ML-KEM) is a different thing. It works with every certificate (section 8.3).

If OpenSSL cannot make an ML-DSA key, the script STOPS. It does not quietly use a weaker key. To allow RSA instead, use -PqcFallback. Those certificates are NOT quantum safe.

This script makes EV test certificates (397 days). Use GenerateLeafCertificate.ps1 for DV and OV.

6 WHAT IS CREATED#

 6.1  The folders
      Every PKI has its own folder inside .\pki. The first PKI of Agantra is pki\pki-default-01.
          pki\pki-default-01\
            root\                  Enterprise Root:  root.crt   root.key   root.pfx
            classical\root\        Classic Track Root
            quantum\root\          Quantum Track Root
            classical\q1\{root,dv,ov,ev}\     one folder per CA, for quadrant 1
            classical\q2\ ...      quantum\q3\ ...      quantum\q4\ ...
                                   In each CA folder: <id>.crt  <id>.key  <id>.pfx  <id>.cnf
                                   <id>-chain.crt  and the CA database (index.txt, serial ...)
            leaf\                  the test certificates
            publish\               the files for the web server: root.crt, ca-bundle.crt,
                                   <name>.crt, <name>.crl, README.txt
            server\                the facts for the PKI server: server-info.json, ca-list.tsv,
                                   server.env, expected-urls.tsv, DNS-RECORDS.txt  (no keys)
            pki-manifest.json      every certificate: thumbprint, key, digest, expiry date
            telemetry.json         what the run did and how long it took
 6.2  The test certificate files (folder leaf)
      The name is <domain>-<tag>. The tag is q1-rsa2048, q2-ecdsa-p256, q3-mldsa65 or q4-mldsa65.
          .crt            the certificate only
          .key            the private key, no password. Protect it. Never send it.
          -fullchain.crt  leaf + intermediate + quadrant root + track root. Servers send this file.
          .pfx            certificate + key + chain in one file. Password: see -Password.
          -fips.pfx       FIPS quadrants only. Windows may refuse to import it. Use the .pfx.
          .sha256 .sha512 a hash file for each certificate file set. Check it with:
                          sha256sum -c <name>.sha256
          .pub, -chain.crt, .cnf   the public key, the chain without the leaf, the OpenSSL file.
      The default PFX password is  Abc12345!  . Change it with -Password for real use.
 6.3  Which file does each product need?
      Classic = quadrant 1 or 2.   Quantum = quadrant 3 or 4.
          Product                Files                       Classic   Quantum
          ---------------------  --------------------------  --------  -------
          Kestrel on Windows     .pfx                        yes       no
          IIS                    .pfx                        yes       no
          Kestrel on Linux       .pfx or PEM                 yes       yes
          nginx, Apache          -fullchain.crt and .key     yes       yes
          Node.js, Python        -fullchain.crt and .key     yes       yes
          Go, PHP                -fullchain.crt and .key     yes       not verified
          Java 25                .pfx                        yes       no
          Browsers               (the server decides)        yes       no
      Every CLIENT must trust  root.crt  (section 7).

7 TRUST THE ROOT ON EVERY DEVICE#

A device trusts your PKI when it has your root. Install ONLY pki\pki-default-01\root\root.crt. Servers send the intermediates inside the -fullchain.crt file. For many devices use the trust kit: New-PkiTrustKit.ps1 (PkiTrustKit-MANUAL.txt).

 The computer that builds the PKI:
     .\pki_setup.ps1 -InstallTrust          (or -ReinstallTrust for an existing PKI)
 Result in certlm.msc:
     Trusted Root Certification Authorities    7 certificates: Enterprise Root, 2 Track Roots,
                                               4 Quadrant Roots
     Intermediate Certification Authorities    12 certificates: all DV, OV and EV CAs
     Personal                                  the test certificate PFX files

Other devices, by hand:

     Windows        certlm.msc  ->  Trusted Root Certification Authorities  ->  Import root.crt
                    Edge, Chrome and Brave use this store.
     Firefox        Settings -> Privacy and Security -> Certificates -> View Certificates ->
                    Authorities -> Import. Tick "Trust this CA to identify websites".
                    Or about:config  security.enterprise_roots.enabled = true  (uses the OS store).
     Ubuntu         sudo cp root.crt /usr/local/share/ca-certificates/agantra-root.crt
                    sudo update-ca-certificates
     RHEL family    sudo cp root.crt /etc/pki/ca-trust/source/anchors/agantra-root.crt
                    sudo update-ca-trust
     SUSE           sudo cp root.crt /etc/pki/trust/anchors/agantra-root.crt
                    sudo update-ca-certificates
     macOS          sudo security add-trusted-cert -d -r trustRoot \
                        -k /Library/Keychains/System.keychain root.crt
     Android        Copy root.crt to the phone. Settings -> Security -> Install a certificate ->
                    CA certificate. Apps for Android 7 and newer ignore user CAs by default.
     Chrome on Linux   It reads the NSS database:
                    sudo apt install libnss3-tools
                    certutil -d sql:$HOME/.pki/nssdb -A -t "C,," -n AgantraRoot -i root.crt
     UC Browser, QQ Browser   Not verified. They may use their own store. Test one page first.

Programs that do not use the OS store:

     Node.js    set NODE_EXTRA_CA_CERTS=C:\path\root.crt
     Python     ssl.create_default_context(cafile="root.crt")   or   SSL_CERT_FILE=root.crt
     PHP        'cafile' => 'root.crt' in the stream context, or openssl.cafile in php.ini
     Java 25    keytool -importcert -trustcacerts -alias agantra-root -file root.crt -cacerts
     Go, .NET   use the OS store.

8 USE THE CERTIFICATES IN YOUR SERVERS#

 8.1  nginx and Apache
      Do not write the configuration by hand. Create-WebServerConfig.ps1 (or .sh) writes it for
      you from your leaf certificate. See Create-WebServerConfig-MANUAL.txt.
 8.2  Windows
      Kestrel (.NET) and IIS use the Classic .pfx.
          Import-PfxCertificate -FilePath .\nextmantra.com-q1-rsa2048.pfx `
              -CertStoreLocation Cert:\LocalMachine\My -Password (Read-Host -AsSecureString)
      In IIS Manager: Site -> Bindings -> https -> choose the certificate.
      The default certificate names include localhost and 127.0.0.1. So https://localhost:5001
      is trusted once the root is installed. Keep the PFX password out of source control. In
      development use:   dotnet user-secrets
 8.3  The key exchange rules (all products)
      The hybrid key exchange X25519MLKEM768 comes from the TLS library, not from the certificate.
      To keep it working:
        * Keep TLS 1.3 turned on. It is the only protocol that carries the hybrid group.
        * Do not write a fixed list of ciphers or groups, unless it contains the hybrid group.
        * Use OpenSSL 3.5 or newer in nginx, Apache, Node.js and Python.
 8.4  Test the key exchange
      With an OpenSSL 3.5 or newer client:
          "" | openssl s_client -connect app.example.com:443 -servername app.example.com `
               -CAfile pki\pki-default-01\root\root.crt -groups X25519MLKEM768
      (Linux: openssl s_client ... < /dev/null)
      You should see:
          Negotiated TLS1.3 group: X25519MLKEM768     hybrid ML-KEM was used
          Verification: OK                            the chain is trusted
      For a Quantum certificate you also see:  Peer signature type: ML-DSA-65
      If the group line shows only X25519: the server or its OpenSSL is too old, TLS 1.3 is off,
      or the group list was limited.
      On Windows,  .\pki_setup.ps1 -Verify  asks Windows itself whether it accepts every chain.
 8.5  Mutual TLS
      The test certificates carry both serverAuth and clientAuth. The same certificate can be
      a server certificate and a client certificate. The other side must trust root.crt.
 8.6  Copy a certificate to a Linux server by hand
      Copy only what the server needs: the leaf files and root.crt. NEVER copy the .key files of
      the CAs (the folders root, classical and quantum).
      On Windows (the OpenSSH client is part of Windows 11):
          $h = "user@server.example.com"
          scp pki\pki-default-01\root\root.crt                    "${h}:/tmp/agantra-root.crt"
          scp pki\pki-default-01\leaf\example.com-q1-rsa2048-fullchain.crt   "${h}:/tmp/"
          scp pki\pki-default-01\leaf\example.com-q1-rsa2048.key             "${h}:/tmp/"
      On the server (Ubuntu, as root or with sudo):
          cp /tmp/agantra-root.crt /usr/local/share/ca-certificates/agantra-root.crt
          update-ca-certificates
          mkdir -p /etc/pki/agantra
          mv /tmp/example.com-q1-rsa2048-fullchain.crt /etc/pki/agantra/
          mv /tmp/example.com-q1-rsa2048.key /etc/pki/agantra/
          chmod 644 /etc/pki/agantra/*.crt
          chmod 600 /etc/pki/agantra/*.key
      Test on the server itself:
          curl --resolve example.com:443:127.0.0.1 https://example.com/ -I
      The host name of the server must be in the certificate (the SAN). If it is not, edit
      [ leaf_san ] in agantra_pki.cnf, or use -Domain, and build again.
      For a whole server (CRL, OCSP, time stamping) use New-PkiServerPackage.ps1.

9 MANY PKIs, RELEASES AND THE NoCR VARIANT#

 9.1  One PKI for each company  (profiles)
      A profile is a file  <short>_pki.cnf  next to the scripts. agantra_pki.cnf is the default.
      For another company:
          .\New-PkiConfig.ps1                   asks for the company data, writes raksaka_pki.cnf
          .\pki_setup.ps1 -Pki raksaka -InstallTrust
          .\pki_setup.ps1 -ListPki              lists all PKIs. These names are the values for -Pki.
      Every script that works on a PKI has the same -Pki option. Tab completion shows the names.
      Full text: PkiProfiles-MANUAL.txt.
 9.2  Releases
      Run pki_setup.ps1 again and it builds the NEXT release. It never changes an old one.
          pki\pki-default-01    release 1
          pki\pki-default-02    release 2  (a new Enterprise Root and everything below it)
      Old certificates keep working, because their CAs still exist.
          .\pki_setup.ps1 -InstallTrust            next free release
          .\pki_setup.ps1 -Release 3               exactly release 3. If it exists, nothing
                                                   happens and the script says "R3 already exists".
          .\pki_setup.ps1 -Clean -Release 3        replace release 3 on purpose
      "Exists" means: the folder exists OR the certificates are in the Windows store.
      Names: release 1 has no suffix. From release 2 every CA name ends with " R2", " R3" ...
          Agantra Root CA G1          release 1
          Agantra Root CA G1 R2       release 2
 9.3  The NoCR variant
      NoCR means "no CA revocation information". The CA certificates have no CRL, OCSP or CA
      Issuers address. Some programs wait a long time when such an address is not reachable (for
      example signatures in Microsoft Office). NoCR avoids that.
          .\pki_setup.ps1 -NoCaRevocationInfo -InstallTrust
      Folder:  pki\pki-default-nocr-01.   Names get " (NoCR)":  Agantra Root CA G1 (NoCR)
      NoCR is a SEPARATE set of roots with its own keys. Leaves of the normal PKI do not chain to
      it. To switch: remove the trust of the normal PKI, install the NoCR PKI, issue the leaves
      again. Leaves keep their own CRL and OCSP addresses. Add -NoRevocationInfo to the leaf
      generators to remove them too.
 9.4  Which release do the other scripts use?
          (nothing)             the LATEST release of the normal PKI
          -Release N            release N. If it does not exist, the latest one is used and
                                a warning says so.
          -NoCaRevocationInfo   the NoCR PKI
          -PkiRoot <folder>     exactly that folder
      -Verify, -ReinstallTrust and -RemoveTrust use exactly the release you name. If several
      releases are installed, -RemoveTrust needs -Release N, so nothing is removed by accident.
 9.5  A kit holds one PKI
      A DevKit or a server package holds ONE PKI: the latest release, unless you choose another.
      Make one kit for each release.

10 NAMES OF THE CAs#

 10.1  The default names
          Enterprise Root     Agantra Root CA G1
          Track Roots         Agantra Classic Root CA G1        Agantra PQC Root CA G2
          Quadrant Roots      Agantra Classic Q1 Root CA G1     (quadrant 1, no FIPS)
                              Agantra Classic Q2 Root CA G1     (quadrant 2, FIPS)
                              Agantra PQC Q1 Root CA G2         (quadrant 3, no FIPS)
                              Agantra PQC Q2 Root CA G2         (quadrant 4, FIPS)
          Intermediates       Agantra <EV|OV|DV> <algorithm> <G1|G2> CA
                              Example:  Agantra OV ECDSA-P384 FIPS G1 CA
      G1 = the Classic track. G2 = the Quantum track.
      In names, a quadrant is only Q1 (no FIPS) or Q2 (FIPS), in both tracks. The track word and
      G1 / G2 tell them apart. The numbers 1 to 4 stay in -Quadrant and in the folders.
 10.2  See the names before you build
          .\pki_setup.ps1 -ShowNames
 10.3  Change the names
      The names come from templates. Put your changes in agantra_pki.cnf, section [ ca_names ].
      Your changes then survive an update of the scripts. Remove the "#" of the lines to change.
          [ ca_names ]
          Prefix              = Agantra Inovatif
          QuantumLabel        = PQC
          SlugPrefix          = agantra          (the start of the CRL and CA file names)
          GenEnterprise = G1   GenClassic = G1   GenQuantum = G2
          EnterpriseRoot      = {Prefix} Root CA {Gen}
          ClassicTrackRoot    = {Prefix} Classic Root CA {Gen}
          QuantumTrackRoot    = {Prefix} {QuantumLabel} Root CA {Gen}
          ClassicQuadrantRoot = {Prefix} Classic Q{N} Root CA {Gen}
          QuantumQuadrantRoot = {Prefix} {QuantumLabel} Q{N} Root CA {Gen}
          Intermediate        = {Prefix} {Level} {Algorithm} {Gen} CA
      Allowed tokens: {Prefix} {QuantumLabel} {Gen} {N} {Level} {Algorithm} {Track} {Id}
      Rules. The script stops and says why when you break one:
        * A name has at most 64 characters.
        * Every CA has a different name.
        * Only the tokens above.
      A name is fixed when the CA is made. To change it later you must build a new PKI (-Clean).
      The OU of each layer comes from OU_Root, OU_Track, OU_Quadrant and OU_Intermediate in
      the section [ pki_settings ].

11 CLASSIC PKI ONLY, AND A PUBLIC CA ROOT#

 11.1  Classic PKI only
          .\pki_setup.ps1 -ClassicPKI -InstallTrust
      Builds only: Enterprise Root, Classic Track Root, Quadrant 1 Root, DV, OV and EV
      intermediates, and the quadrant 1 test certificate. RSA only. No FIPS module. No ML-DSA.
      It is the smallest PKI and the most compatible one. Use it under a public CA.
      You cannot combine -ClassicPKI with -Quadrant.
 11.2  Let a public CA sign the Enterprise Root
      DigiCert, GlobalSign or Sectigo can sign your root. Clients that trust the public root then
      trust your PKI without installing anything. The script makes the files and checks the
      answer. The public CA does the signing.
          1.  .\pki_setup.ps1 -ClassicPKI -EnterpriseRootCsr -ExternalCa DigiCert `
                  -EnterpriseRootKeyBits 4096
              It writes pki\...\root\root.csr and external-request.txt (what to ask the CA).
          2.  Send root.csr to the CA. You receive the signed certificate and the chain.
          3.  .\pki_setup.ps1 -ImportEnterpriseRoot signed.pem -ExternalChain chain.pem `
                  -InstallTrust
          4.  .\pki_setup.ps1 -Verify
      Already have a PKI? Cross-sign it instead:
          .\pki_setup.ps1 -CrossSignCsr
          .\pki_setup.ps1 -ImportCrossCert cross.pem -ExternalChain chain.pem
      Know this before you start:
        * The public CA decides the key size, the path length (this PKI needs 3 or more), the
          key usage, name constraints and the validity. It can refuse RSA 8192.
        * Every CA below the root is shortened so that it ends before the public certificate.
        * Public TLS certificates are limited to 398 days.
        * Never use -Clean together with -ImportEnterpriseRoot. It deletes the key.
      The full text is in PUBLIC-CA-ENTERPRISE-ROOT.txt.

13 REMOVING A PKI#

Windows needs an Administrator PowerShell for the certificate stores. Linux removes only files.

   .\pki_remove.ps1 -List                    what is installed (release, variant, folder, expiry)
   .\pki_remove.ps1 -Release 2               take release 2 out of Windows. Files stay.
   .\pki_remove.ps1 -Release 2 -DeleteFiles  and delete its folder
   .\pki_remove.ps1 -Release 1 -NoCaRevocationInfo -DeleteFiles     the NoCR release
   .\pki_remove.ps1 -Pki raksaka -All        one company only
   .\pki_remove.ps1 -All                     every release and both variants of one company
   .\pki_setup.ps1 -RemoveTrust -Release 2   same as pki_remove (by thumbprint and by name)
   .\pki_setup.ps1 -RemoveAllTrust           EVERY PKI of EVERY company: all certificates from
                                             Windows, and the whole pki folder is deleted
   .\pki_setup.ps1 -Clean -InstallTrust      remove the release being built, then build it again

The script asks "Yes?" before it removes anything. -Yes skips the question. A certificate that is already gone is ignored. If a program holds the folder, the script retries and then names the program. -Clean and -RemoveAllTrust do NOT touch the folder leafcerts: leaf certificates of the old PKI do not chain to a new PKI. The script warns when such leaves exist. On other systems delete the root file you copied (section 7) and run update-ca-certificates, update-ca-trust or the command for your system again.

15 LIMITS YOU MUST KNOW#

  • Private PKI. Every client must install the root. No browser shows the EV company name for a private root.
  • ML-DSA certificates are not accepted for HTTPS by Windows Schannel, Java 25 and the browsers today. They work in the Windows 11 store and with OpenSSL 3.5 or newer. This is the status of mid-2026. Test on your builds.
  • ML-DSA signatures are large (about 3.3 KB for ML-DSA-65, 4.6 KB for ML-DSA-87). A full chain is tens of KB. Some proxies and servers limit the header size.
  • Dates after 2038 can fail on 32 bit systems.
  • RSA 8192 CA keys are slow. Some TLS stacks restrict P-521. Test certificates use P-256.
  • UC Browser and QQ Browser are not verified.
  • The CRL, OCSP and CA Issuers URLs help only when the files of the folder publish are served there.
  • OpenSSL 4.0 has short support (about May 2027). OpenSSL 3.5 LTS runs to 2030. Only this script needs 4.x. The servers that use the certificates can run 3.5 or newer.
  • A public CA signs only what it accepts. It may refuse RSA 8192 or P-521, limit the path length, ask for an HSM, add name constraints and limit the validity. Signing is not automated. It was tested with a stand-in CA, not with DigiCert, GlobalSign or Sectigo.
  • The full list: PKI-Design-with-FIPS-and-PQC.txt, section 9.

17 WHAT WAS TESTED, WHAT WAS NOT#

Tested on Linux with a real OpenSSL 4.0.3 and the real FIPS provider: the whole PKI, ML-DSA, -Check, -Verify, and a live TLS 1.3 handshake with an ML-DSA leaf.
