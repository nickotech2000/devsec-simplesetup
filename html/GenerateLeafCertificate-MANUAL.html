1 WHAT THE SCRIPT DOES

pki_setup.ps1 builds the CAs and one default EV leaf per quadrant. GenerateLeafCertificate.ps1 issues every other leaf certificate from the intermediates (DV, OV or EV; Classic or Quantum; FIPS or non-FIPS).

 ONE RUN, EVERYTHING
      .\GenerateLeafCertificate.ps1 -DnsName www.example.com
   makes SEVEN certificates, one for EVERY purpose (TLS in THREE variants: server only, client only,
   server + client; code signing, S/MIME, time stamping, OCSP signing), each in EVERY format (PEM,
   DER, CER, CERT, P7B, RFC 7468, PFX), validates all of them, and writes them to <script
   folder>\leafcerts\www.example.com\<purpose>\
   (next to the scripts, NOT inside the pki folder).

Every certificate has its own purpose and its own key (the three TLS certificates too). Code signing and TLS are NOT mixed in one certificate (that is the usual practice, and RFC 3161 requires a time stamping certificate to carry that purpose alone). To get ONE certificate with several purposes anyway, give -Purpose (section 4).

It uses the shared modules of the scripts folder (set Library), the same generator as pki_setup.ps1, and the naming configuration of agantra_pki.cnf [ leaf_names ]. Nothing it does is irreversible: a folder that exists is never touched (a new one with the date and time is made), and

a failed run removes its own new folder.#

2 WHAT YOU NEED, AND THE OPENSSL CHECK

 * PowerShell 7+, the PKI made by pki_setup.ps1 (folder .\pki, or -PkiRoot).
 * OpenSSL 4.x WITH the FIPS module and native ML-DSA. Before anything is made the script checks and
   prints:
       OPENSSL READINESS  (4.x with FIPS and quantum-safe support)
       [PASS] OpenSSL 4.x            [PASS] ML-DSA (default provider)
       [PASS] FIPS provider          [PASS] ML-DSA (FIPS provider)
   What THIS run needs and is missing STOPS the script (a FIPS leaf needs the FIPS provider, a
   Quantum leaf needs ML-DSA). What it does not need is a warning. Both suggest the fix: run your
   bootstrap, elevated, OpenSSL only:
       .\Install-DevEnvironment.ps1 -Only OpenSSL,7Zip
   then open a NEW PowerShell window. OpenSSL 3.x is refused. Check only:   .\GenerateLeafCertificate.ps1 -Check
 * A quadrant the PKI does not have (built with -ClassicPKI or -Quadrant) is refused with the way to

build it.#

4 PURPOSES: ONE CERTIFICATE FOR EACH

 ServerAuth       TLS server.        EKU serverAuth (1.3.6.1.5.5.7.3.1).
                  Key usage digitalSignature (+ keyEncipherment for RSA).   SAN: DNS names / IPs.   CN: first DNS name.
 ClientAuth       TLS client, mutual TLS.   EKU clientAuth (1.3.6.1.5.5.7.3.2).
                  Key usage digitalSignature.   SAN: DNS names / IPs.   CN: first DNS name.
 ServerClientAuth TLS server AND client in ONE certificate.   EKU serverAuth + clientAuth.
                  Key usage as ServerAuth.   SAN and CN as ServerAuth.   (Section 15.)
 CodeSigning      Code signing.   EKU codeSigning (1.3.6.1.5.5.7.3.3).
                  Key usage digitalSignature.   SAN: none.   Subject: C=EE, ST=Tallinn, L=Tallinn,
                                                             O=<company>, CN=<company>
                  (-CodeSigningCompany; empty = the organization, default Agantra Inovatif OU).
                  Section 16.
 EmailProtection  S/MIME.   EKU emailProtection (1.3.6.1.5.5.7.3.4) AND clientAuth
                            (1.3.6.1.5.5.7.3.2) - every e-mail certificate.
                  Key usage digitalSignature, nonRepudiation (+ keyEncipherment for RSA).
                  SAN: e-mail address.   CN: the e-mail address.
 TimeStamping     RFC 3161 time stamping.   EKU timeStamping (1.3.6.1.5.5.7.3.8), CRITICAL and the
                                            only purpose.
                  Key usage digitalSignature.   SAN: none.   CN: "<company> Time Stamping".
                  Default: Quadrant 1 (Classic, non-FIPS), 1825 days, policy OID
                  1.3.6.1.4.1.67096.1.4 (-TimestampQuadrant, -TimestampPolicyOid, -TimestampDays).
                  Not a special certificate type: this IS the TSA certificate.
 OcspSigning      OCSP responder.   EKU OCSPSigning (1.3.6.1.5.5.7.3.9) + no-check extension
                                    (1.3.6.1.5.5.7.48.1.5).
                  Key usage digitalSignature.   SAN: none.   CN: "<company> OCSP Responder".
 DocumentSigning      (5.3.7, NOT in the set: ask with -Purpose)   Document signing for Microsoft
                                                                   Office / Office 365 / Microsoft
                                                                   365 and other office programs
                  (LibreOffice ...).   EKU 1.3.6.1.4.1.311.10.3.12 (Microsoft Document Signing).   Key usage digitalSignature + nonRepudiation.   SAN: none.   CN: the company.
 DocumentSigningAdobe (5.3.7, NOT in the set)   Document signing for Adobe Acrobat / Reader (PDF).   EKU 1.2.840.113583.1.1.5 (Adobe Authentic Documents Trust).   Same key usage / SAN / CN.
                  Both in ONE certificate: -Purpose DocumentSigning,DocumentSigningAdobe.   (Acrobat only shows a green "trusted" mark when the CA is in its trust list or you add it.)
 Custom EKU   (5.3.7) any dotted OID in the -Purpose list, for example -Purpose
              1.3.6.1.4.1.99999.1.2 or -Purpose ServerAuth,1.3.6.1.4.1.99999.1.2. Written into
              extendedKeyUsage as
                  it is (digits and dots, first arc 0, 1 or 2, at least three arcs; anything else is
                  refused with the list of valid names) and checked in the finished certificate. The
                  file names get oid-1-3-6-... in them. No program trusts a custom OID until it is
                  told to.
 The set     no -Purpose (or -AllPurposes) = all SEVEN (DocumentSigning / DocumentSigningAdobe are
             not in it). -ExcludePurpose TimeStamping,OcspSigning leaves some out; -ExcludePurpose
             ServerClientAuth drops the combined TLS certificate and keeps the two separate ones.
 TLS         -Purpose ServerAuth,ClientAuth    THREE certificates: server only, client only, server
                                               + client.
             -Purpose ServerClientAuth         ONE certificate with both EKUs.
 One certificate with several other purposes
             -Purpose ServerAuth,EmailProtection    ONE certificate carrying exactly these.
             TimeStamping and OcspSigning must stand alone. Cannot be combined with -AllPurposes /
             -ExcludePurpose.
 Names       ServerAuth, ClientAuth and ServerClientAuth use -DnsName / -IpAddress / -EmailAddress,

             -EmailAddress, else the contact e-mail (-ContactEmail, default info@nextmantra.com).
             The other three have no SAN. -CommonName replaces the CN of the TLS certificates and is
             the base ("<base> Code Signing") of the others; the base defaults to the company name.
 Forced up   Code signing: RSA >= 4096, ECDSA >= P-384, ML-DSA >= 65, SHA-256 or stronger. A note
             says so.
 Every certificate of a set is validated on its own with the OpenSSL purpose that fits (sslserver,

sslclient, smimesign, timestampsign, ocsphelper; code signing has none) before the script says OK.#

5 FORMATS: ALL OF THEM, IN ONE GO

-Format defaults to ALL: every certificate is written in every format below at once. Each file is read back by OpenSSL after it is written (the RFC 7468 file is also checked for its strict form).

 Format    File                  What it is                                            Used by
 --------  --------------------  ----------------------------------------------------  ---------------------------------
 (always)  <stem>.crt            PEM text, the certificate                             nginx, Apache, most tools
 (always)  <stem>.key            PKCS#8 PEM private key (RFC 7468 label PRIVATE KEY)   every server; keep it private
 (always)  <stem>.key         private key, PKCS#8 PEM (-----BEGIN PRIVATE KEY-----), LF line
                              endings, one per certificate / EKU
 (always)  <stem>.pub         public key of that key pair, PEM (SubjectPublicKeyInfo, -----BEGIN
                              PUBLIC KEY-----)
 (always)  <stem>.pub.der     the same public key in DER
 (always)  <stem>-fullchain.crt  leaf + intermediate + quadrant root + track root     nginx ssl_certificate, Apache
 (always)  <stem>-chain.crt      the same without the leaf                             ssl_trusted_certificate, mTLS
 PEM       <stem>.pem            PEM text, the certificate (extension .pem)            Linux tools, OpenSSL
 DER       <stem>.der            binary ASN.1 DER                                      Java, appliances, firmware
 CER       <stem>.cer            DER binary, the Windows default export                double-click in Windows
 CERT      <stem>.cert           PEM text (extension .cert)                            Node.js / Go conventions
 P7B       <stem>.p7b            PKCS#7, PEM armor: leaf + chain, no key               Windows and Java import
 RFC7468   <stem>.rfc7468.pem    strict PEM: 64-character lines, LF only, nothing      tools that parse PEM strictly
                                 around the block
 PFX       <stem>.pfx            PKCS#12: key + leaf + chain, password (-Password)     Kestrel, IIS, Windows import
           <stem>-fips.pfx       FIPS-conformant PKCS#12 (FIPS leaves only)            FIPS-validated software

-Format PEM,DER selects some. -LegacyPfx makes a 3DES / SHA-1 PFX for very old software. convert-formats.ps1 in every folder is clean PowerShell with the exact OpenSSL commands to convert THAT certificate between every format (and key formats: PKCS#8 DER, encrypted, traditional RSA / EC), with its real file names and OpenSSL path. Run it from the folder; it asks for the PFX

password.#

7 LEVEL, QUADRANT, KEYS, VALIDITY, POLICIES

 Level / quadrant  -DV | -OV | -EV (default EV).  -Classic = quadrant 1, -Classic -FIPS = 2,
                   -Quantum = 3, -Quantum -FIPS = 4 (internal numbers). In NAMES (CAs and leaf file
                   names) Q1 = non-FIPS, Q2 = FIPS in both tracks: Classic Q1 / Q2, Quantum Q1 / Q2
                   (a Quantum FIPS leaf is ...-ev-q2-mldsa65.crt). Browsers and Windows servers:
                   Classic. OpenSSL services and mutual TLS: Quantum (or Classic).
 Subject           DV: CN only. OV: C ST L street postalCode O OU CN + name / emailAddress /
                   telephoneNumber. EV: OV + serialNumber, businessCategory, jurisdictionC / ST / L,
                   and -Duns (organizationIdentifier = DUNS+<n>, a private convention). Values:
                   command line, else [ subject_ev ] / [ subject_ov ].
 Keys (floors are REJECTED, not corrected)
                   RSA 2048 | 3072 | 4096 | 8192   ECDSA P-256 | P-384 | P-521   ML-DSA 44 | 65 | 87
                   Defaults: quadrant 1 RSA 2048, 2 ECDSA P-256, 3 / 4 ML-DSA-65. Hash sha256 |
                   sha384 | sha512 (the issuer's by default); SHA-1, SHA-224, MD5 rejected.
 Validity          EV 397 days (the maximum, for every purpose), OV 3 years, DV 5 years, or -Days.
                   Never longer than the issuer.
 Policies          The level OID (EV 2.23.140.1.1, OV 2.23.140.1.2.2, DV 2.23.140.1.2.1), [
                   policy_oids ] / [ iana_pen ], and -Policy "OID" or "OID|https://cps.url". A

policy the issuing CA does not carry is reported.#

8 UNBLOCK AND UNLOCK (EVERY MAIN SCRIPT)

 Every main script of this project (pki_setup.ps1, GenerateLeafCertificate.ps1, and the transport
 script of Phase C) has the same mechanism:
   UNBLOCK   removes the Windows "downloaded from the Internet" mark (Zone.Identifier) from every
             file.
   UNLOCK    removes the Read-only attribute from every file AND folder.
   Both work on the script folder and everything below it, children and recursive, hidden items
   included.
 AUTOMATIC   The STANDARD BOOTSTRAP at the top of the script does it at every start, BEFORE any
             other script is loaded (a blocked script cannot be loaded). The folders include
             leafcerts when it is next to the scripts. After a run the new leaf folder is unblocked
             and unlocked as well.
 -Unblock    .\GenerateLeafCertificate.ps1 -Unblock      (and  .\pki_setup.ps1 -Unblock)
             processes the script folder, the pki folder and the leaf folder, prints how many files
             were unblocked and how many items unlocked, lists the programs that hold files open
             there (Windows Restart Manager) and stops. Nothing is killed: close the listed program
             (Explorer window, editor, shell).
 First time  A script that is blocked the very first time cannot run its own bootstrap; run once:
                 Get-ChildItem -Path . -Recurse -File | Unblock-File
 On Linux and macOS only the Read-only part applies (there is no Internet mark).
 NOT done by the scripts: they never change the access rights (ACLs) of a key file. Protect pki\ and

leafcerts\ yourself (owner only) on a shared machine.#

9 TLS: tls-guidance.txt

 Written in the ServerAuth and ClientAuth folders, tailored to the profile of the certificate:
   Classic non-FIPS  TLS 1.3 + 1.2; AES-256-GCM, ChaCha20-Poly1305, AES-128-GCM;
                     groups X25519MLKEM768, X25519, P-256, P-384.
   Classic FIPS      the same without ChaCha20 and X25519; groups SecP256r1MLKEM768,
                     SecP384r1MLKEM1024, P-256, P-384.
   Quantum (ML-DSA) TLS 1.3 only; for OpenSSL 3.5+ servers and mutual TLS.
   HTTP/2: ALPN h2.   HTTP/3: QUIC, UDP 443, TLS 1.3, Alt-Svc header.
 With settings for nginx, Apache httpd, Kestrel, Node.js and Go, and the s_client command that
 proves the handshake. Proven here on OpenSSL 4.0.3 (TLS 1.3, hybrid key exchange, Verification OK):
 RSA, ECDSA P-384 FIPS and ML-DSA-65 FIPS leaves. Cipher and group names depend on your server
 build: verify on your server. Details: design file, 15.6.

12 LIMITS YOU MUST KNOW

  • Tested on Linux with OpenSSL 4.0.3 and the real FIPS provider. NOT tested: -InstallPfx and everything that touches the Windows stores, the Windows "Internet mark" part of the unblock (it uses Unblock-File), and the server settings of tls-guidance.txt in your nginx / Apache / Kestrel versions.
  • ML-DSA certificates (-Quantum): Windows Schannel (Kestrel / IIS on Windows), Java 25 and the browsers do not accept them for HTTPS today. Use Classic leaves there.
  • Private PKI: wildcard and internal names are allowed; a public CA would refuse some. EV certificates: 397 days at most.
  • -Duns is a private convention (organizationIdentifier = DUNS+<n>); EV here is the policy and the subject fields, not a browser EV badge.
  • Mixing purposes in one certificate (-Purpose) is allowed except TimeStamping / OcspSigning, but a warning recommends separate certificates when code signing is combined with TLS or S/MIME.
  • The OCSP certificate is a responder certificate for YOUR OCSP responder software; this PKI does not run one.
  • leafcerts\ is never deleted by pki_setup.ps1 (-Clean, -RemoveAllTrust). Leaves of a replaced PKI stay until you delete them; pki_setup warns when it finds them.

 THE THREE TLS CERTIFICATES
 Whenever ServerAuth and ClientAuth are both wanted, the run makes THREE certificates, each with its
 own key and its own folder:
      serverauth\                 EKU serverAuth                  a TLS server (a web server, an
                                                                  API, a database)
      clientauth\                 EKU clientAuth                  a TLS client (a browser identity,
                                                                  a service that calls another:
                                                                  mutual TLS)
      serverauth-clientauth\      EKU serverAuth + clientAuth     a service that is both: a server
                                                                  for some peers, a client for
                                                                  others
 They carry the same names (DNS, IP, e-mail) and the same subject; only the EKU (and so the use)
 differs. Why three: a strict server or client may refuse a certificate whose EKU is wider than the

 accepted where either role is needed. Keep the key of each in the place that needs it; do not share
 one key.

16 CODE SIGNING SUBJECT AND QUADRANT NAMES (4.9.2)

 CODE SIGNING SUBJECT   (-CodeSigningCompany, alias -CodesignCompany)
 Every code signing certificate has a short subject, at every level (DV, OV, EV):
      C = EE     ST = Tallinn     L = Tallinn     O = <company>     CN = <company>
   -CodeSigningCompany "Example Ltd"   CN = O = Example Ltd
   (empty)                             CN = O = the organization: -Organization or [ subject_ov ] O,
                                       default Agantra Inovatif OU
   -Country / -State / -Locality       change C, ST and L (otherwise the cnf, then EE / Tallinn /
                                       Tallinn)
 Nothing else is written: no OU, street, postal code, contact fields, and at -EV none of the EV-only
 fields (serialNumber, businessCategory, jurisdiction*). The EV policy, the validity of the level
 and the issuer (the EV intermediate for -EV) are unchanged. The company name may have at most 64
 characters (it is CN and O); a longer name stops the run before a file is written. -CommonName does
 not apply to code signing (it still applies to the TLS certificates and is the base of the CN of
 Time Stamping and OCSP signing). In a set the code signing certificate gets this subject while the
 others keep theirs. The folder of a single code signing certificate is named after the company.
 This is not an "EV code signing" subject in the sense of the CA/B Forum (that needs serialNumber,
 jurisdiction and businessCategory): it is for your own lab and signing scripts, installers and
 drivers inside your organization.
 QUADRANT NUMBERS IN NAMES
 Quadrant numbers 1..4 stay in the parameters, the issuer ids (q3-ev ...) and the folders. In NAMES
 the number is Q1 = non-FIPS and Q2 = FIPS in both tracks. So the CAs are called Classic Q1 /
 Classic Q2 / Quantum Q1 / Quantum Q2 and, since 4.9.2, the files of a leaf too:
      -Classic              quadrant 1   www.example.com-ev-q1-rsa2048.crt
      -Classic -FIPS        quadrant 2   www.example.com-ev-q2-ecdsa-p256.crt
      -Quantum              quadrant 3   www.example.com-ev-q1-mldsa65.crt      (before 4.9.2: q3)
      -Quantum -FIPS        quadrant 4   www.example.com-ev-q2-mldsa65.crt      (before 4.9.2: q4)
 The algorithm in the name tells Classic and Quantum apart. Leaves made before 4.9.2 keep their file

names. Details: pki_setup.ps1 -ShowNames.#

 4.9.3  KEY PAIR FILES AND LINE ENDINGS
   * Every certificate (every purpose folder) has its key pair: <stem>.key (private, PKCS#8) and
     <stem>.pub / <stem>.pub.der (public).
   * All PEM files are LF-only, no BOM. A CRLF key makes nginx/OpenSSL 3.5+ on Linux fail with
     "PEM_read_bio_PrivateKey() failed (SSL: error:1E08010C:DECODER routines::unsupported:No
     supported data to decode)".
     Files made by older versions: on the Linux host   sed -i 's/\r$//' <stem>.key <stem>-fullchain.crt <stem>.crt
     (and never copy PEM files with a tool that converts line endings; keep the key 640
     root:www-data or 600).

17 NO CRL / NO OCSP IN THE CERTIFICATES (4.9.5)#

 -NoCrl             no CRL distribution point (crlDistributionPoints) in ANY certificate this run
                    makes: the whole set, or the single certificate.
 -NoOcsp            no OCSP URL (the OCSP method of Authority Information Access). The caIssuers URL
                    stays.
 -NoRevocationInfo  both.
 Same switches in GeneratePersonLeafCertificate.ps1 and GenerateOffice365LeafCertificate.ps1
 (4.9.4); the Ubuntu twin has --no-crl / --no-ocsp / --no-revocation-info.
 WHY    A client that cannot reach the CRL / OCSP host of a private PKI reports an error: Word /
        Excel "cannot connect to the revocation server", a TLS client "unable to get certificate
        CRL", an offline build agent that waits for a time-out. A certificate without the URL has
        nothing to fetch.
 COST   The client can no longer learn that the certificate was revoked: it accepts it until it
        expires. The certificate stays in the CA database; PkiRevocation.ps1 revokes it and the CRL
        lists it, but nobody reads the CRL. Use it for development, Office and offline systems - not
        for a certificate that must be revocable.
 CHECK  The finished certificate is read back (Test-PkiLeafResult): a certificate that still has what you left out is an error. leaf-info.json records
        "revocationInfo": { "crlDistributionPoints": true|false, "ocsp": true|false }.
 EXAMPLES
      .\GenerateLeafCertificate.ps1 -OV -DnsName www.example.com -NoRevocationInfo          the whole set of 7 certificates without CRL and OCSP
      .\GenerateLeafCertificate.ps1 -EV -DnsName api.example.com -Purpose ServerAuth -NoCrl     keeps the OCSP URL
      .\GenerateLeafCertificate.ps1 -OV -AddDevelopmentSAN -Purpose EmailProtection -NoRevocationInfo
 Tested on a fresh build: -OV -NoRevocationInfo (7 certificates: no CRL distribution point, no OCSP,

caIssuers kept), -EV -NoCrl -AddDevelopmentSAN (OCSP kept, no CRL).#

HASH FILES (6.3.6)#

 For every certificate file set, the script writes hash files next to the files:
   <name>.sha256    <name>.sha512
 Each line is "<hash>  <file name>", so you can check them with:   sha256sum -c <name>.sha256
 Use -HashFile (PowerShell) or --hash-file (shell) to choose other hashes, for example sha384.
 The hash files only show that a file was not changed or damaged. They do not replace the signature.
