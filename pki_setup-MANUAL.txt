====================================================================================================
 1  WHAT THE SCRIPT DOES
====================================================================================================
 pki_setup.ps1 builds a private PKI in the folder .\pki:

     Enterprise Root  ->  Track Roots (Classic, Quantum)  ->  the four Quadrant Roots
                      ->  DV / OV / EV intermediates      ->  one default EV leaf per quadrant

 It also writes the CRL and CA-issuer files (pki\publish), a manifest, and can install the CA
 certificates into the Windows certificate stores.

 "Quantum" in this PKI means: the whole Quantum track (Quantum Track Root, Quantum Q1 and Q2 roots,
 intermediates and leaves, FIPS and non-FIPS) is signed with the post-quantum algorithm ML-DSA
 (roots and intermediates ML-DSA-87, leaves ML-DSA-65). Only the Enterprise Root, which anchors both
 tracks, is RSA 8192. The Classic track uses RSA (Q1) and ECDSA (Q2).

 WHERE ML-DSA CERTIFICATES WORK TODAY (mid-2026, test on your builds):
   * Windows 11 24H2+ and Windows Server 2025 (updated): certificate store and chain validation - YES.
     -InstallTrust installs every Quantum root, intermediate and leaf there.
   * Windows TLS (Schannel: Kestrel / IIS on Windows), Java 25 and all browsers (Chrome, Edge, Brave,
     Firefox, UC, QQ): NOT accepted for HTTPS.
   * OpenSSL 3.5+ based software (nginx, Apache, Node.js, Python, curl, Kestrel on Linux): YES.
 So: use the Classic leaves (Q1 / Q2) for browser-facing sites and Windows servers, and the Quantum
 leaves (quadrants 3 / 4) for OpenSSL-based services and mutual TLS between your own systems. The hybrid key
 exchange (ML-KEM) is separate: browsers, Windows 11 and OpenSSL 3.5+ negotiate it with ANY
 certificate. See the design file, sections 3 and 7.

 2  WHAT YOU NEED
====================================================================================================
 2.1  Operating systems that can RUN the script
        Windows 11 Home / Pro      recommended (hybrid ML-KEM in Schannel: Kestrel, IIS)
        Windows 10 Home / Pro      works; builds only the Classic quadrants by default (see 4)
        Ubuntu, RHEL 9, Rocky 10, CentOS Stream 10, Oracle Linux 10, SUSE 16, macOS (M2, M4)
                                    generation works; installing trust is manual (section 7)
        FreeBSD                    PowerShell is not an officially supported platform there:
                                    build the PKI on another system and install root.crt by hand
 2.2  PowerShell 7 or newer (not Windows PowerShell 5.1)
        Windows : winget install --id Microsoft.PowerShell      then start "pwsh"
        macOS   : brew install --cask powershell
        Linux   : follow the Microsoft package instructions for your distribution
 2.3  OpenSSL 4.x ONLY  (OpenSSL 3.x is refused)
        Windows : run your Install-DevEnvironment.ps1 in an ELEVATED PowerShell. It installs FireDaemon
                  OpenSSL through winget (package FireDaemon.OpenSSL), adds it to PATH and creates
                  fipsmodule.cnf. OpenSSL only:
                      .\Install-DevEnvironment.ps1 -Only OpenSSL,7Zip
                  Then open a NEW PowerShell window (PATH is read at start).
        macOS   : Homebrew OpenSSL 4 (NOT /usr/bin/openssl, which is LibreSSL)
        Linux   : build from source (enable-fips), or a 4.x package if your distribution has one
        Check   : openssl version      must print  OpenSSL 4.x.x
        Which one is used: the script asks EVERY openssl it can find (PATH and the usual install folders)
                  and takes the newest 4.x. An older OpenSSL that comes first in PATH (Git for Windows, an old
                  package) is skipped and named in the output. To force one:
                      .\pki_setup.ps1 -OpenSslPath "C:\Program Files\FireDaemon OpenSSL 4\bin\openssl.exe"
        If only 3.x exists the script stops and prints these steps itself.
        Machine-wide settings: Install-DevEnvironment.ps1 sets OPENSSL_CONF (a master configuration, with
                  oqsprovider) and OPENSSL_MODULES for the whole machine. pki_setup.ps1 ignores the
                  OPENSSL_CONF: every OpenSSL command runs with its own configuration (native providers
                  only), so that master file can never break or change the PKI. OPENSSL_MODULES is kept
                  (the FIPS module is found through it).
        Capability gate: before any key is made the script proves that this OpenSSL can create ML-DSA keys
                  (Quadrants 3 / 4) and load the FIPS provider (Quadrants 2 / 4). If not, it stops at once with
                  the reason, instead of failing halfway through the build.
        Note    : OpenSSL 4.0 is a short-support release (about May 2027). Only this script needs
                  4.x. The servers that USE the certificates can run OpenSSL 3.5 LTS (to 2030).
 2.4  FIPS module (only for quadrants 2 and 4)
        openssl fipsinstall -out fipsmodule.cnf -module "<folder>\fips.dll"
        then  .\pki_setup.ps1 -FipsModuleConfig <path>\fipsmodule.cnf
        The module must match the OpenSSL version. Without it use  -Quadrant 1,3.
 2.5  Administrator rights (elevated PowerShell) only for -InstallTrust, -RemoveTrust,
      -RemoveAllTrust and -Clean.


====================================================================================================
 3  FIRST RUN
====================================================================================================
 1. Put pki_setup.ps1, agantra_pki.cnf and the scripts\ folder together in one project folder.
 2. Unblock the files once (needed only if they came from a download or zip):
        Get-ChildItem -Path . -Recurse -File | Unblock-File
    If Windows refuses to run scripts:   Set-ExecutionPolicy RemoteSigned -Scope CurrentUser
 3. Open PowerShell 7 AS ADMINISTRATOR in the project folder (for the trust install).
 4. Edit agantra_pki.cnf if needed: company data, URLs, SAN names, policies and the IANA PEN
    (section 5.4). The PEN may stay blank.
 5. Check the machine first (changes nothing):
        .\pki_setup.ps1 -Check
    Every line must be PASS or INFO and the last line READY. It tests PowerShell, OpenSSL 4.x,
    the providers, the FIPS module (only when quadrant 2 or 4 is selected), blocked files, rights,
    the output folder, and runs a real mini CA with the exact OpenSSL options the generator uses.
 6. Run:
        .\pki_setup.ps1 -InstallTrust
    Windows 11 builds all four quadrants. Windows 10 builds quadrants 1 and 2 only.
    RSA 8192 keys take a while; the progress is printed for every CA. -Check must show
    "ML-DSA (Quantum quadrants)  PASS" before you build Quadrants 3 and 4.
 7. Read the summary table at the end. Every CA is listed with validity, key, digest, expiry date
    and common name.
 8. Re-validate what was written (changes nothing):
        .\pki_setup.ps1 -Verify
    "PKI is valid" means every key, digest, pathlen, policy, chain and PFX is correct; on Windows it
    also tells whether each CA certificate is in the certificate store.
 9. Open a browser that uses the Windows store (Edge, Chrome, Brave) and test a server that uses
    one of the leaf certificates (section 8). Firefox needs its own import (section 7).
10. The acceptance checklist of both of your machines is in PKI-Design-with-FIPS-and-PQC.txt,
    section 14.


====================================================================================================
 4  WHICH QUADRANT DO I USE?
====================================================================================================
   Quadrant   Track     Provider    Root key / digest         Intermediate           Default leaf     Named
   ---------  --------  ----------  ------------------------  ---------------------  ---------------  -----------
   1          Classic   non-FIPS    RSA 8192 / SHA-512        RSA 4096 / SHA-256     RSA 2048
   2          Classic   FIPS        ECDSA P-521 / SHA-512     ECDSA P-384 / SHA-384  ECDSA P-256
   3          Quantum   non-FIPS    ML-DSA-87                 ML-DSA-87              ML-DSA-65
   4          Quantum   FIPS        ML-DSA-87                 ML-DSA-87              ML-DSA-65

   Browser-facing sites, IIS, Kestrel on Windows, Java 25:     use quadrant 1 (RSA) or 2 (FIPS ECDSA).
   OpenSSL-based services, Kestrel on Linux, mutual TLS
   between your own systems, post-quantum tests:               use quadrant 3 (non-FIPS) or 4 (FIPS).
   Windows 11 24H2+ / Server 2025 hold all four in the certificate store. Windows 10 and Server 2022
   cannot hold ML-DSA certificates: there the script builds quadrants 1 and 2 only.
   If this OpenSSL cannot create an ML-DSA key the script STOPS (no silent downgrade). -PqcFallback
   makes it create RSA keys instead, with warnings; those certificates are not quantum-safe.
   In Phase A the script issues EV leaf certificates (397 days). DV and OV leaf certificates come
   with GenerateLeafCertificate.ps1 (Phase B); their default validity is already set: OV 3 years,
   DV 5 years (-OvLeafYears, -DvLeafYears, or agantra_pki.cnf).

 5  COOKBOOK
====================================================================================================
 5.1  Generate and install everything (Windows 11)
        .\pki_setup.ps1 -InstallTrust
 5.2  Only the quadrants that need no FIPS module
        .\pki_setup.ps1 -Quadrant 1,3 -InstallTrust
 5.3  Include the FIPS quadrants
        .\pki_setup.ps1 -FipsModuleConfig C:\openssl\ssl\fipsmodule.cnf -InstallTrust
 5.4  Your own domain, company data, policies and IANA PEN
        .\pki_setup.ps1 -Domain app.example.com -Organization "Example Ltd" -Country EE `
                        -Serial 12345678 -InstallTrust
      Policies. Every certificate carries the policy of its level (EV 2.23.140.1.1, OV, DV), so your
      applications can tell what they hold. The EV policy is required and always written.
      Your IANA Private Enterprise Number (PEN) may stay blank. When you have it:
        .\pki_setup.ps1 -IanaPen 12345 -Clean -InstallTrust       (or IanaPen = 12345 in the cnf)
      The certificates then also carry  1.3.6.1.4.1.12345.1  (company policy) and the level policies
      .1.1 EV, .1.2 OV, .1.3 DV  - so your apps can recognise a company EV certificate.
      Another EV OID:   -EvPolicyOid 1.3.6.1.4.1.12345.7.1     (or [ policy_oids ] EV in the cnf)
      Extra policies:   agantra_pki.cnf [ custom_policies ]   label = OID | CPS-URL
 5.5  Start over
        .\pki_setup.ps1 -Clean -InstallTrust
 5.6  Different validity or intermediate algorithm
        .\pki_setup.ps1 -IntYears 100 -LeafDays 365 -OvLeafYears 2 -DvLeafYears 4 -IntermediateCurve P-521
 5.7  Use a specific OpenSSL
        .\pki_setup.ps1 -OpenSslPath "C:\Program Files\OpenSSL\bin\openssl.exe"
 5.8  See every OpenSSL command
        .\pki_setup.ps1 -Verbose
 5.6a Quantum algorithm choices
        .\pki_setup.ps1 -PqcAlgorithm mldsa65 -PqcLeafAlgorithm mldsa44      (intermediates, leaves)
        .\pki_setup.ps1 -PqcFallback              (only if ML-DSA fails: RSA instead, NOT quantum-safe)
 5.8a Check the machine / re-validate an existing PKI (read-only)
        .\pki_setup.ps1 -Check
        .\pki_setup.ps1 -Verify
 5.9  Unblock files and find out who locks the folder
        .\pki_setup.ps1 -Unblock
 5.10 Remove this PKI from Windows (files stay)
        .\pki_setup.ps1 -RemoveTrust
 5.11 Remove everything: all Agantra certificates from Windows AND the pki folder
        .\pki_setup.ps1 -RemoveAllTrust

 5.11a Install the existing PKI in Windows again (no rebuild, no OpenSSL)
        .\pki_setup.ps1 -ReinstallTrust            (elevated)
 5.15 Leaf certificates and the transport have their own manuals (GenerateLeafCertificate-MANUAL.txt, PkiTransport-MANUAL.txt)
 5.16 Unblock and unlock the folders, children and recursive
        .\pki_setup.ps1 -Unblock          .\GenerateLeafCertificate.ps1 -Unblock
 5.12 Classic PKI only (Enterprise Root, Classic Track Root, Q1 Root, DV / OV / EV intermediates)
        .\pki_setup.ps1 -ClassicPKI -InstallTrust
 5.13 See the names of all CAs before generating, and change them (section 14)
        .\pki_setup.ps1 -ShowNames
 5.14 Enterprise Root signed by a public CA (section 15; full text PUBLIC-CA-ENTERPRISE-ROOT.txt)
        .\pki_setup.ps1 -ClassicPKI -EnterpriseRootCsr -ExternalCa DigiCert -EnterpriseRootKeyBits 4096
        .\pki_setup.ps1 -ImportEnterpriseRoot signed.pem -ExternalChain chain.pem -InstallTrust

 6.1  Folder .\pki

        classical\root\  quantum\root\ Track Roots

        publish\                       root.crt, ca-bundle.crt, <slug>.crt / .crl / .pem, README.txt

 6.2  Leaf files  (pki\leaf\<domain>-<tag>.*, tag = q1-rsa2048, q2-ecdsa-p256, q3-mldsa65, q4-mldsa65)
        .crt             the certificate
        .key             the private key (PKCS#8 PEM, no password): protect it
        -fullchain.crt   leaf + intermediate + quadrant root + track root   <- servers send this
        .pfx             certificate + key + chain, password from -Password (default Abc12345!)
        -fips.pfx        FIPS leaves only (quadrants 2, 4): FIPS-conformant container (PBMAC1). Windows may not
                         import it; use the normal .pfx on Windows
 6.3  Which file each product needs      (Classic = q1 / q2 leaf, Quantum = q3 / q4 leaf)
        Kestrel on Windows (.NET 10 / 11)  .pfx  Classic only      (Schannel cannot serve ML-DSA)
        IIS (Windows 11 Pro / Server)      .pfx  Classic only      -> LocalMachine\My
        Kestrel on Linux                   .pfx or PEM, Classic or Quantum (OpenSSL 3.5+)
        nginx                              -fullchain.crt + .key   Classic or Quantum (OpenSSL 3.5+)
        Apache httpd                       -fullchain.crt + .key   Classic or Quantum (OpenSSL 3.5+)
        Node.js 26                         -fullchain.crt + .key   Classic or Quantum (bundled OpenSSL 3.5+)
        Python 3.14                        -fullchain.crt + .key   Classic or Quantum (OpenSSL 3.5+)
        Go                                 -fullchain.crt + .key   Classic (Quantum: not verified)
        PHP 8                              -fullchain.crt + .key   Classic (as client: root.crt as cafile)
        Java 25                            .pfx (PKCS12 keystore)  Classic only
        Browsers                           Classic only
        Every CLIENT of these servers must trust  pki\root\root.crt  (section 7).


====================================================================================================
 7  TRUST THE ENTERPRISE ROOT ON EVERY DEVICE
====================================================================================================
 On other devices install only pki\root\root.crt (PEM). The servers send the intermediates in the fullchain
 file. On the Windows machine that BUILDS the PKI, pki_setup installs every CA:
 Windows            .\pki_setup.ps1 -InstallTrust   (or -ReinstallTrust for an existing PKI). Result in certlm.msc:
                      Trusted Root Certification Authorities   Enterprise Root, Classic and Quantum Track
                                                               Roots, the four Quadrant Roots  (7 certificates)
                      Intermediate Certification Authorities   all DV / OV / EV CAs          (12 certificates)
                      Personal                                 the default leaf PFX files
                    Another Windows device: certlm.msc -> Trusted Root Certification Authorities -> Import
                    root.crt (the Enterprise Root is enough there). Edge, Chrome and Brave use this store.
 Firefox (all OS)   Settings -> Privacy & Security -> Certificates -> View Certificates ->
                    Authorities -> Import (tick "Trust this CA to identify websites").
                    Or about:config -> security.enterprise_roots.enabled = true (uses the OS store).
 Chrome, Chromium,  on Linux they read the NSS database:
 Brave, Edge        sudo apt install libnss3-tools      (or dnf / zypper equivalent)
                    certutil -d sql:$HOME/.pki/nssdb -A -t "C,," -n AgantraRoot -i root.crt
 Ubuntu             sudo cp root.crt /usr/local/share/ca-certificates/agantra-root.crt
                    sudo update-ca-certificates
 RHEL 9, Rocky 10,  sudo cp root.crt /etc/pki/ca-trust/source/anchors/agantra-root.crt
 CentOS Stream 10,  sudo update-ca-trust
 Oracle Linux 10
 SUSE Linux 16      sudo cp root.crt /etc/pki/trust/anchors/agantra-root.crt
                    sudo update-ca-certificates
 FreeBSD (14+)      sudo cp root.crt /usr/local/share/certs/agantra-root.pem
                    sudo certctl rehash          (verify on your FreeBSD version)
 macOS (M2, M4)     sudo security add-trusted-cert -d -r trustRoot \
                         -k /Library/Keychains/System.keychain root.crt
 Android            copy root.crt to the phone -> Settings -> Security -> Install a certificate ->
                    CA certificate. Chrome honours it; apps that target Android 7+ ignore user CAs
                    unless they allow them.
 UC Browser,        NOT verified. They may use their own certificate store or ignore user CAs.
 QQ Browser         Test one page first; if it fails, use the browser's own certificate settings.
 Application runtimes (they do not always use the OS store):
        Node.js     set NODE_EXTRA_CA_CERTS=C:\path\root.crt
        Python      ssl.create_default_context(cafile="root.crt")  or  SSL_CERT_FILE=root.crt
        Go          uses the OS store; or x509.NewCertPool() + AppendCertsFromPEM
        PHP         'cafile' => 'root.crt' in the stream context, or openssl.cafile in php.ini
        Java 25     keytool -importcert -trustcacerts -alias agantra-root -file root.crt -cacerts
        .NET        uses the OS store; or X509Chain with CustomRootTrust

 7A  COPY THE PKI FROM THE WINDOWS VM TO THE UBUNTU 26.04 SERVER
====================================================================================================
 The Ubuntu development server has no PowerShell: generate the PKI on the Windows 11 VM and copy only
 what the server needs. Never copy the CA keys (.key files below pki\root, classical, quantum).

 On Windows (PowerShell; OpenSSH client is part of Windows 11):
     $h = "user@terminal-node-01.makananmurah.com"
     scp pki\root\root.crt                                       "${h}:/tmp/agantra-root.crt"
     # Classic leaf (browsers, any client) and Quantum leaf (OpenSSL 3.5+ clients):
     scp pki\leaf\nextmantra.com-q1-rsa2048-fullchain.crt        "${h}:/tmp/"
     scp pki\leaf\nextmantra.com-q1-rsa2048.key                  "${h}:/tmp/"
     scp pki\leaf\nextmantra.com-q3-mldsa65-fullchain.crt        "${h}:/tmp/"
     scp pki\leaf\nextmantra.com-q3-mldsa65.key                  "${h}:/tmp/"

 On Ubuntu (as root or with sudo):
     cp /tmp/agantra-root.crt /usr/local/share/ca-certificates/agantra-root.crt
     update-ca-certificates                     # prints "1 added": Python, Go, .NET, curl now trust it
     mkdir -p /etc/pki/agantra
     mv /tmp/nextmantra.com-q*-fullchain.crt /tmp/nextmantra.com-q*.key /etc/pki/agantra/
     chown root:root /etc/pki/agantra/* ; chmod 644 /etc/pki/agantra/*.crt ; chmod 600 /etc/pki/agantra/*.key
     # Java: update-ca-certificates also updates /etc/ssl/certs/java/cacerts when ca-certificates-java is installed
     # Node : export NODE_EXTRA_CA_CERTS=/usr/local/share/ca-certificates/agantra-root.crt

 Test from the server itself (SAN names: nextmantra.com, www.nextmantra.com, localhost, 127.0.0.1):
     curl --resolve nextmantra.com:443:127.0.0.1 https://nextmantra.com/ -I
 If the host name of your server is not in the SAN, set it first: edit [ leaf_san ] in agantra_pki.cnf
 or use  -Domain  and generate again.

 Your nginx 1.31.4 (OpenSSL 3.5.5, HTTP/3 module present) needs the configuration of section 8.3.


====================================================================================================
 8  USING THE CERTIFICATES IN YOUR SERVERS
====================================================================================================
 Which leaf for which product: browsers, IIS, Kestrel on Windows and Java 25 need a CLASSIC leaf (q1 /
 q2); the examples below use q1-rsa2048. A QUANTUM leaf (q3 / q4, ML-DSA) is for OpenSSL 3.5+ based
 servers and clients (nginx, Apache, Node, Python, curl, Kestrel on Linux): same configuration, with
 the file names nextmantra.com-q3-mldsa65-fullchain.crt / .key.

 Rules for the post-quantum key exchange (all products):
   * TLS 1.3 must be enabled (it is the only protocol that carries the hybrid group).
   * Do not hard-code cipher suites or key-exchange groups unless you include the hybrid group.
   * Hybrid ML-KEM comes from the TLS library, not from the certificate.

 8.1  Kestrel on Windows 11 (.NET 10 LTS / .NET 11)
        builder.WebHost.ConfigureKestrel(k => k.ConfigureHttpsDefaults(h =>
        {
            h.ServerCertificate = X509CertificateLoader.LoadPkcs12FromFile(
                "nextmantra.com-q1-rsa2048.pfx", pfxPassword);
            h.SslProtocols = System.Security.Authentication.SslProtocols.Tls13 |
                             System.Security.Authentication.SslProtocols.Tls12;
        }));
      Windows: use the CLASSIC .pfx (q1). Schannel cannot bind an ML-DSA certificate for HTTPS, so
      a Quantum .pfx fails there. On Linux Kestrel uses OpenSSL and can serve the Quantum certificate.
      On Windows the TLS stack is Schannel; hybrid ML-KEM is part of Windows 11 (July 2026 update or
      newer, TLS 1.3). Follow Microsoft's "Kestrel and Schannel with TLS 1.3 post-quantum" article for the
      Schannel setting. On Linux Kestrel uses OpenSSL (3.5+ for the hybrid group); on macOS it uses
      the Apple TLS stack (hybrid support: macOS 26 or newer; verify with your build).
      Mutual TLS: h.ClientCertificateMode = ClientCertificateMode.RequireCertificate.
      Visual Studio 2026 / Visual Studio Code (no code): appsettings.json
        "Kestrel": { "Endpoints": { "Https": { "Url": "https://*:5001" } },
                     "Certificates": { "Default": { "Path": "C:\\pki\\leaf\\nextmantra.com-q1-rsa2048.pfx",
                                                   "Password": "Abc12345!" } } }
      or environment variables ASPNETCORE_Kestrel__Certificates__Default__Path / __Password.
      The default SAN set includes localhost and 127.0.0.1, so https://localhost:5001 is trusted once the
      root is installed (instead of the dotnet dev-certs certificate). Keep the password out of source
      control: use  dotnet user-secrets  in development.
 8.2  IIS (Windows 11 Pro, Windows Server 2025; legacy applications)
        Import-PfxCertificate -FilePath .\nextmantra.com-q1-rsa2048.pfx `
            -CertStoreLocation Cert:\LocalMachine\My -Password (Read-Host -AsSecureString)
      IIS Manager -> Site -> Bindings -> https -> choose the certificate. IIS uses Schannel, so
      it follows Windows for the hybrid key exchange.
 8.3  nginx  (your Ubuntu server: 1.31.4 built with OpenSSL 3.5.5, HTTP/3 module present)
        server {
            listen 443 ssl;
            listen 443 quic reuseport;                 # HTTP/3 (nginx built with --with-http_v3_module)
            http2 on;
            server_name nextmantra.com www.nextmantra.com;
            add_header Alt-Svc 'h3=":443"; ma=86400';
            ssl_certificate     /etc/pki/agantra/nextmantra.com-q1-rsa2048-fullchain.crt;
            ssl_certificate_key /etc/pki/agantra/nextmantra.com-q1-rsa2048.key;
            ssl_protocols       TLSv1.3 TLSv1.2;
            # Leave ssl_ecdh_curve out (default "auto"). A classical-only list turns the hybrid group
            # off. If you set it, put the hybrid group first with "?" so older OpenSSL still starts:
            # ssl_ecdh_curve ?X25519MLKEM768:X25519:prime256v1;
        }
        sudo nginx -t && sudo systemctl reload nginx
      QUANTUM certificate (OpenSSL 3.5+ clients only; browsers will refuse it): use the q3-mldsa65
      files in the two ssl_certificate lines, on a test host name.
      BOTH on one site (dual certificates; nginx loads one certificate per key type and OpenSSL
      presents the one the client supports - test it before relying on it):
            ssl_certificate     /etc/pki/agantra/nextmantra.com-q1-rsa2048-fullchain.crt;
            ssl_certificate_key /etc/pki/agantra/nextmantra.com-q1-rsa2048.key;
            ssl_certificate     /etc/pki/agantra/nextmantra.com-q3-mldsa65-fullchain.crt;
            ssl_certificate_key /etc/pki/agantra/nextmantra.com-q3-mldsa65.key;
      Open UDP 443 as well as TCP 443 in the Alibaba Cloud security group for HTTP/3.
      nginx -V 2>&1 | grep -i "built with"   must show OpenSSL 3.5 or newer (yours: 3.5.5). This is not
      the same as  openssl version.  Other nginx 1.30.x / 1.31.x builds: same configuration.
 8.4  Apache httpd 2.4 (latest)
        SSLEngine on
        SSLProtocol -all +TLSv1.3 +TLSv1.2
        SSLCertificateFile    /etc/pki/nextmantra.com-q1-rsa2048-fullchain.crt
        SSLCertificateKeyFile /etc/pki/nextmantra.com-q1-rsa2048.key
        # optional: SSLOpenSSLConfCmd Groups ?X25519MLKEM768:X25519:prime256v1
        Protocols h2 http/1.1
      mod_ssl must be built against OpenSSL 3.5 or newer for the hybrid group.
 8.5  Node.js 26
        https.createServer({
          key:  fs.readFileSync('nextmantra.com-q1-rsa2048.key'),
          cert: fs.readFileSync('nextmantra.com-q1-rsa2048-fullchain.crt'),

====================================================================================================
 13  LIMITS YOU MUST KNOW  (full list: design file, section 9)
====================================================================================================
 * Private PKI: every client must install root.crt. No browser shows the EV company line.
 * The Quantum track is ML-DSA at every level, but ML-DSA certificates are not accepted for HTTPS by
   Windows Schannel, Java 25 or the browsers today: Classic leaves for those, Quantum leaves for
   OpenSSL 3.5+ services and mutual TLS.
 * The hybrid key exchange (ML-KEM) is separate and needs both ends; otherwise the connection is
   classical. ML-DSA signatures are large: Quantum chains are tens of KB.
 * UC Browser and QQ Browser are not verified.
 * Phase A has no DV / OV leaf generator, no transport script, and pki_reuse.ps1 still expects the
   old layout.
 * Tested by me on Linux with a real OpenSSL 4.0.3 and the real FIPS provider: the whole PKI, ML-DSA,
   -Check, -Verify, and a live TLS 1.3 handshake with an ML-DSA leaf. NOT tested by me: Windows (store
   functions, Kestrel, IIS), browsers, nginx / Apache / Node / Python as servers: please run section 3
   and the checklist (design file, section 14) and report.

 14  CHANGE THE NAMES OF THE CAs
====================================================================================================
 All names of roots and intermediates are decided in ONE place: scripts\01b_CaNaming.ps1 holds the
 defaults, agantra_pki.cnf [ ca_names ] overrides them (recommended: your changes survive a script
 update). Remove the "#" of the lines you want to change:

     [ ca_names ]
     Prefix              = Agantra Inovatif
     QuantumLabel        = PQC-PostQuantum
     SlugPrefix          = agantra                 (file-name stem of CRL / CA-issuer files)
     GenEnterprise = G1   GenClassic = G1   GenQuantum = G2
     EnterpriseRoot      = {Prefix} Enterprise Root CA {Gen}
     ClassicTrackRoot    = {Prefix} Enterprise Classic Root CA {Gen}
     QuantumTrackRoot    = {Prefix} Enterprise {QuantumLabel} Root CA {Gen}
     ClassicQuadrantRoot = {Prefix} Enterprise Classic Q{N} Root CA {Gen}
     QuantumQuadrantRoot = {Prefix} Enterprise {QuantumLabel} Q{N} Root CA {Gen}
     Intermediate        = {Prefix} {Level} {Algorithm} {Gen} CA

 Tokens: {Prefix} {QuantumLabel} {Gen} {N} {Level} {Algorithm} {Track} {Id}.
   {Level}  DV | OV | EV         {Algorithm}  the real key, e.g. RSA-4096, ECDSA-P384 FIPS, ML-DSA-87
 Rules (the script stops with the reason): at most 64 characters, every CA a different name, only these
 tokens. Always run  .\pki_setup.ps1 -ShowNames  after a change. Names are fixed when a CA is issued:
 changing them later needs  -Clean  (a new PKI). The Organizational Unit of each layer is OU_Root, OU_Track,
 OU_Quadrant, OU_Intermediate in [ pki_settings ].

 15  CLASSIC PKI ONLY, AND A PUBLIC CA FOR THE ENTERPRISE ROOT
====================================================================================================
 CLASSIC PKI    .\pki_setup.ps1 -ClassicPKI
   Builds only Enterprise Root -> Classic Track Root -> Q1 Root -> DV / OV / EV intermediates (RSA, no
   FIPS module needed, no post-quantum) and the Q1 EV leaf. Same names as the full PKI (G1).
   Cannot be combined with -Quadrant. Add the other quadrants later by generating a full PKI.

 PUBLIC CA      DigiCert, GlobalSign, Sectigo can sign the Enterprise Root, so clients that trust the
   public root accept the PKI without installing anything. The script prepares the files and checks the
   answer; the CA does the signing. Short form (full text and cautions: PUBLIC-CA-ENTERPRISE-ROOT.txt):
     1. .\pki_setup.ps1 -ClassicPKI -EnterpriseRootCsr -ExternalCa DigiCert -EnterpriseRootKeyBits 4096
        -> pki\root\root.csr and external-request.txt (what to ask the CA)
     2. send root.csr; receive the signed certificate and the chain
     3. .\pki_setup.ps1 -ImportEnterpriseRoot signed.pem -ExternalChain chain.pem -InstallTrust
     4. .\pki_setup.ps1 -Verify
   Already have a PKI? Cross-sign instead: -CrossSignCsr, then -ImportCrossCert <file> -ExternalChain <file>.
   Things you must know: the public CA decides key size, pathlen (this PKI needs >= 3), EKU, name
   constraints and validity; every CA below is shortened to end before the public certificate; public TLS
   leaves are limited to 398 days; do not combine -Clean with -ImportEnterpriseRoot (it deletes the key).

ROOT KEY POLICY  (enforced, not configurable)
  Every root-level CA (Enterprise Root, Track Roots, Quadrant Roots) is RSA 8192 with SHA-512.
  Where the algorithm is not RSA, the strongest key and the largest digest it offers are used:
      RSA      8192 bit           SHA-512   (8192 is also the largest size Chrome accepts)
      ECDSA    P-521              SHA-512   (largest NIST curve; Classic FIPS quadrant)
      ML-DSA   ML-DSA-87          none      (NIST level 5, the highest; a pure signature that hashes
                                             internally with SHAKE256; the whole Quantum track)
  The Enterprise Root is RSA because it anchors both tracks. The validator rejects a root-level CA
  that does not meet this, and checks that every certificate below an ML-DSA CA is ML-DSA signed.

QUANTUM TRACK  (post-quantum signatures, FIPS and non-FIPS)
  The Quantum track uses ML-DSA at EVERY level: Track Root, Quantum Q1 / Q2 roots, intermediates and leaves.
  If OpenSSL cannot create an ML-DSA key the script STOPS (a silent downgrade would defeat the
  purpose). -PqcFallback creates an RSA key instead (genrsa), with a warning per key, in the summary
  (marked *) and in pki-manifest.json; such a certificate is not quantum-safe.
  WHERE ML-DSA CERTIFICATES WORK (status of mid-2026; test on your builds):
    Certificate store, chain validation   Windows 11 24H2+ and Windows Server 2025 (updated), via
                                          CryptoAPI. -InstallTrust installs every Quantum root,
                                          intermediate and leaf there. NOT Windows 10 / Server 2022.
    TLS server certificate                OpenSSL 3.5+ servers and clients: nginx, Apache, Node.js,
                                          Python, curl, Kestrel on Linux. NOT Windows Schannel
                                          (Kestrel / IIS on Windows), NOT Java 25, NOT the browsers
                                          (Chrome, Edge, Brave, Firefox, UC, QQ) today.
  So: use the Quantum leaves for OpenSSL-based services and mutual TLS between your own systems.
  Sites that browsers or Windows servers must serve use the Classic leaves (quadrants 1 / 2); every browser
  and Windows 11 also negotiates the hybrid ML-KEM key exchange (X25519MLKEM768) with those.
  Windows 10 / Server 2022: quadrants 3, 4 are not built by default (-Quadrant 1,2,3,4 overrides).

CLASSIC PKI  (-ClassicPKI)
  Builds only:  Enterprise Root -> Classic Track Root -> Q1 Root -> DV / OV / EV intermediates
  (RSA only, no FIPS module, no post-quantum) and the Q1 EV leaf. The widest compatibility and the
  smallest PKI; also the shape to use under a public CA. Cannot be combined with -Quadrant.

CA NAMES  (all roots and intermediates)
  The names are configurable. Defaults live in scripts\01b_CaNaming.ps1; override them in
  agantra_pki.cnf [ ca_names ] (templates, prefix, Quantum label, generation labels, file-name stem).
  Tokens: {Prefix} {QuantumLabel} {Gen} {N} {Level} {Algorithm} {Track} {Id}.

WINDOWS TRUST   (elevated PowerShell; other modes need no elevation)
  -InstallTrust        Every ROOT -> LocalMachine\Root  (Trusted Root Certification Authorities):
                         Enterprise Root, Classic / Quantum Track Roots, the four Quadrant Roots.
                       Every INTERMEDIATE -> LocalMachine\CA  (Intermediate Certification Authorities):
                         all DV / OV / EV CAs.
                       Default leaf PFX files -> LocalMachine\My (ONLY the leaf is imported; the chain
                       certificates inside the PFX are not, because Windows would file them under Intermediate).
                       Track and Quadrant Roots are issued by the Enterprise Root (not self-signed);
                       Windows treats a certificate in the Trusted Root store as a trust anchor either way.
                       A certificate an earlier version put in the wrong store is moved. Afterwards the
                       script READS THE STORES BACK and prints how many roots / intermediates are in place;
                       a certificate in the wrong store (or in both) is an ERROR and ends the run.
                       (An Enterprise Root signed by a public CA is an intermediate: it goes to CA.)
                       This includes every ML-DSA certificate on Windows 11 24H2+ and Windows
                       Server 2025. Each certificate is installed with .NET, then certutil.exe if
                       needed, and checked by thumbprint. A CA certificate that cannot be installed
                       stops the run with an error; a leaf PFX Windows cannot import is a warning.
  -ReinstallTrust      Install the PKI that ALREADY EXISTS in .\pki into the Windows stores again, without
                       regenerating anything and without OpenSSL: puts roots in Trusted Root, intermediates
                       in Intermediate, moves certificates found in the wrong store. Use it after an update
                       or when -Verify reports certificates in the wrong store.
  -Clean               Remove this PKI's trust and the .\pki folder first.
  -RemoveTrust         Remove only this PKI (by thumbprint) from Root, CA and My.
                       The files stay on disk.
  -RemoveAllTrust      Remove EVERY certificate whose subject or issuer contains
                       'Agantra Inovatif' or 'NextMantra' from Root, CA and My, then delete
                       the .\pki folder: all contents and the folder itself.
  Certificates that are already gone from the stores are ignored and the run continues.
  Linux, macOS, FreeBSD and the browsers' own stores: install pki\root\root.crt as described
  in pki_setup-MANUAL.txt.

UNBLOCK / UNLOCK
  -Unblock             UNBLOCK (remove the Windows "downloaded from the Internet" mark) and UNLOCK (remove the
                       Read-only attribute) every file and folder below the script folder, the PKI folder and the
                       leaf folder (<script folder>\leafcerts), children and recursive; then list the programs
                       that hold files in those folders open (Windows Restart Manager). Nothing is killed: close
                       the listed program (Explorer window, editor, shell).
  Every start of the script does the same for its own folder BEFORE any script is loaded (the standard bootstrap
  of every main script), and again for the PKI folder before and after generation. GenerateLeafCertificate.ps1
  has the same -Unblock. A script that is still blocked the very first time needs once:
      Get-ChildItem -Path . -Recurse -File | Unblock-File
  -Clean / -RemoveAllTrust leave the folder first when your shell is inside it, retry while a program holds it, and
  name that program. They do NOT touch <script folder>\leafcerts: leaf certificates of the old PKI do not chain to a
  new one; the script warns when such leaves exist.

LIMITATIONS  (details: PKI-Design-with-FIPS-and-PQC.txt, section 9)
  * Private PKI: install the Enterprise Root on every client. No browser shows the EV company
    line for a private root.
  * ML-DSA certificates are NOT accepted for HTTPS by Windows Schannel (Kestrel / IIS on Windows),
    Java 25 or the browsers today; they work in the Windows store and with OpenSSL 3.5+ stacks.
  * ML-DSA needs OpenSSL 3.5 or newer (4.x here); the FIPS quadrant also needs a FIPS module that
    contains ML-DSA.
  * ML-DSA signatures are large (about 3.3 KB for ML-DSA-65, 4.6 KB for ML-DSA-87): a full chain is
    tens of KB. Some proxies and servers limit header or handshake size.
  * Validity beyond 2038 can fail on 32-bit systems (old 32-bit Android, embedded devices).
  * RSA 8192 CA keys are slow to sign and verify; P-521 CA keys are validated by all listed
    platforms, but some TLS stacks restrict P-521 for TLS handshakes (leaves are P-256).
  * UC Browser and QQ Browser are not verified: they may use their own certificate store.
  * The CRL / OCSP / CA Issuers URLs help only when the files in .\pki\publish are served there.
  * Windows: -Verify asks the Windows chain engine itself whether it accepts every leaf chain. ML-DSA
    chains need Windows 11 24H2+ / Server 2025; the result on your machine is the proof.
  * OpenSSL 4.0 is a short-support release (about May 2027); the OpenSSL 3.5 LTS runs to 2030.
    Only this script needs 4.x; the servers that use the certificates can link 3.5 or newer.
  * A public CA signs only what it agrees to: it may refuse RSA 8192 / P-521, limit pathlen below 3, require
    an HSM, add name constraints and cap the validity (public TLS leaves: 398 days). Signing is not
    automated. Tested here with a stand-in CA, not with DigiCert, GlobalSign or Sectigo.
  * pki_reuse.ps1 and GenerateLeafCertificate.ps1 still target the old single-root layout until
    Phases B and C.
