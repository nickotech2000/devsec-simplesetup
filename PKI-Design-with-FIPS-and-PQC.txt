 1  GOALS AND TARGETS
====================================================================================================
 * One private PKI with two tracks, CLASSIC and QUANTUM, and four quadrants:
        quadrant   1 Classic non-FIPS | 2 Classic FIPS | 3 Quantum non-FIPS | 4 Quantum FIPS       (internal numbers)
        NAMED      Classic Q1         | Classic Q2     | Quantum Q1         | Quantum Q2           (Q1 = non-FIPS, Q2 = FIPS, both tracks)
   Each quadrant has three policy-isolated intermediates: DV, OV, EV.
 * CLASSIC  quadrants use RSA (Q1) and ECDSA (Q2).
   QUANTUM  quadrants use the post-quantum signature ML-DSA at EVERY level: Track Root, Quantum Q1 / Q2 roots,
   intermediates and leaves, FIPS and non-FIPS. Only the Enterprise Root, which anchors both tracks,
   is RSA. Servers that support it also negotiate the hybrid key exchange X25519MLKEM768 (ML-KEM).
 * Generation: PowerShell 7+ and OpenSSL 4.x. Older OpenSSL stops the script. ENGINE API gone;
   native providers only:  non-FIPS = -provider default   FIPS = -provider fips -provider base.
   ML-DSA is native in OpenSSL 3.5 / 4.x (genpkey -algorithm mldsa87).
 * Windows: Windows 11 Home / Pro (24H2 or newer, updated) and Windows Server 2025 store and validate
   ML-DSA certificates. Windows 10 and Server 2022 cannot: the Quantum quadrants are skipped there.
 * Other targets: Ubuntu 26, CentOS Stream 10, Rocky 10, RHEL 9, Oracle Linux 10, SUSE 16, FreeBSD (VM),
   macOS on Mac mini M2 and M4. Browsers: Chrome, Edge, Brave, Firefox, UC Browser, QQ Browser.
   Runtimes: Kestrel on .NET 10 LTS / 11, nginx, Apache httpd, Node.js 26, Python 3.14, Go, PHP 8,
   Java 25, Rust, IIS (legacy).
 * Reference machines (your screenshots, section 7.3): an Ubuntu 26.04.1 LTS development server and a
   Windows 11 26H2 Pro development VM with Visual Studio 2026 and Visual Studio Code.
 * Private PKI: every client installs the Enterprise Root. No browser shows the EV company line.
 * Variants of the PKI: the full PKI (four quadrants), -ClassicPKI (Enterprise Root, Classic Track Root, Q1
   Root, DV / OV / EV intermediates only), and an Enterprise Root signed by a public CA (DigiCert, GlobalSign,
   Sectigo) instead of self-signed (section 6, diagram 5; PUBLIC-CA-ENTERPRISE-ROOT.txt).
 * Names of all roots and intermediates are configurable (section 4).
 * IMPORTANT: ML-DSA certificates are not accepted for HTTPS by Windows Schannel (Kestrel / IIS on
   Windows), Java 25 or the browsers today (section 7). Quantum leaves are for OpenSSL-based services
   and mutual TLS; browser-facing sites use the Classic leaves.

 3  RULES BY LEVEL
====================================================================================================

 3.1  ROOT KEY POLICY  (enforced in code, not configurable)
      Every root-level CA (Enterprise Root, both Track Roots, all four Quadrant Roots) is RSA 8192
      with SHA-512. Where the algorithm is not RSA, the strongest key and the largest digest it
      offers are used:

        Algorithm   Root key                  Digest    Used for
        ----------  ------------------------  --------  ------------------------------------------
        RSA         8192 bit                  SHA-512   Enterprise Root, Classic Track Root, Q1 root
        ECDSA       P-521 (secp521r1)         SHA-512   Q2 root (Classic FIPS)
        ML-DSA      ML-DSA-87 (NIST level 5)  none      Quantum Track Root, Quantum Q1 root, Quantum Q2 root

      * Why 8192: it is also the largest RSA size Chrome (BoringSSL) accepts. 16384 would fail.
      * Why P-521: largest NIST curve; roots only sign CA certificates and never take part in a TLS
        handshake, so TLS limits of some stacks on P-521 do not apply (L12).
      * ML-DSA is a pure signature scheme: it hashes internally (SHAKE256) and takes no SHA-512, so
        the digest column reads "none". ML-DSA-87 is the highest parameter set. "ML-DSA-874" in the
        first draft does not exist; ML-DSA has the sets 44, 65 and 87.
      * The validator rejects a root-level CA that breaks this table, and checks that every
        certificate below an ML-DSA CA is ML-DSA signed (and no classical CA signs one by mistake).
      * Not used: Ed448 (poor Windows chain support), RSA above 8192 (Chrome rejects it), SLH-DSA
        (30 KB signatures, little client support).

 3.2  BELOW THE ROOTS  (configurable)
        Level                  Key                        Digest       Parameter
        ---------------------  -------------------------  -----------  ---------------------------
        Q1 intermediates       RSA 4096 (or 8192)         SHA-256      -IntermediateRsaBits
        Q2 intermediates       ECDSA P-384 (or P-256/521) SHA-384      -IntermediateCurve
        Quantum intermediates  ML-DSA-87 (or 65 / 44)     none         -PqcAlgorithm
        Leaf Q1                RSA 2048                   SHA-256      -LeafSizes
        Leaf Q2                ECDSA P-256                SHA-384      -
        Leaf Quantum           ML-DSA-65 (or 44 / 87)     none         -PqcLeafAlgorithm
      Leaf floors (Phase B): RSA below 2048, ECC below P-256 and hash below SHA-256 rejected.
      Code signing: key 4096 or larger and SHA-256 or larger, enforced even if the parameters say less.
      No silent downgrade: if OpenSSL cannot create an ML-DSA key the script STOPS. Only -PqcFallback
      (RSA, size -FallbackRsaBits, default 8192, via genrsa) lets a build continue; each such key is
      warned about, marked * in the summary and listed in pki-manifest.json. Not quantum-safe.

 3.3  VALIDITY  (from the moment of generation; each level shorter than the one above)
        Enterprise Root     1000 years     -RootYears        (expires 3026)
        Track Root           500 years     -TrackYears
        Quadrant Root        400 years     -QuadrantYears
        Intermediates        250 years     -IntYears
        Leaf EV              397 days      -LeafDays         (EV maximum 398)
        Leaf OV                3 years     -OvLeafYears      (default when not given)
        Leaf DV                5 years     -DvLeafYears      (default when not given)
      pki_setup.ps1 issues EV leaves (397 days). The OV and DV defaults are stored in agantra_pki.cnf
      and used by the leaf generator (Phase B). The run prints every CA with its validity and expiry
      date.

 3.4  DIGEST BY ISSUER
        Enterprise Root and Classic Track Root sign with SHA-512.
        Quadrant Roots sign intermediates with SHA-256 (RSA), SHA-384 (ECDSA) or no digest (ML-DSA).
        Intermediates sign leaves the same way.   The Enterprise Root signs the Quantum Track Root
        with SHA-512 (it is an RSA key); everything below the Quantum Track Root is signed by ML-DSA.

 3.5  LENGTH-EXTENSION SHIELD AND OTHER PROTECTION
      A length-extension attack targets H(secret || message) constructions (MACs). An X.509
      signature covers the whole DER TBSCertificate, so the attack does not apply. What the script
      enforces instead:
        * digest allow-list: SHA-1 and MD5 rejected; SHA-512 required for classical root-level CAs
        * critical basicConstraints with a fixed pathlen at every level (3, 2, 1, 0)
        * keyCertSign + cRLSign only on CAs
        * 128-bit random positive serial numbers; separate serial database per CA
        * private key files restricted to the owner, SYSTEM and Administrators (icacls)
        * optional -RsaPss (RSASSA-PSS, randomized padding, MGF1 over the same digest) for RSA CAs.
          Off by default because some older chain engines reject PSS.
        * post-generation validation of every CA and leaf (keys, digests, pathlen, policies, chains)

 4  NAMES  (configurable)
====================================================================================================
 Defaults:
 Enterprise Root     Agantra Inovatif Enterprise Root CA G1
 Track Root          Agantra Inovatif Enterprise Classic Root CA G1
                     Agantra Inovatif Enterprise PQC-PostQuantum Root CA G2
 Quadrant Root       Agantra Inovatif Enterprise Classic Q1 Root CA G1          (Q2 likewise)
                     Agantra Inovatif Enterprise PQC-PostQuantum Q1 Root CA G2  (Q2 likewise)
                     Q1 = non-FIPS, Q2 = FIPS, in BOTH tracks. The track word and the generation (G1 Classic, G2 Quantum) keep every
                     name and file stem unique: agantra-q1-root-g1 (Classic) / agantra-q1-root-g2 (Quantum).
                     The internal quadrant numbers 1..4 (-Quadrant, ids q1-ev .. q4-ev, folders) are NOT renamed.
                     Leaf file names use the same Q1 / Q2: www.example.com-ev-q2-mldsa65.crt is a Quantum FIPS leaf.
 Intermediate        Agantra Inovatif <EV|OV|DV> <algorithm> <G1|G2> CA
                       Agantra Inovatif EV RSA-4096 G1 CA
                       Agantra Inovatif OV ECDSA-P384 FIPS G1 CA
                       Agantra Inovatif DV ML-DSA-87 G2 CA
                       Agantra Inovatif EV ML-DSA-87 FIPS G2 CA
 G1 = Classic track, G2 = everything in the Quantum track. The algorithm in an intermediate name is
 the key that really exists (after a -PqcFallback it reads RSA-8192, never ML-DSA). No year range.
 "PQC-PostQuantum" is literally true for the Quantum track (ML-DSA).

 WHERE THE NAMES ARE DECIDED  (one module: scripts\01b_CaNaming.ps1)
   Defaults   scripts\01b_CaNaming.ps1            ($script:PkiNamingDefaults, documented in the file)
   Overrides  agantra_pki.cnf  [ ca_names ]        (Prefix, QuantumLabel, SlugPrefix, GenEnterprise, GenClassic,
                                                    GenQuantum and one template per kind of CA)
   Templates  EnterpriseRoot  ClassicTrackRoot  QuantumTrackRoot  ClassicQuadrantRoot  QuantumQuadrantRoot
              Intermediate        tokens: {Prefix} {QuantumLabel} {Gen} {N} {Level} {Algorithm} {Track} {Id}
   Rules      at most 64 characters (X.520), every CA a different name, only the tokens above, file-name
              stem only a-z 0-9 '-'. The script stops with the reason; -ShowNames previews everything.
   File stem  agantra-q1-ev-g1 style, used in the CRL / CA-issuer URLs ({ca}) and in pki\publish.
 Every CA subject also carries jurisdictionC, serialNumber, C, L, O, OU, name, emailAddress,
 telephoneNumber. O is written without the umlaut: Agantra Inovatif OU. OU per layer: OU_Root, OU_Track,
 OU_Quadrant, OU_Intermediate in [ pki_settings ].

 5  POLICIES, EXTENSIONS, REVOCATION
====================================================================================================
 Policy OIDs                  EV 2.23.140.1.1     OV 2.23.140.1.2.2     DV 2.23.140.1.2.1  (CA/B Forum defaults)
   The EV policy is REQUIRED: it is always written (a blank value falls back to the default), so a
   client or application can tell that it holds an EV certificate. Change the values in
   agantra_pki.cnf [ policy_oids ] or with -EvPolicyOid. EV, OV and DV must be valid and different.
   Enterprise Root and Track Roots   All issuance policies (anyPolicy 2.5.29.32.0; Windows: "All issuance policies") + EV
                                     2.23.140.1.1, NOTHING else: no OV, no DV, no PEN, no custom policy. No extended key usage
                                     (Windows: all application policies).
   Quadrant Roots                    EV, OV and DV (+ the PEN policies and [ custom_policies ]).
   Intermediates                     only their own level (policy isolation) + the PEN policies of that level + custom policies.
   Leaves                            their level + the PEN policies of that level + custom policies + -Policy.
   The EV leaf carries EV.
 IANA Private Enterprise Number (PEN)   67096 (Agantra Inovatif OU): PEN in agantra_pki.cnf [ iana_pen ]
   or -IanaPen <number>. When set, these OIDs are added (PenPolicyArc defaults to 1):
        1.3.6.1.4.1.<PEN>.1      company policy        Quadrant Roots, intermediates, leaves
        1.3.6.1.4.1.<PEN>.1.1    company EV level      Quadrant Roots, EV intermediates, EV leaves
        1.3.6.1.4.1.<PEN>.1.2    company OV level      Quadrant Roots, OV intermediates, OV leaves
        1.3.6.1.4.1.<PEN>.1.3    company DV level      Quadrant Roots, DV intermediates, DV leaves
   NOT in the Enterprise Root and the Track Roots (they carry All issuance policies + EV only).
   Your applications can therefore recognise a company EV certificate by its own OID.
 Extra policies   agantra_pki.cnf [ custom_policies ]:   label = OID | CPS-URL
   Written into every Quadrant Root, intermediate and leaf (NOT the Enterprise Root and Track Roots). Phase B adds a leaf
   parameter for more. A policy missing from the CA certificates is not asserted by the CA chain.
 CA extensions   basicConstraints critical CA:true pathlen:N | keyUsage critical keyCertSign,cRLSign
   subjectKeyIdentifier | authorityKeyIdentifier keyid:always | certificatePolicies |
   crlDistributionPoints + authorityInfoAccess (CA Issuers, OCSP) pointing to the issuer.
 EV leaf         CA:false | digitalSignature (+ keyEncipherment for RSA) | EKU serverAuth + clientAuth |
   SAN (DNS, IP, e-mail; a wildcard prints a warning) | policies | CRL | AIA | at most 398 days.
 Locations       [ crl_urls ] [ ocsp_urls ] [ ca_issuer_urls ]; "{ca}" = the issuing CA's slug.
   Files go to pki\publish\; you copy them to the hosts. Windows reports "revocation server offline"
   for client certificates until one URL answers. CRL lifetime 365 days.
   ML-DSA CRLs are signed with ML-DSA; a client that cannot validate ML-DSA cannot check them either.

 DIAGRAM 3 - TLS 1.3 HANDSHAKES  (classic and quantum quadrants)
 ---------------------------------------------------------------------------------------------------

  A. CLASSIC leaf (Q1 / Q2): works with every client
        CLIENT (browser, Windows 11, Go, Node, curl ...)               SERVER (any)
          |  ClientHello: groups = X25519MLKEM768, X25519 ...            |
          |------------------------------------------------------------->|
          |  server picks X25519MLKEM768 if it can, else X25519          |
          |<-------------------------------------------------------------|
          |  Certificate: RSA / ECDSA chain from this PKI                |
          key exchange: hybrid (quantum-safe)   authentication: RSA / ECDSA (classical)

  B. QUANTUM leaf (quadrants 3 / 4): both ends must support ML-DSA certificates
        CLIENT with OpenSSL 3.5+ (curl, Python, Node, nginx proxy ...)  SERVER with OpenSSL 3.5+
          |  ClientHello: groups = X25519MLKEM768 ... ; signature_algorithms include mldsa44/65/87
          |------------------------------------------------------------->|
          |  Certificate: ML-DSA leaf + ML-DSA chain from this PKI       |
          |<-------------------------------------------------------------|
          key exchange: hybrid ML-KEM        authentication: ML-DSA   =  fully post-quantum handshake

  C. Where B is not possible: Windows Schannel servers, Java 25, browsers and Windows 10 clients do not
     offer or accept ML-DSA certificates: the handshake fails. For such clients the site needs a Classic
     leaf (A). An OpenSSL server can hold both an RSA and an ML-DSA certificate and present the one the
     client supports (dual-certificate setup; possible with OpenSSL-based servers, test it first).

 DIAGRAM 5 - ENTERPRISE ROOT SIGNED BY A PUBLIC CA  (PUBLIC-CA-ENTERPRISE-ROOT.txt)
 ---------------------------------------------------------------------------------------------------

  MODEL A  subordinate                              MODEL B  cross-sign (your root stays self-signed)

   Public root (already in every client)             Public root (in clients)         Your Enterprise Root
        |                                                  |                           (self-signed, installed
   Public CA intermediate                           Public CA intermediate              on clients that use it)
        |   signs root.csr  (pathlen >= 3)                |   signs root-cross.csr          |
   ENTERPRISE ROOT  (now an intermediate)           ENTERPRISE ROOT - cross-certificate    |
        |   same key, same subject  ----------------------+---------------------------------+
   Track Root -> Quadrant Root -> Intermediate -> leaf      (everything below is unchanged: same CAs, same leaves)

   Server sends (A):  leaf, intermediate, Q root, Track root, Enterprise Root, public intermediate
   Server sends (B):  <leaf>-fullchain-cross.crt = fullchain + cross-certificate + public intermediate

   Every CA below ends before the public certificate does (validity is shortened automatically).
   Windows: Enterprise Root of model A goes to LocalMachine\CA, not Root.   Use with -ClassicPKI.

 9  LIMITATIONS
====================================================================================================
 L1   ML-DSA certificates are not usable for HTTPS on Windows Schannel (Kestrel / IIS on Windows), Java 25
      or any listed browser (7.1). A Quantum leaf cannot be shown in Edge / Chrome / Brave / Firefox /
      UC / QQ. Browser-facing sites use Classic leaves; the Quantum quadrants serve OpenSSL-based
      services and mutual TLS between your own systems.
 L2   Mixed deployments need two certificates for one site (Classic + Quantum) or two sites. Phase B
      will not change that: it is how the client ecosystem works today.
 L3   ML-DSA signatures are big: about 3.3 KB (ML-DSA-65) and 4.6 KB (ML-DSA-87) each. A Quantum chain of
      leaf + intermediate + quadrant root + track root carries four of them: tens of KB. Servers, proxies
      and load balancers with small header or handshake limits can fail.
 L4   The Quantum FIPS quadrant (number 4, named Quantum Q2) needs a FIPS provider that contains ML-DSA (OpenSSL 3.5+ / 4). The
      FIPS provider is not by itself a compliance claim (L13).
 L5   Private PKI. Every client installs the Enterprise Root. Firefox, Chrome on Linux, Java, Node,
      Python, PHP and Android apps have their own stores or settings (manual, section 7).
 L6   UC Browser and QQ Browser are not verified and may ignore user-installed roots. Test first.
 L7   Validity beyond the year 2038 can fail on 32-bit time stacks (old 32-bit Android, embedded).
 L8   OpenSSL. This script needs 4.x, which no listed OS packages, and 4.0 is a short-support release
      (about May 2027; OpenSSL 3.5 LTS runs to April 2030). Servers can use 3.5. macOS /usr/bin/openssl
      is LibreSSL: use a Homebrew OpenSSL 4 with -OpenSslPath.
 L9   PowerShell 7 is required. FreeBSD is not an officially supported PowerShell platform: build
      the PKI elsewhere and install root.crt by hand. Certificate-store functions are Windows only;
      other systems use the commands in the manual. macOS and Linux have no ML-DSA-aware system store
      or browser; use the root in OpenSSL-based tools.
 L10  Windows 10, Windows 11 before 24H2 and Server 2022 cannot hold ML-DSA certificates. On them the
      Quantum quadrants are skipped by default and -InstallTrust fails for them if forced.
 L11  ML-DSA private keys in a PFX: Windows 11 24H2+ / Server 2025 should import them (CNG ML-DSA), but
      this is not documented well and untested by me. If Import-PfxCertificate and certutil both fail,
      the PFX stays on disk and a warning is printed.
 L12  P-521 is used for the Q2 CA signature. Windows, macOS, NSS and BoringSSL verify it, but some TLS
      stacks restrict P-521 in handshakes. Leaves are P-256 for that reason.
 L13  FIPS. The quadrants use the OpenSSL FIPS provider for key generation and signing. That is not a
      compliance statement: it holds only for a FIPS-validated module of the exact version and only for
      algorithms the module covers. The module must match the OpenSSL version.
 L14  Keys are plain PKCS#8 PEM files protected by file permissions. For production keep the roots
      offline or in an HSM. The PFX password defaults to Abc12345!: change it with -Password.
 L15  Revocation. CRL / OCSP / CA Issuers URLs help only after you publish pki\publish at those hosts.
      No OCSP responder is provided. An ML-DSA CRL can only be checked by a client that supports ML-DSA.
 L16  Leaf lifetime. EV 397 days, OV 3 years, DV 5 years by default. Chrome and Apple apply the 398-day
      limit to publicly trusted roots only (private roots are exempt), Windows and Firefox do not
      enforce it, but your own security policy or a customer's scanner may. Phase A issues EV leaves.
 L17  Phase A has only the default EV leaves. DV / OV leaves, formats (DER, P7B, ...), custom leaf
      policies, TLS / cipher guidance output, the transport zip and a new pki_reuse.ps1 are Phases B, C.
      pki_reuse.ps1 and GenerateLeafCertificate.ps1 still expect the old single-root layout.
 L18  Testing. Tested on Linux with PowerShell 7.4 and a real OpenSSL 4.0.3 (built from source with the FIPS
      provider): the full four-quadrant PKI with real ML-DSA, default and FIPS providers; -Check, -Verify,
      tamper detection, strict failure and -PqcFallback; a live TLS 1.3 handshake with the ML-DSA leaf
      (Peer signature type mldsa65, group X25519MLKEM768, Verification OK); -ClassicPKI; naming overrides and
      refusals; the public-CA flows (subordinate and cross-sign) against a stand-in CA; the three module sets.
      NOT tested by me: the Windows
      certificate store functions, any Windows machine, any browser, UC / QQ, macOS, FreeBSD, nginx /
      Apache / Kestrel / Node / Python as servers. Section 14 closes that gap on your machines.
 L18a PFX and FIPS. The FIPS provider has no PKCS#12 KDF, so the normal .pfx of a FIPS quadrant is
      packaged with the default provider (the key stays FIPS-generated); a FIPS-conformant -fips.pfx
      (PBMAC1) is written next to it for the FIPS leaves. Windows import of the -fips.pfx is untested.
 L19  Information in section 7 reflects public documentation of mid-2026 and your screenshots.
      Versions change: check nginx -V, process.versions.openssl, ssl.OPENSSL_VERSION, your Windows build.
 L20  PHP 8.4.13 and Python builds on Windows may bundle an OpenSSL older than 3.5: no ML-DSA and no
      hybrid key exchange there. Java 25 never offers the hybrid group.
 L21  The IANA PEN (67096) is set; company OIDs appear in certificates made AFTER it was set. Existing CAs do not have them (rebuild), and a leaf then warns that its issuer lacks the policy.
 L22  Policy OIDs alone do not make a browser show an EV badge: that needs a public root in the browser's
      EV list. They let YOUR applications recognise the certificate type.

 L23  Public CA (PUBLIC-CA-ENTERPRISE-ROOT.txt). Tested with a stand-in CA, NOT with DigiCert, GlobalSign or
      Sectigo: I did not verify their products, prices or rules. A public CA may refuse RSA 8192 / P-521,
      allow pathlen below 3 only (then level 0 cannot be signed), require an HSM, impose name constraints
      and cap validity. Signing is manual (files); no portal / ACME / REST.
 L24  Under a public root, public TLS rules apply to every leaf (398 days, no private names the CA does not
      allow); the 1000 / 500 / 400 / 250 year CAs are shortened to the public certificate's end date; the
      ML-DSA quadrants are useless for browsers. Use -ClassicPKI with it.
 L25  Renewal of a public-CA-signed Enterprise Root is manual: everything below ends with it, so plan the
      re-signing of the same key and the re-issue of the CAs below early.
 L26  Only level 0 (Enterprise Root) is signed by the public CA. Signing a lower level (Q1 Root or an
      intermediate) is possible in principle but not automated (document, section 5).
 L27  CA names are fixed when a CA is issued: changing a template later needs -Clean (a new PKI).
 L28  Track and Quadrant Roots in the Trusted Root store are trust anchors although they are not self-signed
      (owner decision, 10.17). Consequences: trust in a Quadrant Root does not depend on the Enterprise Root
      staying installed; removing the Enterprise Root alone does not remove trust in the branches (use
      -RemoveTrust / -RemoveAllTrust); a branch can be trusted on its own. Whether Windows accepts the chains
      is shown by -Verify ("Windows chain"); that result on your machine is the proof.
 L29  Machine-wide OPENSSL_CONF. Install-DevEnvironment.ps1 writes a master OpenSSL configuration (default,
      fips AND the third-party oqsprovider) and sets OPENSSL_CONF for the machine. pki_setup.ps1 ignores it:
      every OpenSSL command gets its own configuration. Plain "openssl" commands in your shell still use the
      master file; an oqsprovider built for OpenSSL 3 may print errors under 4.x, which does not affect the PKI.
      Two ML-DSA implementations (native and oqsprovider) in one shell can confuse other tools.
 L30  Install-DevEnvironment.ps1 installs FireDaemon.OpenSSL (latest). It is not guaranteed to be 4.x; the
      scripts check and say so (section 2.3 of the manual).
 L31  Phase B was tested here on Linux with OpenSSL 4.0.3 and the real FIPS provider: all levels, all four quadrants,
      every format, the floors, the naming, live TLS 1.3 handshakes. NOT tested: -InstallPfx and everything that
      touches the Windows stores, Windows PowerShell behaviour of convert-formats.ps1 (UTF-8 with BOM), and the
      server snippets of tls-guidance.txt in your nginx / Apache / Kestrel versions.
 L32  ML-DSA leaves: Windows Schannel (Kestrel / IIS on Windows), Java 25 and browsers do not accept them for HTTPS
      (L1). Issue Classic leaves for those; the Quantum leaves are for OpenSSL services and mutual TLS (10.11).
 L33  -Duns writes organizationIdentifier = DUNS+<number>. The CA/Browser Forum has no D-U-N-S scheme there; this is a
      private convention. EV here means the EV policy OID and subject fields, not a browser EV badge (L22).
 L34  .cer is written as DER (the Windows default export); .cert as PEM; .p7b as PEM-armored PKCS#7 with leaf and
      chain. The conversion script shows how to get the other encodings.
 L35  tls-guidance.txt lists cipher suites and group names that are right for OpenSSL 3.5+ / 4.x servers. FIPS group
      names (SecP256r1MLKEM768 ...) and ChaCha20 / X25519 exclusion follow common FIPS practice; confirm against the
      validated module you deploy. Windows Schannel has its own cipher policy (registry / group policy).
 L36  Unlock = the Read-only attribute is removed from EVERY file and folder of the script folder at every start. A
      key file you marked read-only on purpose is writable again: protect keys with access rights (ACLs) instead.
 L37  The Windows Internet mark is removed with Unblock-File: tested only for its Read-only part on Linux.
 L38  leafcerts\ is never deleted by pki_setup.ps1; leaves of a replaced PKI do not chain to the new one (warning).
      Leaves of version 4.6 (pki\leafcerts) are not moved.
 L39  An OCSP signing certificate is for YOUR OCSP responder; this PKI does not run one. A time stamping certificate
      needs a time stamping authority service to be useful.
 L40  Phase C was tested on Linux (OpenSSL 4.0.3, real 7-Zip, Ubuntu 24.04 real system store). NOT tested: -Install / -RemoveTrust on
      Windows, macOS, and the other Linux families except by simulation (--dry-run with a fake os-release). The package names of 7-Zip on
      the RHEL family (EPEL) and SUSE are best effort.
 L41  7-Zip takes the password as an argument (visible in a process list while it runs). The built-in zip engine has no such process.
 L42  ZipCrypto is cryptographically weak; it exists for destinations without 7-Zip and for packages without secrets.
 L43  A package with leafcerts or CA keys is as sensitive as those keys; -IncludeCaKeys lets the destination issue certificates your
      clients trust. Nothing here protects the package after it is unpacked: protect and delete the extracted keys.
 L44  macOS may refuse ML-DSA certificates (post-quantum support of the keychain); classic CAs install. The shell script reports which.
 L45  An Enterprise Root signed by a public CA is not installed as a trust anchor on Linux / macOS (the public root already is).
 L46  The OpenSSL source build was NOT completed here: a 1-core VM compiled for over 30 minutes without finishing. Tested: the download, the checksum, the
      Configure with the full flags, and the five readiness checks against a real OpenSSL 4.0.3. Build time: 5 minutes on 8 cores, over an hour on one.
 L47  Install-DevEnvironment.ps1 was not run on Windows 11 (WinGet, the FireDaemon upgrade, Windows PowerShell 5.1); it parses and its help, unblock and readiness
      code ran on PowerShell 7 / Linux. The package names of 7-Zip (EPEL on the RHEL family, SUSE) and of dotnet / node / go / php are best effort.
 L48  The bootstrap scripts need the Internet and root (or administrator). Distribution packages may be older than "latest". Nothing is removed or downgraded.
 L49  A source build trusts the SHA-256 of the same release page (not a signature). The pwsh download is checked against hashes.sha256 of its release.
 L50  A -AddDevelopmentSAN certificate has 428 SAN entries (about 6 KB more) and is NOT EV-conformant in its SAN: a public CA, a CT-logging validator or a browser
      EV policy would reject it. Some clients ignore IP-address SANs or limit the SAN size. leaf-index.json lists every SAN entry of every certificate.
 L51  A wildcard covers one label only (*.nextmantra.com does not match a.b.nextmantra.com or nextmantra.com): the development list therefore names the apex
      domains separately and has no deeper wildcards.
 L52  The development SAN is added to certificates made by GenerateLeafCertificate.ps1 only, not to the default EV leaves of pki_setup.ps1.
 L53  Certificates cannot be renamed: a PKI built before 4.9.x keeps its old names, subjects and policies (a Quantum quadrant root called "... Q3 Root CA G2", roots with OV / DV
      policies, no PEN). Rebuild with pki_setup.ps1 -Clean to get the current ones; the leaves of the old PKI then no longer chain to the new CAs. Leaf files made earlier keep
      their q3 / q4 names.
 L54  The short code signing subject is not an "EV code signing" subject in the CA/B Forum sense (no serialNumber, jurisdiction, businessCategory): it is for your own lab.

 17  TRANSPORT DESIGN  (Phase C: PkiTransport.ps1, Unpack-PkiTransport.ps1, pki-transport.sh)
====================================================================================================

 17.1 Flow
   SOURCE                                            DESTINATION
   PkiTransport.ps1 -Pack                            Windows 11 25H2+        PkiTransport.ps1 -Install        scan -> unpack -> trust
     Initialize-PkiConfiguration + Import-PkiExisting  any pwsh 7             Unpack-PkiTransport.ps1          unpack only
     Get-PkiPackagePlan   (CAs, bundles, chains,       Linux, macOS           pki-transport.sh                 scan -> prepare -> unpack -> trust
       publish, [leafcerts], [pki])                  --------------------------------------------------------------------------
     manifest: certpack.json / .tsv / SHA256SUMS     Open-PkiCertPackage: decrypt, SHA-256 of EVERY file, then
     New-PkiCertPackage -> .certpacked (zip | 7z)      Get-PkiPackageSelection -> Export-PkiPackageSelection -> Install-PkiPackageWindows
     read back (every entry authenticated)             -> Test-PkiPackageChains (OpenSSL 4)

 17.2 Package  (format version 1)
   Archive    zip AES-256 (WinZip AE-2, built in), zip ZipCrypto (legacy), 7z AES-256 with encrypted headers. Detected by the first bytes.
   Layout     certpack.json  certpack.tsv  SHA256SUMS  README.txt
              ca/roots/<slug>.crt  ca/intermediates/<slug>.crt  ca/ca-bundle-roots.crt  ca/ca-bundle-all.crt  ca/chains/<slug>-fullchain.crt
              ca/publish/*  [ca/external-chain.pem  ca/cross-sign/*]  [leafcerts/*]  [pki/*]
   Roles      root, intermediate, chain, bundle, bundle-roots, publish, external, cross, leaf, leaf-index, pki
   certpack.tsv   role, path, sha256, size, sha1, store, externallySigned, kind, name   (a shell script needs no JSON parser)
   Rebase     the absolute paths in pki/pki-manifest.json are rewritten to the destination when pki/ is extracted.

 17.3 Security model
   Protected   confidentiality and integrity of the package in transit and at rest: AES-256 + HMAC per entry (zip) or AES-256 (7z); SHA-256
               of every file in the manifest; extraction refuses names that leave the destination; a wrong password writes nothing.
   Not protected  the machine that unpacks; the extracted private keys; the password channel; a weak password (policy: 12+ ASCII, 3 classes);
               ZipCrypto (weak by design; refused with private keys); 7-Zip receives the password as an argument.
   Scope as risk  CA certificates only = public data. leafcerts = leaf private keys. -IncludeCaKeys = the ability to issue trusted certificates.

 17.4 Destination rules
   Windows    install only on Windows 11 client build >= 26200 (25H2); older Windows, Server, other OS refused (exit 2). Roots -> Trusted
              Root, intermediates -> Intermediate (Install-PkiTrust, with read-back); PFX: leaf only. OpenSSL >= 4.0.1 required (exit 4).
   Linux      family from /etc/os-release: debian / rhel / suse; anchors dir + update command per family; ca-certificates installed when the
              store tooling is missing; 7-Zip installed when needed; OpenSSL 4.0.3 built from the official release (checksum verified) on consent.
   macOS      security add-trusted-cert (roots) / add-certificates (intermediates, all-ca) in the System keychain.
   Roots      every root is an anchor on Linux / macOS by default (one kind of anchor); --trust changes it.

 17.5 Reuse
   Module set Transport = 00_Common, 02_OpenSSL (OpenSSL discovery and versions, the bootstrap advice), 07_TrustStore (Install-PkiTrust, read-back,
   removal), 09_Administrator, 16_CertPack, 17_Transport. Packing loads the Library set (config, catalog, Import-PkiExisting). -Kit copies the
   destination files, so a destination does not need the project.

 17.6 Tests run (Linux, OpenSSL 4.0.3, real 7-Zip 23.01, real Ubuntu system store)
   * archive engine vs real 7-Zip both ways (AES zip, ZipCrypto, 7z), unicode / empty / 5-byte / random files, wrong password, tamper, traversal;
   * pack: all scopes and formats, refusals (ZipCrypto + keys, weak or non-ASCII password, no leaf match); unpack: every selection;
   * transported PKI issues a leaf that verifies against the original root; Windows gate with 10 simulated machines; exit codes;

     --trust modes, --destdir, selections, error exit codes, apt installation of 7-Zip, ZipCrypto with unzip only, 7z, tarball checksum.

 18  DEVELOPER BOOTSTRAP DESIGN  (Install-DevEnvironment.ps1 / Install-DevEnvironment.sh)
====================================================================================================

 18.1 Purpose and contract
   Prepare a machine for the PKI scripts and for development; install what is MISSING; verify each component by finding the program; prove OpenSSL;
   report a summary; never remove or downgrade. Same options on both sides: check, only / skip, unblock, help. Exit codes: 0 ok, 4 OpenSSL not ready.

 18.2 OpenSSL readiness  (the single definition, implemented in PowerShell and in bash)
   version >= 4.0.1  |  FIPS provider loads with fipsmodule.cnf and is active  |  ML-DSA-65 key + sign + verify  |  ML-KEM-768 key generation  |
   ML-DSA-65 inside the FIPS provider (warning only).  A build that fails any of the first four is STRIPPED and refused.
   Windows: FireDaemon.OpenSSL by WinGet, upgraded when older; fipsmodule.cnf by "openssl fipsinstall"; master openssl.cnf: default + FIPS (+ oqsprovider
   only when its DLL exists and -WithOqsProvider was used).   Linux / macOS: official source release, SHA-256 of the release page, Configure with enable-fips,
   make install, rpath so that no LD_LIBRARY_PATH is needed, link openssl4, system openssl untouched.

 18.3 Reuse
   The PKI scripts find the bootstrap next to themselves or in the parent (Find-PkiCompanionScript, 16_CertPack.ps1) and call it (Install-PkiSevenZip,
   Install-PkiOpenSsl, 17_Transport.ps1); pki-transport.sh calls Install-DevEnvironment.sh and keeps its own copy of the build for a destination that
   has only the shell script. 02_OpenSSL.ps1 searches /opt/openssl-4*, /usr/local/openssl-4*, ~/.local/openssl-4* and Homebrew paths.

 18.4 Unblock + unlock
   Windows: Zone.Identifier removal + Read-only attribute (Get-Item -Stream, Unblock-File). Linux: chmod -R u+rw, execute bit, chattr -i. macOS: xattr -dr
   com.apple.quarantine, chflags nouchg,noschg. At every start, silently; --unblock does only that. Tested: the Linux part (read-only files and folders at
   several depths, both shell scripts and Install-DevEnvironment.ps1 on PowerShell 7).

 18.5 Tests run
   Install-DevEnvironment.sh on Ubuntu 24.04: --check, readiness vs the real OpenSSL 4.0.3 (pass), vs the system 3.0 and a fake 4.0.3 (refused), real apt
   install of 7-Zip with verification, dry runs (Ubuntu, Rocky, openSUSE, macOS), pwsh lookup, OpenSSL download + checksum + Configure + the start of the
   compile (542 objects in two minutes on 1 core), --unblock. PowerShell: -InstallMissing installs 7-Zip through the companion script; kit contents;
   Install-DevEnvironment.ps1 -Help / -Unblock and the readiness functions. NOT run: Windows, macOS, the finished compile.
